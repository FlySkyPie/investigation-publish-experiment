00496_etl-multimodal-retrieval-paradigms

ETL 領域的多模態檢索範式：跨資料孤島的使用者檢索系統之領域模型與核心概念#

摘要#

本報告回答一個特定問題：當目標不是用 ETL 進行機器學習或資料探勘，而只是要建立一套「方便使用者檢索資料」的系統，且資料分散在多個資料孤島（data silo）中時，該領域存在哪些檢索範式，以及必須掌握哪些領域模型與概念。

結論先行：這個問題落在三個學科的交集上，分別是資訊檢索（Information Retrieval, IR）、資料整合（Data Integration）與中繼資料管理（Metadata Management）。ETL 在此不是主角，而是被刻意繞過的對象。取代它的主要範式有三類：

  1. 聯邦式查詢／資料虛擬化（Federated Query / Data Virtualization）：不搬資料，查詢期即時向來源取用。
  2. 索引式企業搜尋（Index-based / Crawl-and-Connector Enterprise Search）：搬內容或中繼資料副本到一個集中索引。
  3. 多模態向量檢索與檢索增強生成（Multimodal Vector Retrieval / RAG）：跨文字、圖片、表格、文件頁面等模態，以語意向量與生成模型服務檢索。

三者可以疊加使用。真正的難點通常不在模型本身，而在語意對齊（semantic alignment）、權限傳遞（permission propagation）、新鮮度（freshness）與排序融合（rank fusion）。

一、問題界定：這裡的 ETL 為何與機器學習無關#

傳統 ETL 的定義是：週期性地從來源系統擷取（Extract）、轉換（Transform）、**載入（Load）**到一個目標儲存體，之後的查詢都跑在一個整合後的副本上。它的代價是批次延遲（batch latency）與資料重複（duplication）1。

相對地，**聯邦式（federated）／虛擬化（virtualized）**的做法「把資料留在來源系統，將查詢即時翻譯為來源特定的請求，並即時彙總結果」（leaves data in place at source systems, translates queries into source-specific requests on-demand, and aggregates results in real-time）1。

需注意一個常見誤解：「不用 ETL」並不等於「沒有中繼資料工程」。索引式搜尋仍然需要連接器、schema 註冊、ACL 抽取與增量同步；這些是 ETL 的「檢索取向變體」，只是目的從「建模」變成「可被找到」。因此本報告把 ETL 的替代路徑視為中繼資料與內容的搬運策略問題，而非機器學習問題。

Promethium 的結論值得引用：多數成熟的資料組織「並不在地端 ETL 與虛擬化之間二選一，而是策略性地兩者並用」，用虛擬化做探索與營運視圖，並為已驗證的使用情境做實體化（materialize）1。這正是「方便使用者檢索」這類系統的典型姿態：先能查到，再談要不要落地。

二、範式 A：聯邦式查詢與資料虛擬化#

2.1 三個常被混用的概念#

資料聯邦（Data federation） 是一種技術：跨多個資料儲存執行單一查詢，並把合併結果呈現得像是來自單一邏輯資料庫。作法是「把查詢拆成給各參與資料庫的子查詢，在各自系統上執行這些子查詢，再把結果合併為單一回應」。當來源相對同質（相容的 SQL 方言）時運作良好，但在混合關聯式資料庫、NoSQL、SaaS API 與檔案系統的異質環境中表現吃力1。

資料虛擬化（Data virtualization） 是一個更廣的架構層，包含聯邦並加上額外能力。ThoughtSpot 定義它為「一種更廣的架構取向，包含聯邦，但也涵蓋快取、查詢最佳化與資料轉換層等額外能力」。經典框架（歸功於 Rick van der Lans）是：「資料聯邦是資料虛擬化的子集；資料虛擬化的功能包含聯邦。」 Denodo 描述它為在資料消費端與底層實體來源之間建立「穩定的邏輯介面」，採零複製（zero-copy）架構，資料在「有幫助時」才被搬移，但「不是預設選項」23。

聯邦式查詢引擎（Federated query engines） 是實作聯邦／虛擬化的軟體系統：一個單一 SQL 端點，透過連接器連上多個來源，並在它們之間規劃與執行查詢，過程中不需 ETL。Trino 被描述為「一個分散式 SQL 查詢引擎，設計用來查詢分散在一個或多個異質資料來源上的大型資料集」4。

2.2 核心領域概念#

（1）查詢下推（Query pushdown）

引擎把查詢的一部分（謂詞、投影、聚合、join、limit）下推到來源系統，讓來源做這些工作，以減少網路流量與遠端負載。Trino 明確記載以下下推類型5：

  • 謂詞下推（Predicate pushdown）：WHERE 條件過濾下推到來源；成功時 EXPLAIN 計畫不會出現 ScanFilterProject。
  • 投影下推（Projection pushdown）：只讀取被引用到的欄位。
  • 解引用下推（Dereference pushdown）：只讀取嵌套 ROW 型別中指定的欄位。
  • 聚合下推（Aggregation pushdown）：例如 count(*)、sum()、avg()、min／max、stddev、variance、corr、regr_*；若下推成功，EXPLAIN 不會顯示 Aggregate 運算子。限制包括 ROLLUP／CUBE／GROUPING SETS、聚合內的表達式、型別強制轉換，以及帶排序／過濾的聚合。
  • Join 下推（Join pushdown）：要求所有 join 謂詞都可下推，且資料表位於同一 catalog。
  • Limit／Top-N 下推：LIMIT 或 ORDER BY … LIMIT 被下推。

PostgreSQL 的 postgres_fdw 描述同樣的原則：它「嘗試最佳化遠端查詢以減少傳輸的資料量」，做法是把 WHERE 子句送到遠端，且不取用不需要的欄位；當兩張表都在同一遠端伺服器時，它會下推整個 join6。DuckDB 的 PostgreSQL 擴充則暴露 pg_experimental_filter_pushdown（預設 true）7。

（2）連接器與 catalog 抽象（Connector / Catalog abstraction）

Trino 的模型是：connector「使 Trino 適配某個資料來源……是 Trino 服務提供者介面（SPI）的實作」；catalog 是「一組用來存取特定資料來源的設定屬性，包含所需的 connector 與其他細節，例如憑證與 URL」，由一個 properties 檔定義，檔名即為 catalog 名稱。多個 catalog（甚至使用不同 connector）可在單一 SQL 查詢中被查詢8。Trino 內建數十種 connector（Iceberg、Hive、Delta Lake、MySQL、PostgreSQL、Oracle、Snowflake、Kafka、Cassandra 等）9。

Apache Calcite 以 schema adapter 表達同一個概念：「schema adapter 讓 Calcite 能讀取特定種類的資料，把資料呈現為某個 schema 內的資料表」，並提供 JDBC、Cassandra、MongoDB、Druid、Elasticsearch、Kafka、Redis、Splunk、Spark 等 adapter。Calcite 被用於「SQL 解析、查詢最佳化、資料虛擬化／聯邦，以及物化檢視改寫」10。

（3）跨來源的成本式最佳化（Cost-based optimization across sources）

  • Trino：「有了成本式 join 列舉，Trino 使用 connector 提供的資料表統計來估計不同 join 順序的成本，並自動挑選估計成本最低的 join 順序」（策略有 AUTOMATIC、ELIMINATE_CROSS_JOINS、NONE）。它也做成本式的 join 分發選擇（partitioned 對 broadcast）。關鍵是：「為了讓 Trino 最佳化器使用成本式策略，connector 實作必須提供資料表統計」11。PostgreSQL connector 支援透過 join-pushdown.strategy=AUTOMATIC 做成本式 join 下推，且只在統計顯示能提升效能時才下推12。
  • Denodo 把最佳化分為靜態階段（branch pruning、把條件與 group-by 推到 join 與 union 之下等改寫）與成本式／動態階段，後者「估計不同可能計畫的成本」，考量 join 策略（MERGE、HASH、NESTED）、來源間的資料搬移，以及 MPP 引擎的使用。成本估計使用來源索引與檢視統計（列數、null 數），可從來源的系統表取得。Denodo 警告：缺失或過時的統計會導致糟糕的計畫，因此 CBO「完全仰賴準確的資訊」13。
  • Apache Drill：「Foreman 把邏輯計畫交給成本式最佳化器以最佳化 SQL 運算子的順序……最佳化器套用各式規則，把運算子與函式重排為最佳計畫，並把邏輯計畫轉為實體計畫」14。
  • Apache Calcite：「成本模型引導整個過程，規劃引擎產生一個語意等價但成本更低的替代表達式。」Calcite 有針對成本函式與統計（選擇率、列數、不重複列數、大小、唯一鍵等）的中繼資料系統，並有兩種規劃引擎：VolcanoPlanner（動態規劃、窮舉搜尋）與 HepPlanner（固定順序規則觸發）15。
  • Dremio 的最佳化器「分析進來的查詢並自動改寫它們以使用預先物化的結果（Reflections）」，無需人工調校16。
  • PostgreSQL FDW 透過 use_remote_estimate（送出遠端 EXPLAIN）做成本估計，並以 fdw_startup_cost、fdw_tuple_cost 模型化連線與傳輸開銷6。

（4）Schema 映射（Schema mapping）

異質來源使用不同型別系統，因此 connector 必須雙向映射型別。例如 Trino 的 PostgreSQL connector 把 NUMERIC 映射為 DECIMAL、TIMESTAMPTZ 映射為 TIMESTAMP WITH TIME ZONE、JSONB 映射為 JSON、HSTORE 映射為 MAP(VARCHAR,VARCHAR)、VECTOR 映射為 ARRAY(REAL)，並提供 unsupported-type-handling 屬性（IGNORE 或 CONVERT_TO_VARCHAR）與 jdbc-types-mapped-to-varchar。名稱映射方面則透過 case-insensitive-name-matching 與一份 JSON 名稱映射設定檔，消解僅大小寫不同的 schema／資料表12。Calcite 透過 SqlDialect、SqlConformance 與 RelDataTypeSystem 客製化來控制映射10。PostgreSQL FDW 則用 foreign table 上的 schema_name、table_name、column_name 選項映射遠端名稱6。

（5）跨異質來源的查詢規劃（Query planning across heterogeneous sources）

Calcite 的關鍵機制是呼叫慣例（calling convention）：「呼叫慣例是特定資料引擎使用的協定。」在規劃多引擎查詢時，「Calcite 依其呼叫慣例為關聯表達式樹的區域『上色』。規劃器藉由觸發規則把運算子推入資料來源。若引擎不支援某個運算子，該規則就不會觸發。有時一個運算可出現在多個位置，最終依成本選出最佳計畫。」Converter 負責在慣例之間轉換資料（有執行期成本），而 EnumerableConvention 是後備方案，它「能實作所有核心關聯運算子與所有內建 SQL 函式」，作法是生成並編譯 Java 程式碼10。

Trino 的規劃是分散式的：coordinator 解析與規劃，把執行拆成樹狀的 stage，每個 stage 以 task 實作，task 操作從 connector 取得的 split8。Drill 則使用 major／minor fragment 搭配 exchange 運算子，並為資料本地性排程14。

（6）聯邦的 SPARQL 面向

聯邦不只是 SQL。CostFed（2018）提出 SPARQL 端點聯邦的成本式最佳化17；VLDB 2025 的 CDMS 工作坊則有〈Rethinking Pluggable Federated Query Optimization〉一文，檢討可插拔的聯邦查詢最佳化18。

2.3 具名系統#

2.4 實務注意事項#

  • 效能取決於來源能力。Trino 指出「下推的支援因各 connector 與相關底層資料庫或儲存系統而異」5。Denodo 表示 CBO 的品質取決於統計品質，而虛擬化「取決於來源效能；對網路敏感」113。
  • 正確性優先於下推。Trino 的 PostgreSQL connector「以正確性為優先」，不會下推可能改變結果的運算（例如因排序規則差異而對 VARCHAR 的範圍謂詞），除非開啟實驗性旗標12。
  • 異質性才是最難的部分。簡單的聯邦「在來源相對同質時運作優雅……但當你需要跨混合關聯式資料庫、NoSQL 儲存、SaaS API 與檔案系統的異質環境做聯邦時就會吃力」，而這正是虛擬化層、中繼資料目錄、快取與治理發揮價值之處1。

三、範式 B：索引式企業搜尋與連接器#

3.1 兩種根本架構#

企業搜尋必須統一散落在互不相連的 SaaS 與地端系統中的內容。存在兩種主流模式，而多數現代平台會混合它們。

（1）索引式（crawl／connector）搜尋

連接器把內容從各來源拉取（或被推送）出來、轉換，然後寫入一個集中索引。查詢時使用者只搜尋一個索引，不接觸來源系統。

  • Microsoft 的 synced Copilot connectors 是典型案例：「Synced connectors 把外部來源的內容爬取並索引進 Microsoft Graph。」每個項目帶有內容、中繼資料與 ACL。一旦匯入，「該項目就成為你組織雲端搜尋索引的一部分。它可被全文檢索，並由語意索引 AI 處理以決定相關性」28。
  • Glean 的「indexed access」模式：「內容與權限是先前被爬取、存於你的 Glean 租戶中，並在查詢時從該語料讀取。延遲通常很低」29。
  • 優點：統一的相關性排序、查詢低延遲、豐富的排序訊號、一致的使用體驗、不造成每次查詢對來源的負載。
  • 缺點：內容是副本，可能過期；匯入成本高；權限漂移風險；完整爬取可能很慢（Glean 指出大型語料的初次同步「估計需 2 天完成」）29。

（2）聯邦式搜尋（query federation）

查詢在查詢期被廣播到多個來源系統，再合併結果。不建立內容的中央副本。

  • Vespa 的 container「允許多個資料來源被聯邦到一個共同的搜尋服務。這些資料來源可以是同一應用中的搜尋叢集，也可以是外部服務。」一個 provider 是「一個產生資料（以 Result 形式）的搜尋鏈」，而 FederationSearcher「把查詢平行轉發給所有 provider。各 provider 鏈把結果往上回傳給 federation searcher，後者把它們合併為完整結果」30。
  • Microsoft 的 federated connectors 使用 Model Context Protocol（MCP）：「即時抓取資料，不把內容索引進 Microsoft 365。聯邦連接器適合連接不應被索引的即時、動態或敏感資料來源。」「不需索引；資料留在來源系統」31。
  • Glean 的「live access」與「hybrid access」模式與此對應：live「在使用者請求期間呼叫來源系統以取得當前記錄或欄位」，hybrid「結合已索引資料與一次或多次即時呼叫」29。
  • 優點：永遠新鮮、無內容重複、原生尊重來源權限、適合敏感或動態資料。
  • 缺點：延遲較高、依賴來源可用性與速率限制、難以一致排序、合併異質引擎的分數很棘手。

（3）取捨對照

Microsoft 明確支援兩者共存：「聯邦與 synced 連接器可在你的租戶中共存，並一起出現在連接器清單中」28。

3.2 連接器框架#

連接器框架標準化任意來源的匯入方式。關鍵例子：

  • Microsoft Graph／Copilot connectors API：connection 是「你外部資料的邏輯容器，可供管理員視為單一單位管理」。生命週期狀態為 Draft → Ready → Obsolete／LimitExceeded。流程是：建立 connection → 註冊 schema → 匯入 items32。每個 externalItem 有三個部分：ACL、properties 與 content。schema（在匯入前註冊）定義哪些屬性是 searchable、queryable、retrievable、refinable，並定義語意標籤（title、url、createdBy 等）與 rank hints3334。Microsoft 提供「超過 100 個預建連接器」（Box、Dropbox、Google Drive、Confluence、Salesforce、ServiceNow、Jira 等），並可用 API 或 Agents Toolkit 建立自訂連接器，另有供地端來源使用的 Graph connector agent28。
  • Glean 連接器型別：native connectors（專用、直接呼叫來源 API，如 Slack、Salesforce、Google Drive）；web history connectors（瀏覽器擴充驅動，結果為每位使用者私有）；push API connectors（供自架／防火牆內系統，透過 Indexing API 推送資料）；partner connectors（由 Glean 技術夥伴建置維護）。Glean 的連接器目錄有 105 個連接器，官網稱 275 個以上連結。連接器做兩件事：資料抓取與內容解析，且它們「也會從各來源取得權限對映」3529。
  • Vespa 採用程式碼層級的連接器模型：一個 provider 內含 Searcher 元件，「連上資料來源並從回傳資料產生 Result」。連接器可指向內部內容叢集（type="local"）或外部服務30。
  • Algolia 是純索引（無爬取框架）：你透過 API 推送紀錄，並以 attributesForFaceting 定義可篩選屬性36。

3.3 權限感知檢索#

這是企業搜尋最難的問題：確保使用者只看得到其在來源系統中被授權看見的內容。核心張力在於權限在哪裡、何時被強制執行。

（a）ACL 傳播（early binding）

權限在匯入時從來源擷取、存到文件上，查詢期以過濾強制執行。

  • Microsoft Graph connectors：每個 item 帶有一個 ACL，「一個代表 Microsoft Entra 使用者或群組的存取控制項陣列」，並有一個 Everyone 項代表所有租戶使用者。deny 優先於 grant。對於非 Entra 群組（Salesforce Profiles、ServiceNow groups、Confluence groups），Microsoft 提供 external groups，可包含 Entra 使用者、Entra 群組與其他 external groups（可嵌套）37。重要指引：「避免把 external groups 的成員直接展開到個別 item 的 ACL 中，因為每個群組成員都可能導致大量 item 更新。」規模限制：「一位使用者應擁有少於 2,049 個 external security group 成員資格……擁有超過 10,000 個 external security group 的使用者，其查詢將以 400 回應失敗」37。
  • Glean 的「權限鏡像」：「當連接器爬取內容時，它也從該來源匯入權限模型（ACL、群組成員、角色指派）。在查詢時，Glean 會在回傳任何結果前，以登入使用者的身分比對這些鏡像權限」38。
  • Elasticsearch 的文件層級安全（DLS, Document Level Security）：角色帶有一個定義使用者可讀哪些文件的 query，例如 {"term": {"department_id": 12}}。角色查詢支援 Mustache 樣板以便引用當前使用者：{"term": {"acl.username": "{{_user.username}}"}}39。
  • OpenSearch DLS：等價機制，使用 OpenSearch Query DSL，並支援參數替代如 ${user.name}、${user.roles}、${user.securityRoles}、${attr.<TYPE>.<NAME>}40。
  • Vespa 使用 predicate fields：儲存於文件中的布林約束（例如 "gender in ['male'] and age in [30..40]"），在查詢時透過 predicate() YQL 函式與查詢屬性比對。Vespa 舉廣告投放與已存查詢為適用場景41。

（b）查詢期／late binding（查詢期安全裁剪）

  • Elasticsearch DLS 本質上是查詢期機制：「你可以用一個查詢指定每個角色能存取的文件……它與資料流與索引上指定的權限一起運作。」它在評分之後套用：「document level security 不影響相關性評分所用的全域索引統計……不符角色查詢的文件永遠不會被回傳」39。
  • OpenSearch 以 plugins.security.dls.mode 明確區分綁定模式40：lucene-level「直接改寫 Lucene 查詢與資料結構。這是最有效率但無法使用某些進階構造……包含 term-level lookup queries」；filter-level「OpenSearch 透過改寫收到的查詢來套用 DLS。這允許 DLS 查詢中使用 term-level lookup queries，但只能使用 get、search、mget、msearch 運算」；adaptive 為預設值，逐查詢自動選擇。
  • Algolia 以 secured API keys 實作 late binding：「在後端產生帶有 filters 的 secured API key（使用者無法修改這些 filters）」。filter（例如 visible_by:group/Finance）內嵌於金鑰並在伺服器端強制執行。visible_by 屬性保持可篩選，但被設為 unretrievableAttributes 以免洩漏於回應中42。
  • Microsoft federated connectors 本質上是 late binding：「來源系統強制執行所有權限。使用者只能存取其在原始資料來源中被授權檢視的內容，也只能做被授權的變更」31。

（c）early 與 late 的實務分野

  • Early binding（ACL 傳播）：權限物化進索引。查詢快，但權限變更需要重新索引，且必須維持鏡像 ACL 同步，有漂移與過期的風險。
  • Late binding（查詢期裁剪）：引擎把使用者身分注入查詢、即時過濾。永遠與來源變更同步、不需重新索引，但查詢期有成本與複雜度。
  • 真實系統通常兩者並用：ACL 被傳播（early），同時查詢期再用一個過濾器收斂到該使用者（late）。

（d）已知的安全限制（重要但常被忽略）

  • Elastic 警告：「雖然 document level security 阻止使用者檢視受限文件，但仍可能寫出會回傳整個索引聚合資訊的搜尋請求。一個被限制只能存取特定文件的使用者……仍可能得知僅存在於不可存取文件中的欄位名稱與詞彙，並計算有多少不可存取文件含有某個詞」43。
  • OpenSearch 警告 text 欄位中的 Unicode 特殊字元問題：像 User-1 這樣的值可能被分詞到 User-1 與 User-2 無法區分，「可能導致非預期的文件過濾，並可能危及對其存取的控制」。緩解方式是改用 keyword 欄位或自訂分析器40。
  • Elastic：「field and document level security 目前是設計與唯讀的特權帳號搭配運作。」寫入 API 不受 DLS 涵蓋43。
  • 多角色合併時，Elastic／OpenSearch 以 OR 合併 DLS 查詢（若有任一角色無 DLS，則以最寬鬆者為準）；欄位權限取聯集39。
  • OpenSearch 的 do_not_fail_on_forbidden: true 會靜默地回傳部分結果，「彷彿它就是完整資料集。沒有任何跡象顯示部分資料可能被省略」40。

3.4 增量同步、新鮮度與刪除#

  • Microsoft Graph connectors 定義兩種爬取機制與兩種同步間隔：incremental crawl「偵測並推送來源資料中的新增項；比完整爬取更省資源」；full crawl「從來源資料更新整個 item（重新爬取），捕捉所有新增與刪除」。同步方式可以是事件驅動（推送，建議用於動態或敏感資料）或排程（每 N 分鐘，建議用於內容豐富但較少更新、且不敏感的資料，如 wiki 或網頁）44。連接器「定期檢查變更。新增、更新或刪除的內容會反映到索引中。管理員可設定同步頻率並視需要觸發完整爬取」28。
  • Glean 執行五種爬取：full content crawl（依間隔索引整個語料）、incremental content crawl（「聚焦於上次爬取後被修改或新增的內容」）、activity crawl（「追蹤並索引特定變更……包含內容新增、更新、刪除與權限修改」）、identity crawl、people data。update rate 是「系統執行增量抓取的頻率」。刪除處理方面：API／webhook 刪除會在「數分鐘至數小時內」移除內容（OneDrive、SharePoint、Google Drive、Box、Slack、Confluence）；否則靠完整爬取清理移除過期內容。若刪除事件被漏掉，內容「會留在索引中直到下次完整爬取」。管理員可用 content hiding 暫時隱藏文件。Glean 也讓管理員調整 API 呼叫速率、並行度、退避與依尖峰／離峰的時段排程4546。
  • Vespa 是即時設計：「對資料的寫入會在數毫秒內可見」，因此「新鮮度」是內生的，而非基於爬取47。

3.5 相關性排序與結果融合#

排序是索引式系統的強項，因為所有訊號都在同一處：

  • Vespa 對「所有結果」使用查詢中選定的排名函式。函式可以是對純量或 tensor 的任意數學運算，可呼叫 ONNX 模型，並支援多階段排序（「把更多 CPU 配置給有潛力的候選」）。內建文字排序使用位置資訊，另有二維距離與新鮮度特徵，並提供 nativeRank 與 BM2547。
  • Microsoft Search 對「外部與內部結果一視同仁地排序，基於查詢匹配、新鮮度與使用者情境」。語意標籤與 rank hints（default → very high）用於調整屬性重要性；個人化來自行 Microsoft Graph 的訊號28。
  • Glean 使用活動訊號：「檢視、編輯與分享，Glean 用它們來依相關性排序搜尋結果，為每位使用者浮現最有用內容」，屬於圖與個人化驅動的排序模型29。

結果融合（rank fusion）：當要融合異質引擎的分數時，分數不可比。標準解法是 Reciprocal Rank Fusion（RRF）。Elasticsearch 的實作為：「一種把多個帶有不同相關性指標的結果集合併為單一結果集的方法。RRF 不需調校，且不同的相關性指標彼此不必相關。」公式為：

score = Σ 1.0 / ( k + rank(result(q), d) )

rank_constant 預設為 60。Elastic 要求「至少兩個 child retriever」，例如把 BM25 的 standard retriever 與 knn 向量 retriever 結合，且「已證實 RRF 的相關性優於單獨使用任一查詢」48。

Vespa 則在應用層處理合併：聯邦之後「我們得到一個結果，其中每個來源對應一個 HitGroup」，再以自訂的 ResultBlender searcher 攤平 hit groups 並套用來源特定的納入規則（範例是只保留 score > 0.7 的新聞 hit）。Vespa 指出最佳結果「不一定是一個攤平的清單」，有時保留來源組織更好；它也支援每個 provider 的逾時、可選 provider（太慢就丟棄）以及用於程式化選源的 TargetSelector30。

跨叢集搜尋（cross-cluster search） 是相關形式：「對一個或多個遠端叢集執行單一搜尋請求」。安全性透過 cross-cluster API keys 處理：「使用者的有效存取權是其角色權限與 API key 權限的交集。」DLS 支援於 search 參數但不支援 replication49。

3.6 系統對照#

四、範式 C：多模態向量檢索與檢索增強生成#

4.1 什麼是「多模態檢索」#

多模態（或跨模態）檢索指的是：以某一模態的查詢（例如文字）檢索另一模態的項目（例如圖片、影片、音訊、文件），或處理異質的查詢與候選集合（文字與圖片混合）。此領域的核心挑戰是異質模態落差（heterogeneous modality gap），也就是跨不同資料型態衡量語意相似度50。

在「跨資料孤島的檢索系統」脈絡下，多模態檢索之所以重要，是因為孤島內的內容本來就異質：ERP 裡是結構化表格、SharePoint 裡是 PDF 與 Office 文件、DAM 裡是圖片與影片、郵件系統裡是對話、工單系統裡是文字紀錄。若要讓使用者在單一入口找到全部，就必須處理這些模態。

4.2 融合分類學：early／late／hybrid fusion#

經典的分類法是依「模態在管線中何處被結合」來區分51：

  • Early fusion（早期融合）：在特徵／輸入階段結合模態（例如在共享編碼器前串接視覺與文字 token）。能早期捕捉跨模態互動，但當模態未對齊時很脆弱。
  • Late fusion（晚期融合）：各模態獨立處理，再於決策／分數層級結合（例如平均或排序融合各自檢索器的分數）。模組化且穩健，但對細緻的跨模態互動掌握較弱。
  • Hybrid／intermediate fusion（混合／中間融合）：在中間層融合（attention／cross-attention、encoder-decoder）。現代綜述另外納入 kernel-based、graphical 與 attention-based 等進階類別51。

代表性系統：

  • ViLBERT（2019）：使用雙流模型與 co-attentional transformer layers，屬於 late／intermediate 互動設計52。
  • ALBEF（2021）：主張「先對齊再融合」（Align before Fuse），在跨模態融合之前做對比式對齊53。
  • VLMo（2021）：以 Mixture-of-Modality-Experts 統一雙編碼器與融合編碼器54。
  • BLIP（2022）：統一理解與生成的視覺語言預訓練55。

在企業檢索的實務對應上，early fusion 對應「把所有來源的欄位攤平成單一 schema 再索引」，late fusion 對應「各來源各自檢索、最後用 RRF 合併」，hybrid fusion 則對應「共享語意層＋來源特定訊號」。

4.3 共用嵌入空間（單向量）#

以一個（或一對）編碼器把所有模態映射到同一個共享向量空間，在此空間中餘弦相似度即代表跨模態相關性。

  • CLIP（2021）：對比式圖文預訓練，是圖文檢索的基礎共用嵌入空間56。
  • CLIP4Clip（2021）：把 CLIP 遷移到影片文字檢索57。
  • ImageBind（2023）：僅使用與影像配對的資料，就把六種模態（影像、文字、音訊、深度、熱影像、IMU）綁進同一個嵌入空間58。
  • VISTA（2024）：以視覺化文字嵌入支援通用多模態檢索59。
  • GME（2024）：以 MLLM 為基礎的稠密檢索器，用於通用多模態檢索，以約 800 萬筆合成實例訓練60。
  • VLM2Vec（2024）：透過對比式訓練把任意 VLM 變成嵌入模型，並提出 MMEB 基準61。

4.4 遲互動與多向量檢索（ColBERT 家族）#

不為每個項目產生單一向量，而是為每個 token 產生一個向量，並計算查詢與文件 token 嵌入之間廉價的「遲互動」（MaxSim）。這能在允許文件離線編碼的前提下捕捉細緻匹配。

  • ColBERT（2020）：提出在 BERT 上的 late interaction（SIGIR 2020）62。
  • ColBERTv2（2021）：殘差壓縮與去噪監督，足跡縮小 6 到 10 倍（NAACL 2022）63。
  • PLAID（2022）：高效率遲互動引擎（centroid interaction／pruning），GPU 最多快 7 倍、CPU 最多快 45 倍64。
  • MUVERA（2024）：以 Fixed Dimensional Encodings 把多向量搜尋化約為單向量 MIPS（Google）65。
  • M3-Embedding／BGE-M3（2024）：單一模型同時支援稠密、多向量（ColBERT 式）與稀疏檢索66。
  • 多模態遲互動：PreFLMR（2024）把細緻遲互動的多模態檢索器規模化（KB-VQA）67；ColPali（2024）用 VLM 直接從文件頁面影像產生多向量嵌入並搭配遲互動，並提出 ViDoRe 基準（ICLR 2025）68。

ColPali 對「文件孤島」特別有意義：它讓使用者可以直接對掃描頁面、排版複雜的 PDF、含表格與圖表的報告做檢索，而不必先做脆弱的版面解析與文字抽取。

4.5 混合稀疏＋稠密檢索#

結合詞彙／精確匹配訊號（BM25、learned sparse）與語意稠密嵌入，再做排序融合（通常是 RRF）。

  • DPR（2020）：經典的稠密雙編碼檢索器69。
  • SPLADE（2021）：具反向索引效率的學習式稀疏詞彙擴展70。
  • 混合實務：BM25 ＋ SPLADE ＋ DPR／BGE，以 RRF 融合；已展示優於任一方（例如 SPLADE＋DPR 搭 RRF，nDCG@10 達 0.681）71。
  • 稠密－稀疏混合向量（2024）：單一索引的混合搜尋，避免雙路徑的複雜度72。
  • BGE-M3（2024）：在單一模型統一稀疏、稠密與多向量檢索66。

實務判準：BM25「對精確 token 依然無可取代」，例如產品編號、錯誤字串、函式名稱、法律術語、縮寫，而稠密嵌入恰好會在這些地方把關鍵 token 模糊掉。Anthropic 舉例：查詢「Error code TS-999」用純嵌入可能失敗，但 BM25 能找到該精確字串73。

4.6 多模態 RAG（MRAG）#

RAG 把「檢索 → 擴增 → 生成」串成管線，MRAG 則擴展到檢索並以圖片／影片／表格為條件，通常以 VLM 同時做檢索與生成。

  • RAG（2020）：原始檢索增強生成框架74。
  • MuRAG（2022）：第一個對圖片與文字做檢索增強的多模態 transformer75。
  • Retrieving Multimodal Information for Augmented Generation（2023 綜述）76。
  • DSE／Document Screenshot Embedding（2024）：直接編碼文件截圖來檢索77。
  • VisRAG（2024）：以 VLM 為基礎的 RAG 管線，把頁面當影像嵌入；相較純文字 RAG，端到端增益 20% 到 40%78。
  • A Survey on Multimodal Retrieval-Augmented Generation（2025）79。
  • Ask in Any Modality（ACL Findings 2025）：涵蓋檢索、融合、擴增、生成的完整 MRAG 綜述80。

4.7 統一／指令導引的通用檢索（新興範式）#

以單一模型處理多種跨模態任務，並由指令引導：

  • UniIR（2023）：單一指令導引檢索器處理 8 種檢索任務，並提出 M-BEIR 基準81。
  • GME（2024）與 VLM2Vec ＋ MMEB（2024）6061。

4.8 企業 RAG 的工程細節#

企業 RAG 已不再是「向量搜尋＋提示」的單階段系統。有 2026 年的生產指引直言：「RAG 的 Hello World 已正式死亡。2024 年只要嵌入文件跑餘弦相似度就夠了；2026 年那種做法是一種負債。」天真的單索引管線在真實企業查詢上約有 40% 無法浮現含答案的段落，而其中約 80% 的失敗可追溯到匯入與切塊層82。

失敗可分成兩類，必須分別診斷：

  • 召回失敗（recall failure）：含答案的區塊從未進入候選清單。修法是更好的切塊、混合搜尋、更強的嵌入、更大的第一階段 top_k。
  • 排序失敗（ranking failure）：正確區塊被檢索到但被雜訊埋住。修法是加 reranker。

更強的生成模型無法修好爛檢索，反而常讓答案更流暢、更有說服力卻建立在錯誤脈絡上82。

  • Contextual Embeddings ＋ Contextual BM25：降低 49%（5.7% → 2.9%）
  • 再加上 reranking：降低 67%（5.7% → 1.9%）

4.9 重排序（reranking）#

為何有效：第一階段檢索器是雙編碼器（bi-encoder），查詢與文件分別嵌入，因此捕捉的是主題相似度，而非真正的相關性。**交叉編碼器（cross-encoder）**把 (query, chunk) 對一起餵進 transformer 產生單一相關性分數，準確得多但無法預先索引。生產模式是：便宜地檢索前 50 到 100 筆（混合式），再重排到前 5 到 10 筆。

報告的效益：「增加 50 到 150 毫秒延遲與每查詢數美分成本，換得在困難查詢上 recall@5 提升 5 到 15 點，這幾乎是普遍划算的增益」82。

模型版圖（2026 年上半年）82：

  • 開放權重：bge-reranker-v2-m3（BAAI）是預設選擇。
  • 託管服務：Cohere Rerank（現為 Rerank 4.0，rerank-v4.0-pro／fast，支援 100 種以上語言）、Voyage Rerank 2.5、Jina Reranker v3（listwise）。
  • 2026 年初的獨立 ELO 測試把 Zerank 與 Cohere Rerank 4 Pro 排在頂端；Voyage rerank-2.5 是準確度與延遲平衡最佳的通用選擇；Cohere v3.5 最快。

關鍵規則82：

  • 重排序在召回高、精確度低時有幫助；在召回低時反而有害。 沒有重排器能救回從未進入候選清單的區塊。
  • 交叉編碼器過度偏重語意，在識別碼密集的查詢上表現較差（函式名稱、SKU），而這正是 BM25 發揮之處。
  • 把重排器放在單一可替換介面後面，並設逾時回退（退化為檢索順序，絕不回 500）。
  • 把區塊上限設在約 512 token 以維持重排延遲可預測；一張適度的 GPU（T4／L4）可讓 100 對在 50 毫秒內完成。
  • 它也能緩解「lost in the middle」效應。

Cohere 的 API 行為：給定 query 與 documents 清單，Rerank 回傳由語意相關性高到低排序的文件與 relevance_score（結構化資料建議以 YAML 字串傳入以獲得最佳表現）86。

4.10 查詢改寫（query rewriting）#

查詢改寫發生在檢索之前，重排序在之後。改寫的主要目標是召回，重排序的目標是精確度。

常見技術87：

  1. 查詢擴展：加入相關詞（例如「心臟病發作治療」→「心肌梗塞」、「心臟照護」）。
  2. 查詢分解：把複雜查詢拆成子查詢（多部分問題）。
  3. 查詢改述：產生替代說法。
  4. 多重查詢生成：產生數個針對不同面向的改寫版本再彙總。
  5. 逐步退後提示（step-back prompting）：先產生較廣義的問題再精煉（在脈絡稀薄時有效）。

相關技術：HyDE（Hypothetical Document Embeddings）——產生一個假設性的答案文件並嵌入它以提升召回（用於 GraphRAG 的 DRIFT search 內）；以及子查詢分解87。

它解決的問題：模糊／含糊查詢、缺少脈絡、詞彙不匹配、對話式追問（解析代名詞、延續先前限制）、跨內部系統的企業搜尋87。

限制：過度擴展（回傳不相關文件）、語意漂移、額外的 LLM 延遲與成本、評估複雜。它「不是完整解法」，仍需中繼資料過濾、重排序與強健的嵌入87。

4.11 GraphRAG（Microsoft）#

核心概念（GraphRAG 論文，arXiv:2404.16130，v1 於 2024-04-24，2025-02-19 修訂）：標準 RAG 在面對全域性問題時會失敗（「這份語料的主要主題是什麼？」），因為那是查詢導向的摘要任務，而不是明確的檢索任務。GraphRAG 用 LLM 以兩個階段建立圖索引8889：

  1. 從來源文件萃取實體知識圖譜。
  2. 為緊密相關實體的群組預生成社群摘要（透過 Leiden 技術做階層式分群）。

查詢時，每個社群摘要產生一個部分回應，所有部分回應再被摘要為最終答案（map-reduce）88。

基線 RAG 無法處理的兩類失敗90：

  • 「串接線索（connecting the dots）」：透過共享屬性串連分散的資訊片段。Microsoft 舉 VIINA 為例：基線 RAG 無法回答「What has Novorossiya done?」，因為沒有任何被檢索到的區塊提及它；GraphRAG 找到該實體並以出處佐證答案。
  • 整體／全域理解：例如「資料中的前 5 大主題是什麼？」

查詢模式89：

  • Global Search：透過社群摘要回答整體、跨語料的問題（廣度優先）。
  • Local Search：針對特定實體，向外擴散到鄰居與概念。
  • DRIFT Search（2024 年 10 月，由 Uncharted 提出）：結合全域與區域；用 HyDE 針對前 K 個社群報告（作為「引子」）擴展查詢，接著執行迭代式的區域搜尋追問。它在全面性上 78% 勝過 Local Search、在多樣性上 81% 勝過91。
  • Basic Search：標準的 top-k 向量搜尋。

2024 到 2026 的關鍵最佳化9293：

  • 動態社群選擇（2024 年 11 月）：LLM 從根節點開始為社群報告評分相關性，在 map-reduce 之前修剪不相關的子樹。相較靜態全域搜尋在第 1 層社群（1,500 份報告降到約 470 份），平均成本降低約 77%，品質相當；便宜的 GPT-4o-mini 評分器表現幾乎與 GPT-4o 一樣好。
  • LazyGraphRAG（2024 年 11 月；2025 年 6 月整合進 Microsoft Discovery 與 Azure Local）：把所有 LLM 使用延後到查詢時，用 NLP 名詞片語抽取建立概念圖，不做前置摘要。索引成本與向量 RAG 相同，僅為完整 GraphRAG 的 0.1%；在查詢成本與向量 RAG 相當的前提下，它在區域查詢上勝過所有競爭者；在品質相當時，查詢成本比 GraphRAG 全域搜尋低超過 700 倍。
  • 使用的評估指標：Comprehensiveness、Diversity、Empowerment（LLM 成對評判），加上 SelfCheckGPT 評估忠實度88。

何時該用：只在「對實體關係做推理」是被實測到的失敗模式時才導入，因為代價是圖的建置與維護89。對跨資料孤島的檢索而言，GraphRAG 的價值在於把不同孤島中指向同一實體（人、組織、專案、產品）的線索連接起來。

4.12 聯邦式／多來源 RAG#

定義：聯邦式 RAG 結合聯邦學習（分散式訓練而不暴露原始資料）與 RAG（以外部知識為依據），用於隱私敏感的領域，例如醫療、金融與個人化助理94.

第一份系統性對映研究（Chakraborty, Dahal & Gupta；arXiv:2505.18906，2025-05-24 提交、2025-09-02 修訂；發表於 Findings of EMNLP 2025, pp. 7362–7374, Suzhou, China, 2025 年 11 月）涵蓋 2020 到 2025 的文獻，辨識出三項關鍵挑戰：隱私保護檢索、跨客戶端異質性、評估限制94。

企業架構模式：聯邦式 RAG 讓你透過單一統一端點查詢多個獨立的 RAG 實例（「孤島」），每個孤島保有自己的向量資料庫、知識圖譜與文件集合。最重要的設計決策是broker 是對每個來源都檢索，還是先做來源選擇；「在企業中，選擇性路由通常較優」94。

值得注意的框架與實作94：

  • FedRAG（Flower）：聯邦式 RAG 系統的微調。
  • VectorInstitute/fed-rag：支援集中式與聯邦式微調的開源框架。
  • FedMosaic（SIGIR'26）：第一個建立在參數化 adapter（PRAG 範式）上的 FedRAG 框架。

4.13 檢索評估指標#

評估分為兩大家族：線上（搜尋日誌，如 session abandonment、CTR、session success、zero-result rate）與離線（相關性判斷）95。

核心離線指標95：

  • Precision：檢索到的文件中相關者所佔比例：|{relevant} ∩ {retrieved}| / |{retrieved}|。
  • Recall：相關文件中被檢索到的比例：|{relevant} ∩ {retrieved}| / |{relevant}|。全部回傳即可讓它達到 100%，因此必須與 precision 並用。
  • Recall@k：相關段落是否出現在前 k 名。Anthropic 以 1 − recall@20 作為其失敗指標（前 20 名中未被檢索到的相關文件百分比）。這是最常見的 RAG 檢索指標9573。
  • Precision@k（P@k）：前 k 名中相關結果的數量。它不考慮位置；在相關結果少於 k 的查詢上，即使系統完美也會低於 1。
  • MAP（Mean Average Precision）：跨查詢對 Average Precision（AveP）取平均：MAP = Σ_q AveP(q) / Q。AveP 捕捉每個相關文件排名處的精確度，因此 MAP 獎勵把相關文件排前面。（R-precision 常與 MAP 高度相關。）
  • MRR（Mean Reciprocal Rank）：第一個正確答案排名倒數的平均：MRR = (1/|Q|) Σ 1/rank_i。例如排名為 3、2、1 時，(1/3 + 1/2 + 1)/3 = 11/18 ≈ 0.61。它只考慮第一個相關項目，適合只有一個答案的問答；若後續相關項目也重要，應改用 MAP。
  • nDCG（Normalized Discounted Cumulative Gain）：處理分級相關性的排序指標（Järvelin & Kekäläinen, SIGIR 2000; TOIS 2002）。DCG 對分級增益依位置做對數折扣：DCG_p = Σ (2^rel_i − 1) / log2(i+1)；nDCG_p = DCG_p / IDCG_p，其中 IDCG 為理想 DCG（相關文件依相關性排序）。nDCG 落在 [0,1] 且可跨查詢比較。它有兩個假設：高度相關文件在越前面越有用，且更相關優於略微相關。限制：它不懲罰結果中的壞文件，也不懲罰缺少的文件（因此要固定結果集大小，例如用 nDCG@5），且可能不適合有許多同等優良結果的查詢。

RAG 專屬評估（RAGAS）95：由於檢索器與生成器以不同方式失敗，應分別評估。RAGAS（不太依賴參考答案）的指標為：Context Precision 與 Context Recall 評檢索；Faithfulness 與 Answer Relevancy 評生成。其擴充指標典還包含 noise sensitivity、response groundedness、factual correctness。

生產實務95：把一組 30 到 100 題的黃金題庫接進 CI，在每次切塊／嵌入／提示變更時設下回歸門檻。另可每週監控 top-1 相似度以捕捉嵌入漂移。指標權重需適切配置：選擇嵌入模型時，「Recall@k 顯示相關段落是否被檢索到，而 MRR 與 nDCG 另外考量其位置」。

五、必須知道的領域模型與概念#

前一節談「怎麼查」，本節談「查的是什麼」。跨孤島檢索的成敗，多半取決於是否建立了正確的語意層（semantic layer）與中繼資料模型。以下分成五組。

5.1 語意層（Semantic Layer）#

語意層位於原始資料與消費者（BI 工具、應用、AI agent）之間，把商業邏輯（指標、維度、join、存取規則）定義一次，以便各處重用。它抽象化實體 schema，並為指標定義提供受治理的「單一真相來源」。

dbt Semantic Layer（由 MetricFlow 驅動）：MetricFlow「透過允許資料團隊在既有模型之上定義指標並自動處理資料 join，消除了重複編碼」。指標定義從 BI 層移到建模層，因此不同業務單位無論用什麼工具都使用相同定義96。MetricFlow 的模型包含96：

  • Semantic models：對應 dbt 模型的資料入口點，帶有中繼資料（資料表名稱、主鍵）。
  • Entities：join 鍵（語意模型之間的遍歷路徑／邊）。
  • Dimensions：指標分組／切分的依據。
  • Metrics：聚合函式，分為 simple、ratio、derived、cumulative、conversion。
  • Semantic graph：「語意模型與 YAML 設定之間的關係，創造出一片用於建構指標的資料地景……像一張地圖，資料表像地點，而它們之間的連結（邊）像道路。」它是 dbt DAG 的子集。

dbt Semantic Layer 支援 Snowflake、BigQuery、Databricks、Postgres、Redshift，並與 Apache Ossie 格式協作（dbt v1.12 以上）。它是 Open Semantic Interchange（OSI） 倡議的一部分（由 Snowflake 於 2025 年 9 月發起）。GitHub：dbt-labs/metricflow，約 1.8k stars、Apache-2.0（2026 年 10 月）；授權歷史為 AGPL（v0 到 0.140）、BSL（0.150 到 0.208）、Apache 2.0（0.209 以上）9697。

Cube：「開源的語意層。用程式碼定義指標、維度、join 與存取規則一次，然後透過 SQL、REST 與 GraphQL API 把它們暴露給下游任何東西，包含 BI 工具、自訂應用或 AI agent。」它是**無介面（headless）**的，內建關聯式快取引擎以達成次秒級延遲，支援所有 SQL 來源（Snowflake、Databricks、BigQuery、Presto、Athena、Postgres）。Cube Core（開源：後端 Apache 2.0、客戶端 MIT）與商業版 Cube（agentic analytics 平台，含儀表板、RBAC、多租戶）有別。GitHub：cube-js/cube，約 21.0k stars、2.2k forks、11,538 commits（2026 年 10 月），topics 包含 semantic-layer、headless-bi、embedded-analytics98。

AtScale：自稱「為 AI 與 BI 而生的語意層：企業可信分析」，能「以受治理的商業邏輯、一致的指標與成本可控的效能，驅動 AI agent、BI 工具與分析應用」。客戶包含 Netflix、Visa、The Home Depot、Toyota、Vodafone 與 Cigna。AtScale 為專有／商業軟體（無公開 GitHub 儲存庫）；其部落格強調語意層是生成式 BI、text-to-SQL 準確度與多雲指標問題的關鍵缺環99。

在「多孤島檢索」脈絡下，語意層的作用是統一語彙：當 A 系統的「客戶」與 B 系統的「帳戶」其實是同一概念時，語意層提供對映規則，讓檢索端不必為每個來源客製查詢。

5.2 中繼資料模型與血緣（Metadata Model & Lineage）#

DataHub Metadata Model 採取 schema 優先的取向，以開源 Pegasus schema language（PDL） 加上自訂註解來建模。其概念抽象為100：

  • Entities：中繼資料圖中的主要節點（例如 Dataset 或 CorpUser），由型別、唯一識別碼（urn）與成組的 attributes 構成。
  • Aspects：描述實體某一面向的屬性集合，是寫入的最小原子單位（例如 DatasetProperties、Ownership、GlobalTags、GlossaryTerms、InstitutionalMemory）。
  • Relationships：兩個實體之間的具名邊，透過帶 @Relationship 的外鍵屬性宣告，可雙向遍歷。
  • Identifiers（Keys & Urns）：key aspects 唯一識別實體，序列化為 Urns 以供主鍵查詢（例如 urn:li:corpuser:johnsmith）。

核心實體包含 Data Platform、Dataset（表／檢視／串流／檔案）、Chart、Dashboard、Data Job（Task）、Data Flow（Pipeline／DAG）。模型存於 Entity Registry（entity-registry.yml，自 2022 年 1 月起取代 Snapshot 模型）。中繼資料有三種查詢方式：主鍵查詢、搜尋查詢與關聯遍歷。Aspect 分兩類：Versioned（存於關聯式儲存，如 ownership、tags、描述）與 Timeseries（存於 Elasticsearch／Kafka，如 profile、使用統計）100。

GitHub：datahub-project/datahub，約 12.8k stars、3.7k forks、16,485 commits、Apache 2.0（2026 年 10 月）。2019 年始於 LinkedIn，管理超過 1,000 萬個資產，有 150 種以上整合。它現在自我定位為「Context Platform」，透過 MCP、GraphQL、REST 與 SDK 暴露情境101。

OpenLineage：一套開放的中繼資料與血緣蒐集標準，設計用來在作業執行時加以 instrument。它「定義 run、job 與 dataset 實體的一般化模型，並以一致的命名策略識別」，可透過 facets（附加於核心實體上的原子中繼資料片段）擴充。規格以 OpenAPI 定義並允許自訂 facets。它是 LF AI & Data Foundation 的 Graduate 專案。整合對象包含 Apache Airflow、Flink、Hive、Spark、dbt、Feast、Great Expectations、SQL、Trino。Marquez 是參考實作（蒐集、彙總、視覺化中繼資料）102。GitHub：OpenLineage/OpenLineage，約 2.7k stars、542 forks、Apache 2.0；MarquezProject/marquez，約 2.3k stars、Apache 2.0（2026 年 10 月）103104。

Apache Atlas：「一組可擴充的核心基礎治理服務，讓企業能有效且有效率地在 Hadoop 內滿足法遵要求，並與整個企業資料生態系整合。」它透過規範性與鑑識性模型提供可視性、技術與營運稽核，以及由業務分類中繼資料充實的血緣。它使用共同中繼資料儲存以促成互通，並透過 Apache Ranger 維護中繼資料的真實性；安全模型為 RBAC 與 ABAC。GitHub：apache/atlas，約 2.2k stars、907 forks、Apache 2.0（2026 年 10 月），支援 Java 8／11／17105。

Amundsen：一套資料探索與中繼資料引擎，被形容為「資料的 Google 搜尋」。它索引資料資源（資料表、儀表板、串流），並提供基於使用模式的 page-rank 式搜尋（被查詢越多的資料表越前面）。以探險家 Roald Amundsen 命名，2019 年 4 月始於 Lyft，由 LF AI & Data Foundation 託管。架構分為 frontend（Flask＋React）、search（Elasticsearch）、metadata（Neo4j 或 Apache Atlas）、databuilder（匯入）與 common；支援的實體為 Tables、Dashboards、ML Features、People。GitHub：amundsen-io/amundsen，約 4.8k stars、Apache 2.0，但已於 2026-09-29 封存（「因不活躍……內容將保留供歷史用途」）106。

5.3 資料網格與資料產品（Data Mesh & Data Products）#

Data Mesh 是一種社會技術取向的分散式資料架構，由 Zhamak Dehghani 於 2019 年（當時於 Thoughtworks）提出，借鏡領域驅動設計與團隊拓樸。四項原則107108：

  1. 領域擁有權（Domain ownership）：領域團隊擁有其分析資料。
  2. 資料即產品（Data as a product）：「領域資料應被視為如同任何其他公開 API。」
  3. 自助式資料基礎設施平台：平台團隊提供領域無關的工具。
  4. 聯邦式治理（Federated governance）：一個 guild 定義全球的互通性、安全與文件政策。

資料產品是「一個邏輯單位，包含所有處理與儲存領域資料以供分析用途的元件，並透過**輸出埠（output ports）**讓其他團隊取用」，例如一個 BigQuery dataset、S3 中的 Parquet 檔或 Kafka topic。資料契約（data contract）定義結構、格式、語意、品質與使用條款；Data Contract Specification（datacontract.com）定義了一種 YAML 格式。資料產品應該是可被發現、可被定址、可被信任、自我描述、可互通、安全且受治理的。實作者包含 Zalando、Netflix、Intuit、PayPal 與 VistaPrint。在資料網格中做探索「需要一個所有分散式資料產品的中央入口」，通常以 wiki、git 儲存庫或雲端資料目錄實作（Select Star、Google Data Catalog、AWS Glue Data Catalog）107。

這對檢索系統的意涵是：在資料網格環境中，目錄（catalog）本身就是檢索入口，而「資料產品」是檢索的回傳單位，而非單一資料表。

5.4 標準詞彙：DCAT、schema.org、RDF／SPARQL#

（1）DCAT（Data Catalog Vocabulary）

DCAT 是一套 RDF 詞彙，用於促進網際網路上中繼資料目錄的互通：「使用 DCAT 描述目錄中的資料集，發布者可提升可發現性，並讓應用能消費來自多個目錄的中繼資料。它促成目錄的分散式發布，並促進跨目錄的聯邦式資料集搜尋」109。

DCAT 最初於 DERI 開發，後由 W3C 的 eGov Interest Group 繼續開發。DCAT v2 為 W3C Recommendation，日期 2020-02-04（新增資料服務／API、更強的資料集關聯、與 schema.org 對齊）；DCAT v3 為 W3C Recommendation，日期 2024-08-22（現行版本）。它是歐盟開放資料集描述的基礎，其應用 profile 包含 DCAT-AP、StatDCAT-AP 與 GeoDCAT-AP109。

（2）schema.org

schema.org 的 Dataset 是「描述某個感興趣主題之結構化資訊的集合」，位於 Thing > CreativeWork > Dataset 的階層中。它宣告等價類別：dcat:Dataset、dctype:Dataset、void:Dataset，是與 DCAT 的明確橋接。關鍵屬性為 distribution（DataDownload）、includedInDataCatalog（DataCatalog）、variableMeasured、measurementTechnique、issn。依 Google 的網頁索引，使用於 1 萬至 10 萬個網域（2026 年 8 月）110。

（3）RDF 與 SPARQL

RDF（Resource Description Framework）：「一種描述與交換圖形資料的方法」，最初由 W3C 設計為中繼資料資料模型。它是一個由 主詞—述詞—受詞（subject–predicate–object） 三元組構成的有向圖（例如「天空—有顏色—藍色」）。每個部分可以是 IRI；受詞也可以是字面值（literal）。時間軸：1999 年採為 W3C 建議標準、RDF 1.0（2004）、RDF 1.1（2014）。序列化格式包含 Turtle、RDF/XML、JSON-LD、N-Triples、TriG、Notation3。建構於 RDF 之上的本體語言有 RDFS、OWL、SHACL111。

SPARQL（SPARQL Protocol and RDF Query Language，唸作「sparkle」）是 W3C 標準的 RDF 查詢語言，也是語意網的關鍵技術。SPARQL 1.0 於 2008-01-15 成為 W3C Recommendation；SPARQL 1.1 於 2013 年 3 月。查詢形式有 SELECT、CONSTRUCT、ASK、DESCRIBE。它支援圖形遍歷（+ 表遞移路徑）、管線式求值，以及跨多個端點的聯邦式查詢。參考實作有 Apache Jena、Eclipse RDF4J、OpenLink Virtuoso112。

（4）知識圖譜（Knowledge Graph）

知識圖譜是「一種使用圖形結構資料模型或拓樸來表示與操作資料的知識庫」，儲存實體的互連描述。該詞由 Edgar W. Schneider 於 1972 年提出（引用 1968 年一份 HumRRO 簡報）。Google 以 2012 年的 Knowledge Graph 使其普及，建構於 DBpedia／Freebase 之上並使用 schema.org 術語。近期發展包含 Microsoft 的 GraphRAG（2024），把 LLM 生成的圖整合進檢索增強生成。圖資料庫有 Neo4j、GraphDB、AgensGraph。**虛擬知識圖譜（Virtual Knowledge Graph）**不把資料存於專用資料庫，而是映射到關聯式或湖儲存113。

5.5 資料孤島、語意互操作性與本體式整合#

（1）資料孤島（Information silo）

一種封閉的管理系統，其中某個資訊系統或子系統無法與其他相關系統做互惠運作，資訊「未被充分共享，而是被隔離在各系統內」。每當某個資料系統與其他系統不相容或未整合時就會產生孤島，可能發生在技術、應用或資料架構層，而「多數資料系統至少在資料架構層是不相容的」。functional silo syndrome 一詞由 Phil S. Ensor 於 1988 年提出。孤島是 OBDI、OBDA 與 MDM 共同試圖解決的根本問題114。

（2）語意互操作性（Semantic interoperability）

「電腦系統能交換具無歧義、共享意義之資料的能力」，是機器可運算邏輯、推論、知識發現與資訊系統間資料聯邦的前提。它關注的「不只是資料的封裝（語法），還包括意義與資料的同時傳遞（語意）」，作法是加入中繼資料，把每個資料元素連結到受控的共享詞彙及其關聯的本體。缺少它，資料就會「巴別塔化」。一份實務影響估計（引用於維基百科）指出，美國因缺乏語意互操作性在醫療、營建與汽車製造業的年損失超過 1,000 億美元115。

（3）本體式資料整合（Ontology-Based Data Integration, OBDI）

使用一個或多個本體來結合多個異質來源的資料；被歸類為 Global-As-View（GAV） 的資料整合取向。它處理四種異質性：語法、schema／結構、語意與系統異質性；本體（具明確定義概念與具名關聯的形式模型）處理的是語意異質性。本體扮演三種角色：內容闡明、查詢模型（全域查詢 schema）與映射驗證。三種架構為：單一本體（如 SIMS、Cyc SKSI、Gellish）、多重本體（每個來源一個，加上彼此映射，如 OBSERVER）、混合式（多個本體共享一個共同的上層詞彙）116。

（4）本體式資料存取（Ontology-Based Data Access, OBDA）

這是「無 ETL」整合背後的查詢期技術。資料留在來源，被暴露為虛擬知識圖譜（Virtual Knowledge Graph, VKG）。使用者對本體撰寫 SPARQL 查詢；系統用本體改寫／重述（rewrite/reformulate）查詢，再透過映射展開（unfold）成直接對關聯式來源執行的 SQL。Ontop 精確定義為：「一種對非 RDF 資料的虛擬表示……資料以其原始格式留在資料來源中，但可被虛擬表示為 RDF 圖」。這是資料虛擬化（Denodo 式）的語意對應物，後者「與傳統 ETL 流程不同……資料留在原處，並對來源系統提供即時存取」117118。

（5）標準資料模型（Canonical Data Model）

一種在不同資料格式之間通訊的設計模式：「建立一個是所有其他模型超集（『標準』）的資料模型，並建立一個『翻譯器』模組或層，讓所有既有模組與之雙向交換資料。」它充當中間人，讓每個系統只需認識標準模型，而非其他所有系統，從而減少資料翻譯的數量與維護成本。在 EAI／SOA 中常表達為標準 XML schema119。共享本體（OWL／SKOS）是標準模型的語意類比物，但它是宣告式的、查詢期的，而非訊息載荷。

（6）實體解析與記錄連結（Entity Resolution / Record Linkage）

亦稱資料比對、實體解析、去重、模糊比對，是「在不同資料來源之間找出指向同一實體的記錄」的任務，前提是它們缺少共同識別碼。理論基礎：Halbert L. Dunn（1946）、Newcombe（1959），以及 Fellegi–Sunter 模型（1969），至今仍是數學基礎，使用概似比、m 機率／u 機率，以及上下決策門檻，中間區間交由人工複核。方法包含確定性（規則式）、機率性（模糊）、分塊（blocking）（只比對在分塊鍵上一致的配對）與語音演算法（Soundex、NYSIIS、Metaphone）。實體解析特別指「一種營運情報流程……組織藉此跨多個資料孤島連結不同資料來源」，套用概似與機率評分找出匹配與非顯而易見的關係120。

（7）身分解析（Identity resolution）

是同一核心任務的眾多名稱之一（維基百科的 Record linkage 條目會把「Identity resolution」重新導向至此）。實務上指引擎／中介軟體的觀點：它「套用概似與機率評分來判定哪些身分匹配」。進階的身分解析引擎加上規則引擎與工作流程，對解析出的身分及其關係做自動化決策，用於詐欺偵測、監視名單篩選、客戶資料整合（CDI）與 MDM。記錄連結標準上把「實體」等同於人類個體，而 Linked Data 則透過 URI 一般化到任何網路資源120。

（8）主資料管理（Master Data Management, MDM）

MDM 是「一種業務與 IT 協作的學科，以確保企業官方共享主資料資產的一致性、準確性、可管理性、語意一致性與可歸責性」。目標包含資料一致性與準確性、單一版本真相（SVOT）、營運效率與法規遵循。它依賴記錄連結來關聯指向同一實體的記錄（例如銀行的行銷與客服資料庫）。實作模型有來源記錄（source of record）、註冊庫（registry）、整合（consolidation）、共存（coexistence）與交易／集中式。交付風格有資料整合、資料聯邦（單一虛擬視圖）與資料傳播。關鍵在於，維基百科指出 MDM 問題常「需要資料轉換……與其他以 ETL 為基礎的資料移動一樣，這些流程昂貴且低效率」，這正是前述語意／虛擬化取向被定位為 ETL 式 MDM 替代方案的原因121。

6.2 關鍵設計決策#

  1. 要不要建索引副本？ 若資料敏感、變動快、量小 → 偏好聯邦。若需要全域排序、量極大、延遲要求嚴 → 偏好索引。多數組織兩者並用281。
  2. 權限採 early 還是 late binding？ 兩者並用最穩：ACL 傳播供快速過濾，查詢期再以使用者身分收斂3937。
  3. 排序融合用什麼？ 異質分數不可比時用 RRF（rank_constant 預設 60），必要時對不同來源設權重或納入規則4830。
  4. 檢索單位是什麼？ 資料表、文件、區塊（chunk）、資料產品或實體（entity）。這是一個資訊架構決策，決定目錄與語意層的建模方式100107。
  5. 要不要做圖？ 只在「跨孤島串接線索」是被實測到的失敗模式時才做，因為圖的建置與維護成本高；可先評估 LazyGraphRAG 以降低前置成本8993。
  6. 要不要生成？ 若使用者要的是「找到檔案」而非「得到答案」，就不要引入生成層，避免將檢索失敗偽裝成流暢的錯誤答案82。

七、常見誤解與反模式#

  • 誤解一：「不用 ETL 就不用工程」。 索引式搜尋仍需連接器、schema 註冊、ACL 抽取與增量同步，這些是 ETL 的檢索取向變體3234。
  • 誤解二：「換更強的生成模型就能改善檢索」。 生成模型不能修好爛檢索，反而會讓錯誤答案更流暢、更有說服力82。
  • 誤解三：「向量搜尋可以取代關鍵字搜尋」。 對精確 token（錯誤碼、產品編號、函式名稱）BM25 仍無可取代，混合＋RRF 是更穩的作法73。
  • 誤解四：「權限可以事後再處理」。 權限模型會反向決定索引結構（例如是否需要把群組成員展開、text 或 keyword 欄位選擇），事後補做往往需要重建索引3740。
  • 誤解五：「MTEB 排名高就是好模型」。 不同聚合與版本不可直接比較，且必須在自己的查詢上驗證；換模型還需全語料重新嵌入84。
  • 反模式：一次性的中繼資料填寫。 目錄若依賴人工撰寫描述，通常會迅速腐化；DataHub 的 Context Intelligence 改以「挖掘多年的查詢歷史，建立組織實際如何使用資料的語意索引，不需人工撰寫」來對抗此問題101。

九、結論#

針對「ETL 領域的多模態檢索範式為何」這個問題，可以濃縮成以下幾點：

  1. 這裡的 ETL 是被繞過的對象，不是主角。 因為目標是「方便使用者檢索」而非「建模或探勘」，所以主流作法是聯邦式查詢／資料虛擬化（不搬資料）與索引式企業搜尋（搬副本或中繼資料）。ETL 只在需要效能加速時以物化（materialization）形式局部回歸，且與虛擬化並存1。

  2. 三個範式可以疊加。 聯邦式負責結構化來源的即時精確查詢；索引式負責非結構化內容的全域排序；向量式與 RAG 負責語意與跨模態檢索。三者共同由語意層與中繼資料層（語意層、資料目錄、血緣）黏合2810096。

  3. 必須知道的領域模型與概念，最核心的是這八個：語意層（semantic layer）、中繼資料模型與血緣（metadata model and lineage）、資料目錄與詞彙標準（data catalog、DCAT、schema.org）、語意互操作性與本體式整合（OBDI／OBDA、虛擬知識圖譜）、標準資料模型（canonical model）、實體／身分解析（entity and identity resolution）、主資料管理（MDM）、以及排序融合與檢索評估（RRF、recall@k、nDCG、MRR、MAP）961001091161171191201214895。

  4. 真正的難點不在模型，而在四個工程問題：語意對齊（不同孤島對同一概念的命名不同）、權限傳遞（early 與 late binding 的組合）、新鮮度（增量同步與刪除處理）、排序融合（異質分數不可比時用 RRF）116394648。
