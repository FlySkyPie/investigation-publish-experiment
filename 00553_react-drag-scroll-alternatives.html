00553_react-drag-scroll-alternatives

react-indiana-drag-scroll 的替代方案調查#

摘要#

react-indiana-drag-scroll 是一個 React 生態系的「按住滑鼠拖曳即捲動」函式庫，由俄羅斯開發者 Norserium 維護。它讓任何可捲動容器（橫向、縱向或雙向）具備如同 Google Maps 般的「抓取拖曳」體驗，並且預設隱藏原生捲軸1。其 GitHub 專案約有 529 顆星，npm 每週下載量約 100,580 次（統計區間 2026-10-06 至 2026-10-12），最新穩定版為 2.2.1，於 2025-03-01 發布23。

本報告調查其替代方案，並依「專職拖曳捲動函式庫」、「通用拖曳／手勢工具」與「輪播滑動函式庫」三類整理。核心結論：若只需要最單純的拖曳捲動，react-use-draggable-scroll 是下載量最接近、體積最小且最成熟的替代品；若同時需要輪播、吸附與慣性動畫，embla-carousel-react 與 swiper 是維護最活躍、下載量最高的選項456。

一、調查對象：react-indiana-drag-scroll 是什麼#

react-indiana-drag-scroll 的官方描述為「React component which implements scrolling via holding the mouse button or touch」（實作透過按住滑鼠或觸控來捲動的 React 元件）1。它的主要特徵如下：

功能上，它提供 ScrollContainer 元件與 useDraggableScroll hook 兩種用法，支援橫向與縱向拖曳、以 activationDistance（預設 10px）區分「點擊」與「拖曳起點」、以 ignoreElements 選擇器排除特定子元素（例如彈窗）不觸發拖曳、以 nativeMobileScroll（預設 true）在行動裝置沿用原生觸控捲動，並預設以 hideScrollbars 隱藏原生捲軸1。

需要留意的維護訊號：本專案自 2025-03-01 之後沒有新的程式碼推送，且 npm registry 顯示只有一位維護者12。這代表它並非「已废弃」，但更新節奏偏慢。

二、替代方案總覽#

下表把候選方案分為三類。下載量與星數皆為 2026-10 的查詢結果，日期為統計截止日。

2.1 專職「拖曳捲動」函式庫（與原專案最同性質）#

補充：npm 上另有 @skax/drag-scroll（2026-02-26 發布，每週約 112 次下載）22、drag-scroll-carousel（2026-04-10 發布，每週約 6 次下載）23，以及 drag-scroll-provider（2018 年後未更新）24。這三個方案下載量與星數都極低，除非有特殊需求，否則不建議採用。

2.2 通用拖曳／手勢工具（可自行組出拖曳捲動）#

2.3 輪播／滑動函式庫（同時提供拖曳與吸附）#

三、各方案深入比較#

3.1 react-use-draggable-scroll#

這是與原專案最直接對應的替代品。它以單一 hook useDraggable 實作，回傳可直接展開到目標元素的事件處理器，並在拖曳結束後加入慣性（動量）效果8。可調參數包含：

  • decayRate（預設 0.95）：慣性衰減率，數值越接近 1 滑得越遠47
  • applyRubberBandEffect（預設 false）：捲動到邊界時讓子元素產生橡皮筋回彈效果47
  • activeMouseButton：指定以左／中／右鍵觸發47
  • safeDisplacement、isMounted 等其他選項47

它內部使用自訂的 useIsomorphicLayoutEffect，在伺服器端渲染（SSR）時退回 useEffect，因此與 Next.js 等 SSR 框架相容47。體積限制設定在 10 kB 以內4。

風險：最後一次程式碼提交為 2022-09-28，官方沒有任何 GitHub Release8。雖然下載量仍高（每週約 92,809 次9），但屬於「成熟但無人維護」的狀態。若專案需要支援未來新版 React，需自行驗證相容性（其 peer dependency 標示 react >= 164）。

3.2 react-scroll-ondrag#

此方案以 hook useScrollOnDrag(ref, options?) 呈現，回傳 { events } 供展開10。最特別的是 runScroll 回呼，開發者可完全自訂捲動邏輯，例如只允許橫向捲動：

const { events } = useScrollOnDrag(ref, {
  runScroll: ({ dx, dy }) => {
    ref.current.scrollLeft += dx;
  },
});

它另提供 onDragStart 與 onDragEnd 生命週期回呼，且不需要匯入任何 CSS10。mousemove／mouseup 事件綁定在 globalThis 上，因此游標離開元素後拖曳仍可持續10。

取捨：它是本調查中維護最活躍的專職拖曳捲動方案（2026-07-14 發布 5.0.0，2026-09 仍有依賴更新提交）1012，但採用者極少（GitHub 僅 7 顆星、每週 3,556 次下載）1011，生態驗證不足。此外它標示為 ESM only、Node engine >=20.0.012，對舊工具鏈不友善。

3.3 @use-gesture/react 與 react-draggable#

若不想依賴小眾套件，可選用成熟的手勢／拖曳底層來自行實作。@use-gesture/react 提供 useDrag 等 hook，能取得拖曳過程的位移量，再手動寫入 scrollLeft／scrollTop25。其下載量（每週約 735 萬次）與生態成熟度遠勝任何專職方案26。

react-draggable 的 DraggableCore 子元件提供不含定位邏輯的原始拖曳事件，可用來組出拖曳捲動28。它維護活躍（2026-09-16 發布 4.7.2）30，但要注意它是為「拖曳元素本身」設計，用來捲動容器需要自行撰寫位移對應邏輯。

取捨：自由度最高、長期維護最穩，但開發成本也最高，且需要自行處理慣性、點擊與拖曳的區分、行動裝置觸控等細節。

3.4 embla-carousel-react#

Embla 是本次調查中下載量最高的候選（embla-carousel-react 每週約 2,856 萬次36），且核心完全無相依35。它最關鍵的選項是 dragFree：

  • dragFree: false（預設）：拖曳後吸附到最近的投影片37
  • dragFree: true：自由慣性捲動，停在使用者放手的任意位置，不吸附37
  • dragFree: 'snap'：保留自由流暢手感，但最終仍吸附到最接近的吸附點37

另有 dragThreshold（預設 10，僅影響點擊是否觸發，不影響拖曳起始）37、containScroll（預設 'trimSnaps'，處理頭尾空白）37。因此當需求其實是「拖曳捲動清單」時，以 Embla 設定 dragFree: true 即可逼近原專案的體驗，同時獲得活躍維護（最近推送 2026-10-12）35。

取捨：它本質是輪播，需要包一層投影片結構；若只是要一個可拖曳的 div，使用它屬於「殺雞用牛刀」。

3.5 swiper#

Swiper 是星數最高的選項（41,899 顆星）38，維護非常活躍（最新 14.3.0 於 2026-09-28 發布）6。模擬拖曳捲動的關鍵設定為：

  • freeMode：關閉吸附，可設為 true 或傳入物件微調 momentum、momentumBounce、momentumRatio 等40
  • grabCursor：滑鼠移入時顯示「抓手」游標，強化可拖曳的視覺提示40
  • mousewheel：讓滑鼠滾輪也能操作，並可用 releaseOnEdges 在邊界時交還頁面捲動40

取捨：功能最全面，但體積與 API 複雜度也最高；對「單純拖曳捲動」而言明顯過重。

3.6 Splide 與 keen-slider#

@splidejs/react-splide 主打無障礙與零 Lighthouse 錯誤41，每週下載約 13.8 萬次42。但核心 Splide 自 2024-07-08 後未再推送程式碼41，React 包裝版本停留在 0.7.1243。

keen-slider 強調「最接近原生的觸控手感」，每週下載約 22 萬次45，但同樣面臨更新放緩的情形（核心最後推送 2026-01-22，且累積 149 個未結議題）44。

五、批判性來源反思#

本報告的數據來自三類來源，各有其偏誤與限制，閱讀時應留意：

  1. npm 官方 API 與 registry（下載量、版本、相依、授權）：這是最可信的一手資料，下載量取自 2026-10-06 至 2026-10-12 的單週區間3。限制在於「下載量」會被 CI 快取、鏡像與相依樹重複計數放大，並不精確等於「實際使用人數」；且單週快照可能受當週事件（如某大專案發版）影響而波動。此外，本報告查詢 npm 網站頁面時數次遭遇 HTTP 403，因此改以 registry.npmjs.org 與 api.npmjs.org 的程式化端點取得資料，這反而避開了網頁版的可能延遲。

  2. GitHub REST API（星數、推送時間、授權、未結議題）：屬於平台官方資料，可視為一手。但星數只是「受關注度」而非品質保證，且會被議題討論與歷史累積影響；pushed_at 也無法區分「實質功能更新」與「依賴機器人更新」，本報告因此在 react-scroll-ondrag 的維護活躍度判斷上，特別查閱了提交紀錄，確認 2026-09 的推送為 dependabot 依賴更新而非核心功能變更10，並在正文中據實標註。

  3. 官方文件與第三方聚合網站（功能說明、體積）：套件功能說明來自官方 README、官方文件與釋出頁，可信度高。體積數據（7.66 kB／2.63 kB）來自第三方聚合服務，可能因打包設定不同而與實測有落差，僅宜作相對比較。選項語意（dragFree、freeMode、grabCursor）則交叉核對了官方文件與原始碼，兩者一致。

未能驗證的事項：本報告未實際安裝並執行任何套件，因此「拖曳手感」、「在特定 React 版本下的相容性」與「行動裝置實機行為」皆未經實測，讀者若要做最終決策，建議以最小範例在各候選方案上實際操作一次。此外，react-indiana-drag-scroll 的 3.x alpha 系列仍在變動中，本報告未深入評估其穩定性。

六、結論#

react-indiana-drag-scroll 本身仍是一款體積小、API 直覺的專職拖曳捲動元件，並非不能用，只是更新節奏放緩。替代方案中：

  • 最平價的替代：react-use-draggable-scroll（同為 hook 式、下載量與體積相近，但自 2022 年停更）。
  • 最活躍的專職替代：react-scroll-ondrag（維護中，但社群極小）。
  • 最穩健的長期選擇：以 @use-gesture/react 或 react-draggable 自行實作。
  • 若需求其實是輪播：embla-carousel-react（dragFree: true）與 swiper（freeMode + grabCursor）是維護最活躍、下載量最高的選項。
