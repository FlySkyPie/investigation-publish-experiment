如何安裝輕量級的 Debian 系作業系統作為 Server Host#

摘要#

本報告回答一個具體的實務問題：如何取得並安裝一套「輕量級、屬於 Debian 家族」的作業系統，並把它當作伺服器主機（server host）使用。

「輕量級」在此有兩層意思：

  1. 安裝映像本身輕量：下載檔小、安裝流程短、不需要圖形介面。
  2. 執行期足跡輕量：開機後常駐行程少、記憶體佔用低、磁碟佔用小、可攻擊面（attack surface）小。

本報告先說明 Debian 家族的版本現況，再逐一介紹七條可行路徑（官方最小安裝、mini.iso、雲端映像、debootstrap/mmdebstrap、preseed 自動化、DietPi、Devuan），並補充 Ubuntu Server 與 Proxmox VE 作為「以 Debian 為底的主機平台」選項。最後給出安裝後的必要加固步驟與決策樹。

1. 背景：Debian 家族的版本現況#

在選擇任何方案之前，必須先確認「你要裝的是哪一個 Debian 版本」。撰寫本報告時（2026-10-11）的狀態如下：

Debian 每個版本的生命週期為五年：前三年完整支援，後兩年為長期支援（LTS）12。

關鍵提醒：網路上大量教學仍以「Debian 12 Bookworm = stable」為前提撰寫。2026 年的正確答案是 Debian 13 Trixie = stable，Bookworm 已是 oldstable 且已於 2026-07-11 結束完整支援1。挑選教學文件時務必確認其對應版本。

3.3 寫入 USB 隨身碟#

i386、amd64、arm64 的 Debian 映像皆採用 isohybrid 技術，可直接寫入 USB 隨身碟並由 BIOS/UEFI 開機。Linux 上可使用6：

cp <file> <device>

或

sudo dd if=<file> of=<device> bs=16M status=progress oflag=sync

其中 <device> 是 USB 裝置（例如 /dev/sda）。官方明確警告必須確認裝置名稱正確，因為此指令同樣能輕易覆寫硬碟。此外，Debian 建議不要使用 unetbootin，它可能導致難以診斷的開機與安裝問題6。Windows 使用者官方推薦 balenaEtcher 或 USBImager6。

3.4 安裝流程（最小化的關鍵步驟）#

安裝程式各階段的細節見官方安裝手冊第六章7。與「輕量化」最相關的是軟體選擇階段：

到 Selecting and Installing Software 畫面時會列出 task 清單。在標準介面中，使用空白鍵切換選取7：

  • 取消勾選「Desktop environment」：它預設是被勾選的，且預設安裝 GNOME78。
  • 勾選「SSH server」：約 21 MB 安裝大小（下載約 3 MB），安裝 openssh，讓機器可遠端連線78。
  • 關於「Standard system utilities」：它會安裝所有 priority 為 standard 的套件。官方原文警告：「除非你知道自己在做什麼、且真的想要一個極精簡的系統，否則你應該保持這個 task 被選取。」7

換言之：

  • 想要保守、安全的最小系統 → 保留 standard，只取消 desktop、加上 SSH server。
  • 想要極致足跡最小 → 連 standard 一起取消。代價是許多慣用工具都不存在，需自行安裝。

其他實用選項7：

  • 不設定 root 密碼：此時 root 帳號會被停用，安裝程式改為安裝 sudo 套件，並讓第一個建立的普通使用者可使用 sudo 執行管理任務。這是比「設 root 密碼並直接用 root」更好的預設。
  • lowmem 模式：低記憶體時安裝程式會自動停用翻譯、僅載入必要元件，並建議建立 1–2 GB 的 swap 分割區7。
  • network-console：可從安裝選單載入此元件，改用 SSH 遠端完成大部分安裝流程（需先在本機完成網路設定）7。

6. 方案 D：debootstrap 與 mmdebstrap（從既有 Linux 建立）#

6.1 debootstrap#

官方安裝手冊明確指出，debootstrap 是「Debian 安裝程式所使用的工具，也是公認安裝 Debian base system 的官方方法」。它只需要 wget、ar、/bin/sh 與基本 Unix 工具10。

基本用法（Trixie，現行版本 1.0.141）1014：

/usr/sbin/debootstrap --arch ARCH trixie \
     /mnt/debinst http://ftp.us.debian.org/debian

SUITE 參數可以是發行代號（sid、trixie 等）或符號名稱（unstable、testing、stable、oldstable）14。MIRROR 可以是 http://、https://、file:/// 或 ssh:// URL；注意 file:/ 會被轉換為正規的 file:///，而 file:// 不會運作14。

variant 選項（這是控制「有多小」的主要旋鈕）14：

debootstrap 不負責安裝開機引導程式。完成後需 chroot 進去、設定 /etc/fstab、網路（/etc/network/interfaces、/etc/resolv.conf、/etc/hostname、/etc/hosts）、apt sources、locale、核心與 GRUB，並安裝 ssh10。官方也提醒：由於此流程高度手動，「你無法期待產出的系統與正常安裝的系統完全相同」，且此程序只涵蓋基本步驟，額外的安裝／設定步驟可能仍需要10。

官方提供的完善化指令10：

# tasksel install standard
# apt clean

前者安裝所有 standard priority 的套件，後者清掉 /var/cache/apt/archives/ 中已下載的套件以釋放空間。

6.2 mmdebstrap（較新的替代品）#

mmdebstrap 是 debootstrap 的替代工具，其標語為「multi-mirror Debian chroot creation」。核心差異在於它內部使用 apt 解析相依性，因此取得 debootstrap 沒有的能力15。

相對於 debootstrap 的優勢15：

  • 支援多個 mirror（apt 式相依解析）
  • 對 Debian stable chroot 預設納入 security 與 updates mirror（這是 debootstrap 自 2009 年以來的 wontfix）
  • 快約兩倍（範例：apt variant chroot 約 11 秒）
  • 在設定 $SOURCE_DATE_EPOCH 時可產出逐位元可重現的輸出
  • 可透過 Linux user namespace 或 fakechroot 以非特權身分執行
  • 支援用 qemu-user 建立外國架構 chroot

限制15：

  • 只能在已安裝 apt 的系統上執行（Debian 及其衍生版），因此永遠無法完全取代 debootstrap
  • 沒有 SCRIPT 參數（改用 hooks）
  • 不存在這些選項：--second-stage、--exclude、--resolve-deps、--force-check-gpg、--merged-usr、--no-merged-usr、--cache-dir

variant 一覽（所有 variant 都含直接與間接硬相依，但不含 recommends）15：

現行版本為 1.6.0（2026-10-03 發行）；Debian stable（Trixie）套件版本為 1.5.7-1+deb13u115。

實用範例（含「去蕪存菁」縮小足跡的作法）15：

# 僅 Essential:yes + apt 的極精簡 chroot
mmdebstrap --variant=apt unstable chroot.tar

# stable chroot（自動加入 security 與 updates mirror）
mmdebstrap stable stable-chroot.tar

# 移除 man page、locale、doc 以縮小 chroot
mmdebstrap --variant=essential \
    --dpkgopt='path-exclude=/usr/share/man/*' \
    --dpkgopt='path-include=/usr/share/man/man[1-9]/*' \
    --dpkgopt='path-exclude=/usr/share/locale/*' \
    --dpkgopt='path-include=/usr/share/locale/locale.alias' \
    --dpkgopt='path-exclude=/usr/share/doc/*' \
    --dpkgopt='path-include=/usr/share/doc/*/copyright' \
    --dpkgopt='path-include=/usr/share/doc/*/changelog.Debian.*' \
    unstable debian-unstable.tar

8. 方案 F：DietPi（極輕量的 Debian 衍生版）#

8.1 定位#

DietPi 官方定義為「高度最佳化且極簡的 Debian 系 Linux 發行版，核心極度輕量，同時安裝與使用極度簡單」18。它主要針對單板電腦（Raspberry Pi、Odroid、Orange Pi、PINE64、Radxa 等），也可跑在 x86_64 PC、虛擬機與容器上；並提供選單驅動的 dietpi-software 工具，可安裝並預先最佳化常見軟體（Nextcloud、Pi-hole、Plex、LAMP/LEMP、VPN、桌面等），裝好即可用18。

8.2 Debian 基底與版本#

DietPi 是建構在 Debian 之上18：

  • 預設／穩定：Debian 13（Trixie）——官方推薦
  • oldstable：Debian 12（Bookworm）
  • testing：Debian 14（Forky）

Ubuntu 明確不支援。此外，DietPi 提供 dietpi-installer 腳本，可把任何既有的「臃腫」Debian／Raspbian 安裝轉換成輕量 DietPi 系統18。

8.3 輕量程度（官方實測數據）#

DietPi 官方比較頁以 2026 年的 Trixie 映像實測19：

以 Raspberry Pi Zero W 為例，DietPi 使用 42 MiB RAM（對比 Raspberry Pi OS Lite 的 96 MiB，低 44%）、702 MiB 磁碟（對比 2378 MiB，約 30%）；下載大小約 178 MiB 對 497 MiB19。

官方另提供一個與 Debian netinst 的對照（Bookworm、x86_64 UEFI PC，2024-05-31）：在 Debian 安裝程式中「所有項目皆取消勾選，只留下 SSH server 與 common system utilities」的情況下，DietPi 為 296 MiB RAM／1055 MiB 磁碟／237 套件，Debian 為 357 MiB RAM／1787 MiB 磁碟／357 套件19。

對照組的詮釋：DietPi 官方自己也提醒「這不代表 DietPi 比其他發行版更好」，只是其 base image 更輕；其他專案（如 Armbian）把重心放在自有建置系統、核心開發與硬體支援上19。換言之，選 DietPi 是用「與 Debian 上游的距離」換取足跡。此頁數據亦標註為 2024–2026 年間分批測得，硬體與軟體世代不同，不宜直接跨列比較。

8.4 硬體需求#

官方安裝前置需求20：

  • 一台受支援的 SBC 或 PC（Raspberry Pi、Odroid 等，或 x86_64 PC／VM）
  • 一張至少 4 GiB 的 SD 卡、USB 隨身碟或 eMMC，以及寫入工具
  • 選用：網路線

支援清單中最低 RAM 的板子是 Raspberry Pi 1／Zero，僅 256 MiB LPDDR2（最高 512 MiB），可見其能在極低記憶體硬體上運作18。

針對 x86_64 虛擬化環境20：

  • VirtualBox：最小運行系統約需 1.2 GiB 磁碟空間，典型含 X11 的系統需 5–10 GiB

8.5 安裝步驟#

官方安裝流程為三步20：

  1. 準備安裝媒體：SD 卡（SBC）或 USB 隨身碟（PC），至少 4 GiB。
  2. 取得並燒錄 DietPi 映像：從 dietpi.com/#download 下載（.xz 壓縮格式）。多數燒錄工具（balenaEtcher、Rufus、Raspberry Pi Imager）可直接處理 .xz；否則需先解壓（Linux 上用 xz-utils：xz -d DietPi-Image.img.xz）。若要用 WiFi，可在開機分割區編輯 dietpi.txt（把 AUTO_SETUP_NET_WIFI_ENABLED 設為 1）與 dietpi-wifi.txt（設定 aWIFI_SSID[0] 與 aWIFI_KEY[0]）20。
  3. 開機並完成一次性設定：插入媒體、開機、依對話完成首次設定。

首次開機注意事項20：

  • 因為會自動調整根檔案系統大小並執行基本設定，這次開機比後續每次開機久很多，依儲存裝置與硬體可能長達數分鐘。
  • 支援無人值守的首次開機安裝（automatic base installation），透過 dietpi.txt 自動化20。

  • 直接匯入 qcow2：跳過 ISO 安裝流程，改在 Proxmox 主機 console 執行（qm importdisk、qm set 等指令）。官方亦提及社群腳本 dazeb/proxmox-dietpi-installer20。

9. 方案 G：Devuan（移除 systemd 的 Debian fork）#

9.1 定位#

Devuan GNU+Linux 是自由軟體作業系統，也是 Debian 的 fork，主要差異是移除了 systemd。其使命是確保「Init Freedom」，讓使用者能執行傳統 init 系統（預設 sysvinit，亦支援 OpenRC、runit 等）。該 fork 於 2014-11-27 在 DNG 郵件列表上宣布，動機是 Debian 的 systemd 爭議。實務上 Devuan 絕大多數套件與 Debian 相同，只有需要 systemd 的套件被排除或以移除該相依的方式 fork23。

9.2 版本與 Debian 對應#

下一個開發中版本為 Devuan 7 "Freia"（基於 Debian Forky）；unstable 代號為 ceres（等同 Debian sid）2423。此外 Excalibur 起 merged-/usr 為強制要求，從 Daedalus 升級前必須先安裝 usrmerge 套件；i386 已無安裝程式與核心23。

官方建議在 sources.list 中使用發行代號而非 stable／testing 這類 suite 名稱，以避免兩個可能不相容的儲存庫被混用24。

9.3 映像種類與大小#

以 Excalibur 6.1.1（2026-04-25 建置）的 amd64 為例25：

*_netinstall.iso 是「最小安裝程式」：先安裝最小 base system，再於安裝過程中從 Devuan 儲存庫下載額外套件（需網路連線，不支援離線安裝）23。另有 *_minimal-live 是純 console 的 live 映像（以無障礙／盲用為重點、使用 refractainstaller），amd64 為 877 MB23。

9.4 硬體需求（社群經驗值）#

Devuan 沒有官方公布的系統需求表；其描述為「軟體的倉庫」，需求取決於你選擇的設定。來自官方論壇的指引23：

  • RAM：執行 Excalibur netinstall 約需 800 MB 最低；視窗管理員加瀏覽器約 1 GB；現代圖形桌面建議 2 GB 以上（或 4 GB）。
  • 磁碟：8 GB 磁碟可「舒適地安裝多數圖形桌面環境」，但建議 20 GB 以上以備未來。
  • 一個被引用的 Debian 等效基準為：雙核 1 GHz CPU、2 GB RAM、20 GB 儲存、8 GB USB 隨身碟；但實際上能在更舊的硬體上運作（例如 13 年前的雙核筆電配 4 GB RAM）。
  • 架構：Excalibur 提供 i386（無核心）、amd64、armel、armhf、arm64、ppc64el、riscv64；安裝 ISO 僅限 amd6423。

來源品質提醒：以上 RAM 數字來自官方論壇討論而非官方規格文件，屬社群經驗值，可信度低於官方白皮書等級的來源。若要嚴謹規劃，應以實機測試為準。

9.5 安裝流程#

  1. 從 release archive 或 mirror 下載 ISO；可用 sha256sum -c SHA256SUMS 與 gpg --verify 驗證23。
  2. 寫入媒體：ISOs 為 hybrid，USB 用 dd if=filename.iso of=/dev/sdX bs=1M && sync23。
  3. 開機後選 Install。圖形安裝程式已被移除；Excalibur 的安裝程式為 console/framebuffer 模式，選 "Expert install" 可排除非自由韌體23。
  4. 依對話完成：語言 → 地區 → 鍵盤 → 網路 → hostname／domain → root 密碼 → 建立使用者帳號 → 時鐘／NTP／時區。
  5. （選用）全磁碟加密。
  6. 分割磁碟（使用最大可用空間以保留既有分割區，或用整顆磁碟——後者會清空一切）。
  7. 寫入分割表並安裝 base system。
  8. （選用）掃描其他光碟；選擇網路 mirror（建議 deb.devuan.org）。
  9. 選擇 popcon（自願參加）與軟體選擇（預設桌面為 Xfce）。
  10. 安裝套件，然後選擇 init 系統（預設 sysvinit）。
  11. 安裝 GRUB 到 MBR（例如 /dev/sda），完成後移除媒體並重開機。

升級路徑：先安裝 usrmerge 後可從 Devuan Daedalus 升級到 Excalibur，或從 Debian Trixie 遷移過來；不支援跳版升級23。

取捨提醒：對「伺服器主機」而言，Devuan 的價值主張是「不使用 systemd」。這是一個技術與哲學的取捨：你得到的是傳統 init 的簡潔與可替換性，付出的是與 Debian 生態中部分依賴 systemd 的現代套件（例如某些容器執行環境、部分桌面整合）的相容性落差，以及社群規模與商業支援較小。若沒有明確的 systemd 排斥理由，方案 A 仍是預設選擇。

（2）Ubuntu Minimal Cloud Images：這是預先安裝好的磁碟映像（非 ISO），由 Ubuntu 工程團隊客製為極小執行期足跡，用於「預期不會有人登入」的環境以提升工作負載密度28。

重點事實2728：

  • Minimal 映像有大幅縮減的預設套件集、沒有供互動使用的便利工具、開機更快、長期下來需要的安全更新更少。
  • 自 23.10（Mantic）起導入 cloud-minimal seed：套件數從 426 降到 288，QCOW2 映像大小從 337 MiB 降到約 227 MiB。
  • unminimize 指令（sudo unminimize）可把 minimal 實例轉回標準 Server 環境（還原說明文件、man page、翻譯，並安裝 linux-image-virtual 等套件）。這是 minimal 模式「可逆」的關鍵。
  • 發行版建置位於 https://cloud-images.ubuntu.com/minimal/releases/，26.04 LTS（resolute）已有發行建置。

10.5 autoinstall（無人值守）#

autoinstall 是 Ubuntu 的自動化安裝機制，由 Subiquity 安裝程式實作，使用 YAML 格式，支援 Ubuntu Server 20.04 以上27。提供設定的兩種方式27：

  1. 透過 cloud-init（官方推薦）：以 cloud-config user data 交付（通常經 NoCloud data source），需要 #cloud-config 標頭與頂層 autoinstall: 鍵。
  2. 直接放在安裝媒體上：把 autoinstall.yaml 置於安裝媒體根目錄（含 casper 子目錄的那個分割區），不需要頂層 autoinstall: 鍵（24.04 起允許單一頂層 autoinstall: 關鍵字）。路徑也可用核心命令列的 subiquity.autoinstallpath= 指定。

當多處同時存在時，優先順序為：核心命令列 > 安裝系統根目錄 > cloud-config > 安裝媒體（ISO）根目錄27。

重要頂層鍵（含預設值）摘錄27：

  • version：必須為 1（必要）
  • identity：初始使用者——username、password（加密）、hostname、realname、groups（除非有 user-data，否則這是唯一必要的鍵）
  • source：id（例如 ubuntu-server-minimal）
  • storage：layout 可選 lvm（預設）、direct、zfs；支援 LUKS、TPM 加密、sizing-policy、reset-partition
  • network：Netplan 格式（預設對 eth*／en* 使用 DHCP）
  • ssh：install-server（預設 false）、authorized-keys、allow-pw
  • packages、snaps、drivers、codecs
  • updates（預設 security；可設 all）、shutdown（預設 reboot）
  • early-commands、late-commands、error-commands：在安裝環境執行，目標系統掛載於 /target，可用 curtin in-target -- 在目標系統內執行
  • interactive-sections：列出仍要互動詢問的區段（* 表示全部）

行為差異提醒：與 debian-installer 的 preseed 不同，未回答的問題會採用預設值（若無預設值則失敗）27。官方亦說明：設定會以 JSON schema 驗證，version 1 中無法辨識的鍵會被忽略，但未來版本會變成致命錯誤27。

11. 方案 I：Proxmox VE（把主機本身當虛擬化平台）#

若「server host」的定義是「要跑多台 VM／容器的宿主」，則 Proxmox VE 是常見的 Debian 系選擇。

11.1 版本與 Debian 基底#

Proxmox VE 9.2 為現行穩定版（ISO 9.2-1，2026-05-21；ARM64 版 9.2-1-arm64 於 2026-08-05 發布），搭載 Linux kernel 7.0 系列2930。Debian 對應關係31：

官方 FAQ 明載：「Proxmox VE is based on Debian GNU/Linux」，且其支援期至少與對應 Debian 版本一樣長（約首次發行後 3 年，依 Debian Security Team 支援期），並採用 rolling release 模式，建議永遠使用最新穩定版31。

注意架構限制：Proxmox VE 僅支援 64 位元 CPU，支援的架構為 x86_64（AMD64 或 Intel 64）以及 NVIDIA Grace Hopper／NVIDIA Vera 平台上的 aarch64，沒有支援 32 位元的計畫。不過VM 與容器本身可以是 32 位元或 64 位元31。

11.2 硬體需求#

最低（僅供評估／測試）32：

  • CPU：64 位元 x86（AMD64 或 Intel 64）並支援 Intel VT 或 AMD-V；或 64 位元 ARM（ARMv8-A 以上）。
  • RAM：1 GB 最低，外加供 guest 使用的記憶體。
  • 磁碟：安裝程式拒絕小於 2 GB 的系統磁碟，並在低於「建議最小空間 8 GB」時提出警告。
  • 一張 NIC。

建議（正式環境）32：

  • RAM：最低 2 GB 供作業系統與 Proxmox VE 服務使用，外加指定給 guest 的記憶體。若用 Ceph 或 ZFS，約每 TB 已用儲存需額外 1 GB（ZFS wiki 建議至少從 8 GB 起）。
  • 儲存：快速且有冗餘的儲存；建議 SSD，最好具備 Power-Loss-Protection（不建議消費級 SSD）。注意 ZFS 與 Ceph 不相容於硬體 RAID 控制器。
  • 具冗餘的 (Multi-)Gbit NIC。
  • 若要 PCI(e) passthrough：需要 IOMMU（x86 上的 Intel VT-d／AMD-Vi，arm64 上的 SMMU）。

補充：安裝程式在 ext4/XFS 安裝中會把根 volume 設為磁碟的 1/4（上限 96 GiB），其餘留給 guest，因此 128 GB 以上的 SSD 對 host 本身而言相當寬裕32。

檢查 CPU 是否支援虛擬化（僅適用 x86 主機）31：

egrep '(vmx|svm)' /proc/cpuinfo

官方說明：在支援的 arm64 平台上，KVM 硬體輔助虛擬化是可用的，且不會回報對應的 CPU flag31。

11.3 從 ISO 安裝#

ISO 安裝程式是官方推薦的方法30：

  1. 從下載頁取得 ISO 並製作安裝媒體（USB/CD）。
  2. 在韌體中啟用從該媒體開機；關閉 Secure Boot（Proxmox VE 8.1 之前的安裝程式必須如此；memtest 仍需要）。
  3. 開機後選 Install Proxmox VE (Graphical)、Terminal UI 或 Terminal UI, Serial Console（無頭機）。圖形與終端使用相同的安裝程式碼。
  4. 精靈會分割磁碟——ext4（預設）、XFS、BTRFS（tech preview）或 ZFS——並設定時區、語言與網路。所選磁碟上的所有既有資料都會被清除，且不會加入其他 OS 的開機項目。
  5. 重開機，瀏覽 https://<your-ip>:8006，以 root 與 PAM realm 登入。
  6. 設定套件儲存庫（Enterprise repo 需訂閱金鑰），然後建立 Linux bridge（vmbr0）。

11.4 在既有 Debian 上安裝 Proxmox VE#

這是官方文件化的方法，適合想要自訂分割配置的人；官方提醒僅建議進階使用者使用，因為需要相當深入的 Proxmox 知識33。

官方 how-to 步驟33：

  1. 安裝標準 Debian Trixie（amd64），設定靜態 IP，並確保 hostname 能解析到非 loopback IP（透過 /etc/hosts 或 DNS）。
  2. 以 deb822 格式加入 Proxmox 儲存庫：
cat > /etc/apt/sources.list.d/pve-install-repo.sources << EOL
Types: deb
URIs: http://download.proxmox.com/debian/pve
Suites: trixie
Components: pve-no-subscription
Signed-By: /usr/share/keyrings/proxmox-archive-keyring.gpg
EOL

wget https://enterprise.proxmox.com/debian/proxmox-archive-keyring-trixie.gpg -O /usr/share/keyrings/proxmox-archive-keyring.gpg
apt update && apt full-upgrade
  1. 安裝並開機進入 PVE 核心：apt install proxmox-default-kernel 然後 systemctl reboot。
  2. 安裝套件：apt install proxmox-ve postfix open-iscsi chrony。官方說明：chrony 可換成其他 NTP daemon，但不建議在伺服器系統上使用 systemd-timesyncd；而 ntpsec-ntpdate 選項在某些硬體上可能與開機時啟動網路衝突。
  3. 移除 Debian 核心（Trixie 上為 apt remove linux-image-amd64 'linux-image-6.12*'）並執行 update-grub（若用 systemd-boot 則不需要）；建議一併移除 os-prober，因為它會掃描所有分割區並為其建立 GRUB 項目，而被掃描的分割區可能包含已分配給虛擬機的磁碟。
  4. 連到 https://your-ip:8006，建立 vmbr0 bridge，上傳訂閱金鑰。

與本報告主題的關鍵交集：官方此頁明確建議，在安裝 Debian Trixie 基底時「只安裝 "standard system utilities" 與 "SSH server" 套件選擇，因為 Proxmox VE 自帶 QEMU 與 LXC 的套件，不需要桌面環境」33。這正是方案 A 的最小安裝配置，也是本報告中「輕量 Debian 主機」的一個具體應用場景。

注意事項33：

  • 在啟用 Secure Boot 的情況下使用（實驗性的）systemd-boot 方法時，不支援在 Debian 之上安裝 Proxmox VE。
  • 實務陷阱：Proxmox VE GUI 預期自己控制 DNS 管理，不再從 /etc/network/interfaces 取得 DNS 設定；任何會自動產生（覆寫）/etc/resolv.conf 的套件（例如 IPv4 的 resolvconf、IPv6 的 rdnssd）都會導致 DNS 失效。
  • 若 PVE 核心開機失敗並出現 error: bad shim signature.，請確認已關閉 Secure Boot。
  • 若看到 ipcc_send_rec[1] failed: Connection refused 之類訊息，應回頭檢查 /etc/hosts 設定（即前述主機名稱解析要求）。

12. 安裝後的加固與最小化#

無論選哪條路徑，以下是讓「輕量主機」同時「安全」的必要步驟。貫穿全場的原則：在整個過程中保持一條非 SSH 的備援存取管道（供應商 console／VNC／實體存取）開啟，因為每一步做錯順序都可能把自己鎖在外面34。

12.1 先建立可使用 sudo 的非 root 使用者#

最小安裝可能連 sudo 都沒有。以 root 身分執行34：

apt update && apt install sudo        # 最小安裝可能沒有 sudo
adduser username                      # 互動式；設定密碼與家目錄
usermod -aG sudo username             # Debian 透過 'sudo' 群組授予 sudo

群組變更只在新登入 session 生效（su - username 或重新登入）。用 sudo whoami 驗證應輸出 root。另一個做法是用 visudo 加入 username ALL=(ALL:ALL) ALL34。

對照官方安裝手冊的說明：若在安裝時不指定 root 密碼，root 帳號會被停用，而安裝程式會改為安裝 sudo 套件，並讓系統上第一個建立的使用者可以使用 sudo 成為 root7。這是比「設 root 密碼並持續以 root 登入」更好的預設。

12.2 SSH 僅允許金鑰認證#

先安裝金鑰並在另一個終端機確認可用，然後才停用密碼認證。 客戶端34：

ssh-keygen -t ed25519 -C "laptop"
ssh-copy-id username@your-server-ip

伺服器端建立 drop-in 檔案（不要直接編輯主 sshd_config）34：

sudo nano /etc/ssh/sshd_config.d/00-hardening.conf
PermitRootLogin no
PasswordAuthentication no
KbdInteractiveAuthentication no
PubkeyAuthentication yes
MaxAuthTries 3
LoginGraceTime 30
X11Forwarding no
AllowUsers username

驗證並重新載入34：

sudo sshd -t && echo "config OK"
sudo sshd -T | grep -E '^(permitroot|password|maxauth|allowusers)'
sudo systemctl reload ssh     # 用 reload 而非 restart，保留既有 session

關鍵陷阱（有官方 man page 佐證）3534：Debian 的 openssh-server 套件在 /etc/ssh/sshd_config 內預設有 Include /etc/ssh/sshd_config.d/*.conf，而這些檔案被包含在設定檔的開頭，因此其中的選項會覆寫 sshd_config 主體中的設定35。同時，對每個關鍵字而言第一個出現的值才會被採用，而 include 檔案是按字典序處理的3435。這代表雲端映像中的 50-cloud-init.conf（把 PasswordAuthentication 設為 yes）會勝過你的 60-hardening.conf。**因此請將檔案命名為 00-hardening.conf，並且每次都以 sshd -T 確認實際生效值是你要的。**權限也必須正確：~/.ssh 為 700、authorized_keys 為 60034。

其他可用的加固關鍵字（依 man page 定義）35：

  • AllowUsers：只允許符合模式的帳號登入；預設允許所有使用者。允許／拒絕指令的處理順序為 DenyUsers 後 AllowUsers。若模式形如 USER@HOST，使用者與主機分別檢查，可把登入限制在特定來源主機。
  • PermitRootLogin：預設為 prohibit-password（對 root 停用密碼與 keyboard-interactive 認證）。設為 no 則 root 完全不可登入。其餘可選值為 yes 與 forced-commands-only。
  • MaxAuthTries：預設 6。當失敗次數達到此值的一半時，後續失敗會被記錄。
  • LoginGraceTime：預設 120 秒；設為 0 表示無時限。
  • KbdInteractiveAuthentication：上游預設 yes，但 Debian 的 openssh-server 套件已將其設為 no（這是套件層級的非上游預設值之一）35。
  • PerSourcePenalties：OpenSSH 較新版本內建的懲罰機制，對造成 sshd 崩潰、認證失敗後斷線、未嘗試認證即斷線、超過 LoginGraceTime 未完成認證等行為的來源位址（依 PerSourceNetBlockSize 定義的網段）施加一段時間的拒絕連線。預設即啟用，可用 no 停用。預設值包含 authfail:5s、crash:90s、noauth:1s、grace-exceeded:10s、max:10m、min:15s35。

Debian 套件層級的非上游預設值（安裝後即生效）還包括：Include /etc/ssh/sshd_config.d/*.conf、X11Forwarding yes、PrintMotd no、AcceptEnv LANG LC_* COLORTERM NO_COLOR、Subsystem sftp /usr/lib/openssh/sftp-server、UsePAM yes35。

12.3 防火牆：nftables（原生）或 UFW（前端）#

Debian 自 Debian 10 Buster 起就以 nftables 為預設防火牆框架，取代舊的 iptables 及相關工具（ip6tables、arptables、ebtables 皆已棄用）36。官方 wiki 特別指出：舊網頁仍常提及 iptables，但它已棄用多年且可移除；即使安裝了 iptables，實際上也是透過 iptables-nft 相容層使用 nftables36。

UFW（需自行安裝，且啟用前不會生效）——順序非常關鍵，必須先允許 SSH34：

sudo apt install ufw
sudo ufw allow 22/tcp          # 或：sudo ufw limit 22/tcp（30 秒內 6 次以上連線會被封鎖）
sudo ufw default deny incoming
sudo ufw default allow outgoing
sudo ufw allow 80/tcp          # 只開放你實際有在跑的服務
sudo ufw allow 443/tcp
sudo ufw enable
sudo ufw status verbose

啟用後 UFW 會在開機時自動啟動。但必須注意：Docker 會繞過 UFW——已發布的容器 port 會在防火牆規則生效前就被路由，因此要嘛綁定到 127.0.0.1，要嘛管理 Docker 自己的過濾規則34。

nftables（原生，Debian 11 起）36：

sudo apt install nftables
sudo systemctl enable nftables.service
sudo nft list ruleset

規則預設位於 /etc/nftables.conf，此檔案中的規則會跨重開機持續存在（用 nft add rule 臨時加入的則不會）。重新載入用 sudo systemctl reload nftables.service36。Debian 的 nftables 套件在 /usr/share/doc/nftables/examples/ 提供範例規則集，上游亦在 nftables wiki 提供 workstation、server 與 home router 範例36。

一個實用的最小語法範例（改寫自官方 wiki 範例）36：

# 建立 IPv4/IPv6 雙棧的 filter 表
nft add table inet filter
# 建立 input chain
nft add chain inet filter input { type filter hook input priority 0\; }
# 接受 80/tcp 與 443/tcp 的新連線與既有連線並計數
nft add rule inet filter input tcp dport {80, 443} ct state new,established counter accept

官方 wiki 也強調 nftables 與 iptables 的幾個主要差異36：

  • iptables 預設有 filter、nat 等表與 INPUT、FORWARD 等 chain；nftables 沒有預設的 table 或 chain，必須自行建立。
  • iptables 每條規則只能有一個 target（-j ACCEPT、-j LOG 等），nftables 可在單一規則中執行多個動作。
  • nftables 內建資料集（set）能力；iptables 需要另外使用 ipset 工具。
  • iptables 每個 family 各有工具（iptables、ip6tables、arptables、ebtables）；nftables 以單一 CLI 工具管理所有 family，並可透過 inet family 同時看到 IPv4 與 IPv6 流量。

不要同時讓 UFW 與 nftables 各自改寫規則集34。官方 wiki 亦提醒：不要混用 nftables 與 iptables/ebtables/arptables 規則集，除非你知道自己在做什麼36。若要停用 nftables，官方提供兩種層級：nft flush ruleset 可清空所有規則但不阻止服務啟動，systemctl mask nftables.service 則可阻止其在開機時啟動36。

12.4 fail2ban#

sudo apt install fail2ban

Debian 套件已預設啟用一個 sshd jail，並設定 backend = systemd（讀取 journal）與 banaction = nftables34。

絕對不要編輯 jail.conf——建立 drop-in 檔案 /etc/fail2ban/jail.d/sshd-local.conf（檔案按字母順序讀取，後者勝出）34：

[DEFAULT]
bantime  = 1h
findtime = 10m
maxretry = 4
ignoreip = 127.0.0.1/8 ::1 <your-admin-IP>

[sshd]
enabled = true

先把你自己的 IP 加入 ignoreip（echo $SSH_CLIENT 可顯示你目前的位址）。測試後重新啟動34：

sudo fail2ban-server -t                 # 必須印出 "OK"
sudo systemctl restart fail2ban
sudo fail2ban-client status sshd

若被誤鎖，可從 console 解鎖：sudo fail2ban-client set sshd unbanip <IP>34。

成本效益提醒：在已採金鑰認證的情況下，密碼猜測本來就會失敗，因此 fail2ban 的主要作用是降低日誌噪音，應視為其中一層防線，而非主要防禦手段34。DietPi 也對 fail2ban 做了整合，其 dietpi-banner 會顯示封鎖數，且 v10.7 起也計入以 CIDR 標記的整個子網封鎖22。

12.5 unattended-upgrades（自動安全修補）#

sudo apt install unattended-upgrades
sudo dpkg-reconfigure -plow unattended-upgrades   # 回答 yes

官方 wiki 提供的等價檢查方式是 sudo dpkg-reconfigure unattended-upgrades，它應該詢問你是否要自動下載並安裝 stable 更新（答案是 yes）37。

這會建立 /etc/apt/apt.conf.d/20auto-upgrades34：

APT::Periodic::Update-Package-Lists "1";
APT::Periodic::Unattended-Upgrade "1";

官方說明：檢查每天執行兩次，時間隨機化（由 apt-daily.timer 控制）；設定位於 /etc/apt/apt.conf.d/50unattended-upgrades；建議把覆寫放在新檔案 /etc/apt/apt.conf.d/52unattended-upgrades-local，以免套件升級時衝突（官方 wiki 的作法是複製 50unattended-upgrades 為 52unattended-upgrades-local 再編輯）3734。實用設定34：

Unattended-Upgrade::Mail "admin@example.com";
Unattended-Upgrade::MailOnlyOnError "true";
Unattended-Upgrade::Automatic-Reboot "false";
Unattended-Upgrade::Automatic-Reboot-Time "02:00";

注意：預設設定只自動安裝安全更新，不裝新功能；Unattended-Upgrade::Origins-Pattern 區段中想自動更新的來源預設是註解掉的，需自行取消註解37。

測試與監控3734：

sudo unattended-upgrade -d          # 手動執行以除錯

監控 /var/log/unattended-upgrades/ 與 /var/log/dpkg.log。官方 wiki 建議可安裝 apt-listchanges 以設定更新通知（設定檔 /etc/apt/listchanges.conf，範例可設 email_address=root、which=both）37。

官方也提醒兩個實務要點37：

  • 定時器為 apt-daily.timer（下載）與 apt-daily-upgrade.timer（升級），可用 systemctl edit 調整。
  • RandomizedDelaySec 不應隨意關閉：官方說明在 RandomizedDelaySec 之類工具出現前，伺服器會在每天某幾秒出現巨大流量尖峰，其餘時間相對沉寂；「一兩個人關掉不會有太大差別，但請考慮把延遲設為至少 1h」。
  • 若機器是筆電：unattended-upgrades 預設在非 AC 電源時拒絕執行。官方建議可用 Unattended-Upgrade::OnlyOnACPower "false"; 與覆寫 apt-daily-upgrade 服務（移除 ConditionACPower）強制執行，但明確指出這有風險。

替代方案：官方列出 cron-apt、GNOME 的軟體更新設定等，但強調這些方法不應與 unattended-upgrades 同時使用37。

12.6 建議一併安裝的除錯輔助#

官方 wiki 在 See Also 中提及 needrestart 系列套件，用於辨識在套用（先前已安裝的）安全更新後，哪些額外執行中的行程需要重啟、才能在不重開機的情況下真正套用更新37。對長期不重開機的伺服器而言，這是重要的一環。

12.7 最小化與加固的取捨矩陣#

重要：「輕量」不應以犧牲可維護性為代價。官方對 standard task 的警告（「除非你知道自己在做什麼」）值得認真對待：一個缺少常見工具的最小系統，在故障排除時的隱形成本往往遠高於它省下的 196 MB。對多數伺服器，建議保留 standard，只在磁碟極度受限時才省略。

14. 來源批判性反思#

本報告所引用的來源，其性質與可信度並不一致。以下逐類說明，供讀者判斷各項敘述應賦予多少權重。

14.1 最高可信度：官方專案文件#

Debian 的安裝手冊、CD FAQ、releases/ 頁面、man page 系統（manpages.debian.org）、官方 wiki（wiki.debian.org）皆屬第一方文件，內容由專案維護，且有版本對應的明確標示（例如 manpages.debian.org/trixie/... 會標明套件版本，如 openssh-server 1:10.0p1-7+deb13u4）35。這類來源適合直接作為規劃依據。

DietPi、Devuan、Ubuntu、Proxmox 的官方站與文件同屬第一方，但性質不同：它們描述的是各自產品的行為，客觀性仰賴其自我揭露。本報告在引用時已標明其為「官方數據」或「官方說明」。

14.2 需注意的官方偏誤#

DietPi 的比較數據來自 DietPi 自己。官方在同頁聲明「這不代表 DietPi 比其他發行版更好」，並解釋其他專案（如 Armbian）把重心放在自有建置系統、核心開發與硬體支援上19。這是一段值得肯定的自我揭露，但讀者仍應注意：

  • 比較的基準點由 DietPi 選擇（例如選擇 Raspberry Pi OS Lite 而非 Raspberry Pi OS full）。
  • 不同列的測試日期橫跨 2024–2026，硬體與軟體世代不同（例如 x86_64 那兩列標註 2024-05，而 SBC 那幾列標註 2026-03 至 2026-06）19。跨列直接比較並不嚴謹。
  • 「與 Debian netinst 對照」那一列的官方開場白就直接承認：「這些映像難以比較」（These images are hard to compare）19。

因此本報告在引用時保留原始數字與日期，並未把不同列的數字合併成單一「DietPi 比 X 快 Y%」的結論。

14.3 最需警惕：非官方教學與社群經驗值#

本報告在加固一節（第 12 章）中，部分操作細節來自技術教學網站（liberiangeek、linuxize、howtoforge、poweradm、glesys docs 等）34。這些來源的風險在於：

  • 可能未跟上版本：許多教學的預設前提是較舊的 Debian／Ubuntu。
  • 可能包含非最佳實務：例如某些教學仍建議直接編輯 sshd_config 而非使用 drop-in 檔案。

本報告的處理方式是：凡有官方文件可佐證者，以官方為準並於內文標明。例如：

  • SSH 的 Include 機制與「第一個值勝出、按字典序讀取」的行為，由官方 sshd_config(5) man page 直接佐證35，而非僅依賴教學網站。
  • PermitRootLogin 預設為 prohibit-password、MaxAuthTries 預設 6、LoginGraceTime 預設 120 秒等，均引自 man page35。
  • nftables 為 Debian 預設框架、iptables 已棄用，引自 Debian 官方 wiki36。
  • unattended-upgrades 的設定檔覆寫建議與定時器名稱，引自 Debian 官方 wiki37。

凡無法由官方來源佐證者，已於內文明確標示。最明顯的例子是 Devuan 的 RAM 需求：該數字來自官方論壇討論而非官方規格文件，因此報告中標為「社群經驗值」並加上來源品質提醒23。Devuan 官方本身也承認沒有公布系統需求表23。

14.4 版本時效性的風險#

這是本主題最大的陷阱。三個實例：

  1. Debian 版本：大量現存教學以 Bookworm 為 stable 撰寫，但 2026 年已是 Trixie。本報告以 www.debian.org/releases/ 的即時資料確認1。
  2. Proxmox VE：其 Debian 對應關係隨版本演進（8 → Bookworm、9 → Trixie），若沿用舊教學可能裝出與預期不符的基底31。
  3. OpenSSH：較新版本引入 PerSourcePenalties 這類內建防護，舊教學不會提到，可能導致讀者以為必須額外安裝工具才能達到同等防護35。

結論：本報告所有版本號與日期均標註擷取或發行日期，並以 ISO 檔案清單的實際時間戳（例如 debian-13.7.0-amd64-netinst.iso 為 2026-09-12）佐證4。讀者在數月後閱讀本報告時，應重新確認 www.debian.org/releases/ 的現況。

14.5 未取得或無法驗證的資訊#

基於誠實揭露原則，以下事項本報告未能取得可靠來源，故未給出結論：

  • Debian minimal 安裝的實測 RAM 佔用：官方手冊提供的最低記憶體需求（512 MB／1 GB）是安裝條件，而非安裝完成後閒置時的實際 RAM 用量5。官方並未公布對應的實測閒置記憶體數據。DietPi 有公布自身數據，但那是 DietPi 而非原生 Debian19。
  • Devuan 的官方硬體規格：官方無此文件23。
  • 各方案在 Arm 架構上的完整實測：本報告的尺寸數據以 amd64 為主。
  • mini.iso 是否為正式支援路徑：官方 netinst 頁面並未列出它，僅在 CD FAQ 的 unstable 安裝選項中被提及36。因此本報告將它歸類為「進階使用者」路徑而非預設推薦。

15. 結論與建議#

  1. 預設選擇：對絕大多數「要裝一台 Debian 系伺服器主機」的需求，方案 A（netinst 最小安裝） 是最平衡的選擇——官方支援、資料最完整、可維護性最高。具體做法是取消 Desktop environment、勾選 SSH server、保留 Standard system utilities，最終約 843 MB。

  2. 若目標是 VM 或雲端：直接用方案 C（官方雲端映像），選 nocloud 做本機 VM、generic 做雲端。省去整個安裝流程，且開機即是最小系統。

  3. 若磁碟或記憶體極度受限（SBC、老舊硬件）：方案 F（DietPi） 在 Raspberry Pi Zero W 上實測僅 42 MiB RAM 與 702 MiB 磁碟，是同一硬體上原生 Debian 難以達到的水準。代價是與 Debian 上游的距離。

  4. 若要大量重複部署：用方案 E（preseed） 或 Ubuntu 的 autoinstall。注意兩者的失敗行為不同：preseed 未回答會走預設，autoinstall 亦然，但 autoinstall 對無法辨識的鍵在未來版本會變成致命錯誤27。

  5. 若要把主機當虛擬化平台：方案 I（Proxmox VE） 本身即建構在 Debian Trixie 上，且其官方文件反而建議你採用與方案 A 相同的最小安裝配置33。

  6. 無論選哪條路徑，第 12 章的加固步驟都是必要的，其中三個最易出錯的點是：

    • SSH drop-in 檔案的命名順序（用 00- 前綴）與 sshd -T 驗證。
    • 防火牆啟用前必須先允許 SSH。
    • 全程保持一條非 SSH 的備援存取通道。

  7. 關於「輕量」的底線：省下 196 MB 卻換來一個難以故障排除的系統，通常不是好交易。輕量的價值在於較小的攻擊面與較少的常駐服務，而非單純的磁碟數字。
