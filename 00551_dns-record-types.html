00551_dns-record-types

DNS Record 的種類與意義#

摘要#

DNS（Domain Name System，網域名稱系統）是網際網路將「人類可讀的名稱」對應到「機器可讀的位址與服務資訊」的分散式資料庫。這個資料庫的最小單位是「資源紀錄」（Resource Record，簡稱 RR），每一筆紀錄都由若干欄位構成，並以一個「型別代碼」（TYPE code）標示其用途1。本文整理 DNS 紀錄的主要型別、每一種型別代表什麼意思、其資料欄位、以及常見用途；同時說明幾個容易誤解的限制（例如 CNAME 不能與其他紀錄並存、不能放在 zone apex），並在附錄列出 IANA 官方註冊表的完整型別清單。

本文以 IETF 的 RFC 標準文件與 IANA 官方註冊表為主要來源，輔以維基百科與 ICANN、Let's Encrypt 等機構的說明文件。所有事實均標註來源。

一、先理解脈絡：Zone、TTL、快取與伺服器角色#

在逐一介紹紀錄型別前，必須先理解幾個基礎觀念，否則難以理解某些型別為何存在。

1.1 Zone（區域）#

DNS 的命名空間是一棵樹狀結構，這個資料庫被切分成若干「zone（區域）」，由不同的名稱伺服器分別負責1。Zone 是「由單一管理權威所控制的連續命名空間區段」；一旦某個組織控制了自己的 zone，就可以單方面修改其中的資料、新增子樹、刪除節點，或把新的子 zone 委派出去1。一個 zone 通常包含四大部分：該 zone 內所有節點的權威資料、定義 zone 頂端節點的資料（含 SOA 與 NS）、描述被委派子 zone 的資料，以及指向子 zone 內名稱伺服器的 glue（黏合）資料1。

1.2 TTL（存活時間）#

每一筆 RR 都帶有一個 TTL 欄位。TTL 是一個 32 位元整數，單位為秒，主要供 resolver（解析器）在快取 RR 時使用，描述「這筆紀錄可被快取多久才應被丟棄」1。TTL 由資料來源 zone 的管理者指定；較短的 TTL 可降低快取效果，TTL 為零則禁止快取，但實務上典型主機常使用多天的 TTL1。

1.3 快取與解析器#

Resolver 的核心目標之一，是「藉由其先前結果的快取，消除大多數請求的網路延遲與名稱伺服器負載」1。當快取中已有資料時，會被視為「足夠良好」而直接回覆；但「權威資料永遠優先於快取資料」1。DNS 也提供選擇性的「負向快取」（negative caching），讓名稱伺服器能搭配 TTL 散布「此名稱不存在」的結果1。

1.4 伺服器角色：Root、TLD、權威與遞迴#

  • Root name servers（根伺服器）：位於命名樹最頂端（. 這個 zone），知道每個頂級網域（TLD）由哪些名稱伺服器負責；「根伺服器將提供通往整個網域空間的途徑」1。
  • TLD servers（頂級網域伺服器）：如 .com、.org 的權威名稱伺服器，由根 zone 以 NS 紀錄委派而來1。
  • Authoritative nameservers（權威名稱伺服器）：對某段命名空間持有完整、本地設定的資料，被稱為該區域的「權威」；名稱伺服器的「本質任務就是用其 zone 中的資料回答查詢」1。
  • Recursive resolvers（遞迴解析器）：代表使用者端程式介接名稱伺服器，在遞迴模式下「扮演解析器的角色，回傳錯誤或答案，但永不回傳轉介（referral）」1。

二、核心紀錄型別#

以下依型別逐一說明。型別代碼與命名引用自 IANA 的 DNS Parameters 註冊表2，欄位定義引用自各 RFC。

2.1 A（位址紀錄，Type 1）#

  • 意義：主機位址（a host address）2。
  • 內容：一個 32 位元的 IPv4 位址3。
  • 用途：最常見的是把主機名稱對應到其 IPv4 位址；此外也用於 DNSBL（黑名單）與存放子網遮罩等3。
  • 標準：RFC 10354。

2.2 AAAA（IPv6 位址紀錄，Type 28）#

  • 意義：IP6 Address2。
  • 內容：一個 128 位元的 IPv6 位址3。
  • 用途：把主機名稱對應到其 IPv6 位址，是 A 紀錄的 IPv6 對應版本3。
  • 標準：RFC 35965。

2.3 NS（名稱伺服器紀錄，Type 2）#

  • 意義：一個權威名稱伺服器（an authoritative name server）2。
  • 內容：一個權威名稱伺服器的主機名稱3。
  • 用途：把某個 zone 委派給一組權威名稱伺服器。它同時用在兩種位置：zone 頂端（宣告該 zone 自身有哪些 NS），以及在委派點（指向子 zone 的伺服器）1。
  • 重要規則：NS 的目標「不得為別名（CNAME）」6。
  • 標準：RFC 10354。

2.4 SOA（起始授權紀錄，Type 6）#

  • 意義：標示一個授權區域的開始（marks the start of a zone of authority）2。
  • 內容：包含七個欄位4：
  • 補充：每個 zone 恰有一個 SOA，位於其頂端節點1。RFC 2308 指出，MINIMUM 欄位的「最小 TTL」舊義「從未被實際採用，故予以廢止」，現行唯一保留的意義是「用於負向回應的 TTL」7。
  • 標準：RFC 10354，MINIMUM 語意由 RFC 2308 修訂7。

2.5 CNAME（正式名稱／別名紀錄，Type 5）#

  • 意義：別名所對應的正式名稱（the canonical name for an alias）2。
  • 內容：一個正式名稱（alias 的目標網域名稱）3。
  • 用途：建立從一個名稱指向另一個名稱的別名；解析器會用新名稱重試查詢3。RFC 2181 規定「任何一個別名只能有一個正式名稱」6。
  • 重要限制：CNAME 不能與同一名稱下的其他紀錄並存。RFC 2181 指出，一個別名名稱「若使用 DNSSEC，可以有 SIG、NXT、KEY 紀錄，但不得有其他資料」；且任一標籤（網域名稱）在 DNS 中恰好處於下列四種互斥狀態之一：存在一筆 CNAME（選擇性伴隨 SIG、NXT、KEY）、存在一或多筆非 CNAME 的紀錄、名稱存在但無任何 RR、名稱完全不存在6。
  • 標準：RFC 10354。

2.6 DNAME（委派名稱紀錄，Type 39）#

  • 意義：DNAME2。
  • 內容：一個目標網域名稱8。
  • 用途：為「整個子樹」提供重導向，凡是以某字尾結尾的所有名稱，都被重導向到 DNS 的另一部分8。例如 owner 為 example.com.、目標 example.net. 時，a.example.com. 會被改寫為 a.example.net.8。
  • 與 CNAME 差異：CNAME 只把「其 owner 的資料查詢」導向另一個單一名稱；DNAME 則把「其 owner 子孫的名稱查詢」導向樹中另一節點下的對應名稱；「DNAME 的 owner 名稱本身不會被重導向」8。
  • 限制：DNAME 的任一子網域「不得存在任何資源紀錄」，否則那些名稱會被遮蔽（occluded）8；一個 owner 只能有一筆 DNAME，且該名稱不得有 CNAME8。
  • 標準：RFC 66728。

2.7 MX（郵件交換紀錄，Type 15）#

  • 意義：mail exchange2。
  • 內容：清單，每筆包含一個偏好值（preference／priority）與一部郵件伺服器的主機名稱；「較小的數值優先」9。MX 的目標「必須直接指向 A 或 AAAA 紀錄，指向 CNAME 為 RFC 2181 所禁止」9。
  • 用途：指定代表某網域接收電子郵件的伺服器，以及嘗試順序4。寄件方的 MTA 查詢收件網域的 MX，按優先序（由小到大）排序後依序嘗試連線；這提供備援、容錯與負載平衡9。
  • Null MX：RFC 7505 定義了一種特殊 MX，用來宣告某網域「完全不收信」。它只有單一筆 MX，偏好值為 0、交換目標為 .（單一點，非合法主機名稱）；「由於 '.' 不是合法主機名稱，null MX 不會與一般 MX 混淆」10。此設計可讓寄件方立即收到失敗，避免其退回 A/AAAA 嘗試投遞而浪費資源9。
  • 標準：RFC 10354，Null MX 由 RFC 7505 定義10。

2.8 TXT（文字紀錄，Type 16）#

  • 意義：文字字串（text strings）2。
  • 內容：任意文字字串3。
  • 用途：原本供人類可讀文字之用；自 1990 年代起，主要用於攜帶給機器讀取的資料，例如 SPF、DKIM、DMARC、DNS-SD 等協定，是最具彈性、被最廣泛再利用的型別3。
  • 標準：RFC 10354。

2.9 PTR（指標紀錄，Type 12）#

  • 意義：網域名稱指標（a domain name pointer）2。
  • 內容：一個正式網域名稱3。
  • 用途：從名稱（通常是反解 zone 中由 IP 衍生的名稱）指向正式主機名稱，最常見於「反向 DNS 查詢」（reverse DNS），即把 IP 位址反查回主機名稱。「與 CNAME 不同，DNS 處理在 PTR 之後就停止，只回傳該名稱」3。
  • 反解 zone 結構：整個網際網路的反解資料庫根植於 .arpa 頂級網域11。IPv4 使用 in-addr.arpa：把位址切成四個 octet 後反轉順序再接上此字尾，例如 192.168.10.2 記為 2.10.168.192.in-addr.arpa11。IPv6 使用 ip6.arpa：以十六進位 nibble 反序排列11。
  • 常見用途：反垃圾郵件（收件伺服器檢查寄件 IP 的 PTR 是否與寄件網域相符）、DNSBL（以反解機制查詢 IP 是否在黑名單）、系統記錄與監控、網路疑難排解11。
  • 標準：RFC 10354。

2.10 SRV（服務定位紀錄，Type 33）#

  • 意義：Server Selection2。
  • 內容與格式：_Service._Proto.Name TTL Class SRV Priority Weight Port Target12。各欄位定義如下12：
    • Service：所需服務的象徵名稱，前置一個底線（_）以避免與自然出現的 DNS 標籤碰撞。
    • Proto：所需協定的象徵名稱，同樣前置底線，_TCP、_UDP 為目前最有用的值。
    • Priority：目標主機的優先序，「用戶端必須嘗試連線其所能觸及的最低編號優先序主機」，範圍 0–65535。
    • Weight：伺服器選擇機制；「權重為同優先序項目指定相對權重，較大權重應被賦予比例上較高的被選機率」，範圍 0–65535。
    • Port：該服務在目標主機上的埠號，範圍 0–65535。
    • Target：目標主機的網域名稱，「該名稱必須有一或多筆位址紀錄，且不得為別名」；目標為 . 表示該服務在此網域「明確地不存在」。
  • 用途：讓用戶端動態探索提供某服務的伺服器及埠號，例如 SIP、XMPP、Minecraft、Active Directory（網域控制站藉此註冊服務）等13。
  • 權重負載平衡：僅在同一優先序之間生效。RFC 2782 的演算法為：將權重為 0 的排在最前，其餘任意排序，計算權重總和並為每筆累加執行和，取一個 0 到總和（含）之間的均勻隨機數，選中累加和第一個大於等於該隨機數者12。這是「靜態」而非動態的伺服器選擇，「權重僅供靜態使用；若用於動態選擇需搭配不合理的短 TTL，會限縮 DNS 快取的效益」12。
  • 標準：RFC 278212。

2.11 CAA（憑證授權機構授權紀錄，Type 257）#

  • 意義：Certification Authority Restriction2。
  • 內容與格式：CAA <flags> <tag> <value>14：
    • Flags：0 為未設旗標（絕大多數情況），128 為「critical bit」，一旦設定，CA「必須」理解該 tag 的內容，否則「必須拒絕」簽發14。
    • Tag：常見有 issue（控制該網域及其子網域能否由某 CA 簽發憑證，含萬用字元，除非被 issuewild 覆寫）、issuewild（專門控制萬用字元憑證的簽發）、iodef（指定 CA 回報政策違規或不合規簽發嘗試的 URI）14。
    • Value：CA 的識別網域名稱，另可附帶分號分隔的參數，例如 validationmethods（限制驗證方法）、accounturi（限制特定 ACME 帳號）14。
  • 用途：讓網域擁有者指定「哪些 CA 有權為其網域簽發 TLS/SSL 憑證」。預設上任何公開 CA 都能為任何網域簽發；CAA 收斂了這個巨大的信任面，若某 CA 的驗證流程有漏洞，CAA 可阻止它為你的網域簽發14。
  • CA 的檢查流程：每次簽發前，CA 從被請求的確切名稱開始查詢 CAA；若該層無紀錄，則沿網域樹向上逐層檢查，停在第一個找到的 CAA 紀錄14。若查詢發生錯誤（SERVFAIL、逾時），CA 因無法確認是否存在禁止紀錄，故「不得簽發」14。
  • 標準：RFC 865915（取代 RFC 6844）2。

2.12 SVCB 與 HTTPS（服務綁定紀錄，Type 64／65）#

  • 意義：SVCB 為 General-purpose service binding；HTTPS 為 SVCB-compatible type for use with HTTP2。
  • 內容：兩個必填欄位與一個選填欄位16：
    • SvcPriority：此紀錄相對於其他紀錄的優先序，數值越小越優先；值為 0 表示 AliasMode，否則為 ServiceMode16。
    • TargetName：AliasMode 時為別名目標，ServiceMode 時為替代端點；單一 . 有特殊意義（AliasMode 表示服務不可用；ServiceMode 表示使用 owner 名稱）16。
    • SvcParams（選填）：描述替代端點的 key=value 清單（僅 ServiceMode 使用）；已註冊的鍵包含 mandatory、alpn、no-default-alpn、port、ipv4hint、ech（保留給 Encrypted ClientHello）、ipv6hint16。
  • 兩種模式：
    • AliasMode（優先序 0）：把服務別名到 TargetName，主要目的是「在 zone apex 進行別名，因為 CNAME 在此不被允許」；「與 CNAME 不同，AliasMode 紀錄不影響其他 RR 型別的解析，且只適用於特定服務，而非整個網域名稱」16。
    • ServiceMode（優先序大於 0）：把服務的替代端點與其連線參數關聯起來16。
  • 用途：一次 DNS 查詢就提供存取服務的完整指引，達成「改善效能與隱私」（避免先連到次佳的預設伺服器、協商偏好協定、提供相關公鑰）16。其中 ech 參數可傳遞加密 ClientHello 金鑰，ipv4hint 與 ipv6hint 則可省去額外的 A/AAAA 查詢往返16。
  • 標準：RFC 946016。

三、電子郵件相關紀錄#

郵件安全建立在多種 DNS 紀錄的組合之上。以下說明 MX、SPF、DKIM、DMARC 與 PTR 的協作。

  • MX：路由郵件至正確的收件伺服器（見 2.7）9。
  • SPF（以 TXT 發布）：讓網域擁有者指定「哪些電腦被授權以此網域的 envelope-from 位址寄信」17。政策字串以 v=spf1 開頭，後接機制與限定詞；限定詞包含 +（PASS，預設）、?（NEUTRAL）、~（SOFTFAIL）、-（FAIL）17。收件伺服器檢查 SPF，以驗證寄件伺服器是否有權代表該網域寄信17。
  • DKIM（以 TXT 發布）：以密碼學方式簽署外寄郵件。寄件伺服器以私鑰簽署每封郵件，收件伺服器從 DNS 的 TXT 紀錄取得對應公鑰以驗證簽章，證明郵件確實來自所宣稱的網域且未被竄改18。公鑰發布於 selector._domainkey.example.com，以 tag=value 格式呈現（如 v、k、p、s、t）18。
  • DMARC（以 TXT 發布，位於 _dmarc.example.com）：告訴收件伺服器當郵件未通過 SPF 及／或 DKIM 時該如何處理，並要求「對齊（alignment）」，即 From: 標頭中的網域必須與經 SPF 或 DKIM 驗證的網域相符19。主要欄位包含 v、p（none／quarantine／reject）、sp、pct、rua、ruf 等19。
  • PTR：供反垃圾郵件驗證，許多郵件伺服器會檢查寄件 IP 的 PTR 是否與其 HELO/EHLO 主機名稱相符（即 FCrDNS，forward-confirmed reverse DNS）11。
  • TLSA：可將 TLS 憑證綁定到網域，使 SMTP 加密可被驗證（見 5.3）20。

四、DNSSEC 家族#

DNSSEC（Domain Name System Security Extensions）以公開金鑰密碼學為 DNS 加入數位簽章。ICANN 指出：「有了 DNSSEC，被密碼學簽署的並非 DNS 查詢與回應本身，而是 DNS 資料由資料擁有者簽署」21。以下介紹主要 DNSSEC 紀錄。

4.1 DNSKEY（Type 48）#

  • 內容：flags、protocol（有效 DNSSEC 中恆為 3）、algorithm、公開金鑰資料21。
  • 用途：zone 發布其作用中簽章金鑰的公鑰部分，供遞迴解析器取回以驗證該 zone 的資料21。flags 為 256 者為 Zone-Signing Key（ZSK），257 者為 Key-Signing Key（KSK）或 Combined Signing Key（CSK），257 帶有 SEP（Secure Entry Point）位元21。
  • 標準：RFC 403422。

4.2 RRSIG（Type 46）#

  • 內容：被簽署的型別、演算法、labels、原始 TTL、簽章到期與起始時間、key tag、簽署者名稱、簽章值21。
  • 用途：對某一組資源紀錄集（RRset）提供密碼學簽章，證明其完整性與來源真實性；「資料來源驗證讓解析器能以密碼學方式驗證其收到的資料確實來自它相信的來源 zone，完整性保護則讓解析器得知資料自簽署後未在傳輸中被修改」21。
  • 標準：RFC 403422。

4.3 DS（Delegation Signer，Type 43）#

  • 內容：key tag、algorithm、digest type（如 2 為 SHA-256、4 為 SHA-384）、子 zone KSK 的雜湊摘要21。
  • 用途：位於父 zone，是串接子 zone 進入全球信任鏈的關鍵樞紐。「zone 的公鑰就如同 zone 中其他資料一樣被簽署，但它不是由該 zone 的私鑰簽署，而是由父 zone 的私鑰簽署——父 zone 為其子 zone 公鑰的真實性背書」21。
  • 標準：RFC 403422。

4.4 NSEC（Type 47）與 NSEC3（Type 50）#

  • 內容（NSEC）：zone 中依正規順序的下一個存在名稱，以及目前名稱存在哪些型別21。
  • 用途：兩者都提供「已驗證的不存在證明」（authenticated denial of existence）。NSEC 以類似環狀鏈結串列的方式，證明兩個存在的名稱之間不存在任何名稱21。NSEC3 則在建立鏈之前先對名稱做雜湊，以避免 NSEC 的「zone walking」（公開列舉 zone 內所有名稱）隱私問題21。
  • 標準：RFC 403422、RFC 5155（NSEC3）2。

4.5 CDS（Type 59）與 CDNSKEY（Type 60）#

  • 意義：Child DS2；DNSKEY(s) the Child wants reflected in DS2。
  • 用途：兩者都位於子 zone，用於自動化 DS 更新以支援金鑰輪替21。CDS 由子 zone 發布，欄位與 DS 相同，父 zone 營運者可據以自動更新對應的 DS21；CDNSKEY 則發布子 zone 完整的公開 DNSKEY，讓父 zone 可自行推導出 DS 雜湊21。
  • 標準：RFC 73442。

五、加密金鑰與憑證綁定紀錄#

5.1 SSHFP（Type 44）#

  • 意義：SSH Key Fingerprint2。
  • 用途：把 SSH 主機公鑰指紋與主機名稱關聯，讓 SSH 用戶端不需依賴首次連線的 TOFU（trust on first use）提示即可驗證伺服器主機金鑰23。
  • 內容：algorithm、type（雜湊演算法）、指紋23。
  • 與 DNSSEC 關係：SSHFP 的取得「需以 DNSSEC 之類的機制保護，才能建立信任鏈」23。它與 DANE 屬平行機制，並非 DANE 本身的一部分20。
  • 標準：RFC 42552。

5.2 OPENPGPKEY（Type 61）與 CERT（Type 37）#

  • OPENPGPKEY：為特定電子郵件位址發布 OpenPGP 公鑰，實現加密郵件的金鑰自動探索；紀錄名稱以「本地部分的 SHA-256 雜湊」加 ._openpgpkey. 再加網域構成，內容為 base64 編碼的可轉移公鑰20。屬 DANE 協定家族（RFC 7929），同樣需要 DNSSEC 以防金鑰被偽造20。
  • CERT：在 DNS 中存放各種形式的數位憑證（PKIX、SPKI、PGP 等）3。它是 DANE 的通用型前身與替代方案，但並非 DANE 的一部分；DANE 使用帶有 usage、selector、matching 結構化欄位的 TLSA，而非 CERT20。
  • 標準：RFC 7929（OPENPGPKEY）20、RFC 4398（CERT）2。

5.3 TLSA（Type 52）#

  • 用途：把 TLS 伺服器憑證或公鑰與其所在網域關聯，形成「TLSA certificate association」，讓用戶端無須完全依賴傳統 CA 即可驗證 TLS 伺服器20。這是 DANE（DNS-based Authentication of Named Entities）的核心紀錄。
  • 內容：四個欄位20：certificate usage（0 至 3）、selector（0 為全憑證、1 為僅公鑰）、matching type（0 為原始、1 為 SHA-256、2 為 SHA-512）、association data（雜湊或憑證資料）。
  • 與 DNSSEC 關係：「DANE 需要以 DNSSEC 簽署 DNS 紀錄，其安全模型方能運作」，否則攻擊者可偽造 TLSA 紀錄並將用戶端導向惡意憑證20。
  • 標準：RFC 66982。

六、服務探索與其他型別#

6.1 NAPTR（Type 35）#

  • 意義：Naming Authority Pointer2。
  • 內容：六個欄位24：Order（16 位元，較小者先處理）、Preference（同 Order 中較小者優先）、Flags（單一字元，控制重寫的下一步，如 U 表示輸出為 URI、S 表示輸出為需再查 SRV 的網域名稱）、Services（如 E2U+sip）、Regexp（sed 風格取代式）、Replacement（用於取代 regexp 的網域名稱）24。
  • 用途：以正規表達式對網域名稱做重寫，可解析為 URI 或進一步查詢的名稱；最著名的是 ENUM（E.164 電話號碼對 URI 的對應）與 SIP 路由24。電話號碼反轉後以點分隔並加上 e164.arpa 字尾，例如 +1 555 42 42 轉為 2.4.2.4.5.5.5.1.e164.arpa25。
  • 標準：RFC 34032。

6.2 URI（Type 256）#

  • 用途：發布主機名稱到 URI 的對應；欄位包含 priority、weight、target（URI 本身）3。常與 U-NAPTR 搭配，用於服務探索結果需為 URI 而非網域名稱的情境3。
  • 標準：RFC 75532。

6.3 HINFO（Type 13）#

  • 用途：原定義為提供主機的 CPU 型別與作業系統資訊，實務上鮮少用於此目的3。RFC 8482 將其再利用為 ANY 查詢的最小化替代回應，以緩解 DNS 放大攻擊3。
  • 標準：RFC 10354，再利用於 RFC 84822。

6.4 LOC（Type 29）#

  • 用途：以 WGS84 座標表達與某網域名稱相關的地理位置，欄位包含經緯度（度分秒）、海拔、以及主機或子網的實體大小與精度3。因隱私顧慮而鮮少使用3。
  • 標準：RFC 18762。

6.5 其他較新或特殊型別#

  • DELEG（Type 61440，暫時註冊）：傳統 NS 加 glue 委派的可擴充替代方案，借用 SVCB 格式編碼名稱伺服器名稱、其 IP（ipv4hint／ipv6hint）、傳輸協定（如 alpn=dot）等；因位於父 zone 而可被 DNSSEC 簽署，實現簽署過的轉介；並支援類似 CNAME 的 Alias Mode26。
  • DSYNC（Type 66）：用於探索委派同步通知訊息的接收端點，當子 zone 的委派資訊（NS、DS、DNSSEC bootstrap 資料）變更時，父 zone 可據以發送通知26。
  • RESINFO（Type 261）：讓遞迴解析器以結構化 key/value 對發布其能力與政策，例如是否啟用 QNAME minimization（qnamemin）、支援哪些 Extended DNS Error 代碼（exterr）、人可讀資訊的 URL（infourl）等26。
  • WALLET（Type 262）：把網域名稱對應到加密貨幣與公開錢包位址，目標是「減輕 TXT 紀錄被超載使用」的情形26。
  • HHIT（Type 67）與 BRID（Type 68）：與無人機（UAS）遠端識別相關。HHIT 為階層式主機識別標籤，作為可信任的識別碼；BRID 則存放廣播遠端識別資訊26。
  • SPF（Type 99）：曾為 SPF 專用的紀錄型別，但 RFC 7208 因普遍缺乏支援而「停止使用該型別」，SPF 資料現應完全以 TXT 紀錄發布17。
  • NID／L32／L64／LP（Type 104 至 107）：ILNP（Identifier-Locator Network Protocol）相關紀錄，分別對應節點識別碼、32 位元定位器、64 位元定位器及定位器指標2。

七、易誤解的重要規則#

7.1 CNAME 不得與其他紀錄並存#

如 2.5 所述，一個名稱若存在 CNAME，則不得有其他型別（RFC 2181 下的例外為 DNSSEC 的 SIG、NXT、KEY）6。RFC 1034 亦規定「若某節點存在 CNAME，則不應存在其他資料；這確保正式名稱與其別名的資料不會不同」27。

7.2 CNAME 不得放在 zone apex#

Zone apex（例如 example.com）是 zone 中唯一「必須」攜帶運作所需紀錄（SOA、NS，若處理郵件則還有 MX）的位置。若在 apex 放 CNAME，上述關鍵紀錄都會被覆寫，使 zone 損壞且無法解析27。嚴格的名稱伺服器（如 BIND 9）會直接拒絕載入該 zone；寬鬆的管理面板可能允許儲存，但結果是郵件投遞失敗、解析時好時壞、或網域實質上無法解析27。

7.3 MX 與 NS 不得指向 CNAME#

RFC 2181 明文規定 MX 與 NS 紀錄「絕不可指向 CNAME 別名」27。RFC 2181 解釋：額外區段處理不包括 CNAME 紀錄，因此若在 NS 或 MX 值中使用別名，就無法同時回傳其位址紀錄，導致額外查詢甚至失敗6。

7.4 因應方案：CNAME Flattening、ALIAS、ANAME 與 SVCB#

  • CNAME Flattening（Cloudflare）：在儀表板於 apex 建立 CNAME，但對外「不」以 CNAME 形式提供，而是由供應商在伺服器端追隨目標、解析為 A/AAAA 後直接回傳 IP27。
  • ALIAS（Amazon Route 53）：專有紀錄，把 apex 指向 AWS 資源或其他 Route 53 紀錄，內部解析後以目標位址回應27。
  • ANAME（NS1 等）：更通用的 apex 別名，可指向任意外部主機名稱；曾有 IETF 草案但未達共識，已被 RFC 9460（SVCB／HTTPS）取代27。
  • SVCB／HTTPS AliasMode：RFC 9460 標準化的 apex 別名途徑（見 2.12）16。
  • 上述方案共同的取捨：供應商快取解析結果造成的新鮮度落差、依供應商解析器位置決定回應位址（可能把使用者導向非最佳節點）、非標準線格式導致可攜性差27。

十、批判性來源反思#

撰寫本文時，對來源做了以下評估：

  1. 標準文件優先：欄位定義與限制（CNAME 共存規則、SOA 欄位語意、SRV 欄位）皆以 IETF RFC 原文為準，因 RFC 是這些協定的規範性來源。IANA 註冊表則作為型別代碼與指派狀態的權威依據2。
  2. 時間性與暫時性註冊：IANA 註冊表中 DELEGPARAM（54）與 DELEG（61440）標示為暫時註冊，屬草案階段的實驗性指派，未來可能變動；本文僅將其列為「較新與特殊型別」並標明其時限226。
  3. 商業來源的立場：部分說明（CNAME Flattening、ALIAS、ANAME）來自供應商說明，這些內容本質上在推廣各家專有方案，其技術描述可與 RFC 交叉印證，但「哪個方案較優」的評價具有商業立場，本文僅陳述技術事實與共通取捨27。
  4. 資料完整性：IANA 註冊表中 SPF、UINFO、UID、GID、UNSPEC、NID、L32、L64、LP 等型別的「Meaning」欄位為空白；本文對這些未憑推測填補，而是如實標示註冊表未提供意義，或另以 RFC 補充 ILNP 相關型別之用途2。
  5. 未查證事項：本文未逐一驗證每個 RFC 的最新 obsoletes 狀態（例如 CAA 由 RFC 8659 取代 RFC 6844）；此類版本關係以 IANA 註冊表所列參考為準，讀者若需精確版次仍應查閱 IETF 官方文件。
