00734_webapp-authn-to-auth-proxy-sso-migration

既有自建登入（AuthN）的 Web 應用，如何遷移至 Auth Proxy 微服務架構以實現 SSO#

摘要#

許多 Web 應用在早期自行實作登入功能：自己的使用者資料表、自己的密碼雜湊、自己的 session cookie、自己的登入頁面。當這類應用要被放進以「Auth Proxy（身分感知反向代理，identity-aware proxy）」為核心的微服務架構，並與其他服務共用單一登入（Single Sign-On，SSO）時，真正的困難不在於「如何架一層代理」，而在於兩套獨立的身分層如何調和：舊應用有自己的 session 與帳號來源，代理帶來的是另一套 session 與帳號來源。

本報告先定義問題，再拆解 Auth Proxy 與 Forward Auth 的技術契約，接著提出以「絞殺者模式（Strangler Fig）」為框架的分階段遷移路徑，並針對「既有使用者資料如何延續」「雙重 session 與單一登出」「標頭偽造與 Cookie 網域的安全性取捨」三個關鍵難題給出具體作法與工具對照。本報告為獨立文件，讀者無需任何前置背景。

1. 背景與問題定義#

1.1 舊架構長什麼樣子#

一個「已經自己做完 AuthN」的典型 Web 應用具有以下四個特徵：

  • 應用自己維護使用者資料表（帳號、電子郵件、密碼雜湊、角色）。
  • 應用自己比對密碼雜湊（可能是 bcrypt、PBKDF2、Argon2，或更舊的 MD5、SHA1）。
  • 應用自己簽發 session cookie，並在自己的資料庫或記憶體中保存 session 狀態。
  • 應用自己提供登入頁與登出端點。

換句話說，這個應用本身就是一個既小又完整的身分提供者（IdP），只是它只服務自己。

flowchart LR
    B[瀏覽器] -->|登入表單 帳號密碼| L[應用內建登入頁]
    L -->|比對密碼雜湊| DB[(應用自有的<br/>使用者表)]
    L -->|簽發 session cookie| B
    B -->|帶 session cookie| A[應用本體]
    A -->|查 session| SS[(應用自有的<br/>session 儲存)]
    A --> DB

1.2 目標架構長什麼樣子#

Auth Proxy 架構把「誰是使用者」這件事從應用內部抽離到邊緣（edge）。所有請求先經過一個身分感知代理，代理在放行前完成認證，並把「已認證的使用者身分」以標頭（header）形式注入送往後端的請求1234。

flowchart LR
    B[瀏覽器] -->|請求| P[Auth Proxy<br/>Forward Auth]
    P -->|子請求：這個人可以進來嗎| IDP[授權服務<br/>Authelia / Keycloak / oauth2-proxy]
    IDP -->|2xx + 身分標頭| P
    P -->|Remote-User / X-Auth-Request-*| A1[微服務 A]
    P -->|Remote-User / X-Auth-Request-*| A2[微服務 B]
    P -->|Remote-User / X-Auth-Request-*| A3[舊應用 C]

1.3 真正的衝突點#

問題在於：舊應用 C 同時保有自己的 session 與登入頁。於是使用者會體驗到兩個彼此獨立的身分層：SSO 這一層說「你已登入」，但舊應用那一層仍在自己的 cookie 上做判斷。若沒有刻意調和，就會出現「已經從 SSO 登出、卻仍能操作舊應用」這種安全缺口。

1.4 目標架構必須回答的四個問題#

2. Auth Proxy 與 Forward Auth 架構#

2.1 核心契約#

Forward Auth 的共同模式是：代理在轉發請求前，先對授權服務發出一次內部請求；授權服務回應 2xx 代表放行，其他狀態碼代表拒絕1234。放行時，授權服務可在回應中附帶身分標頭，代理再把這些標頭複製到送往後端的請求上23。

2.2 各代理的實作差異#

nginx auth_request（1.5.4+，需 --with-http_auth_request_module）#

nginx 官方模組 ngx_http_auth_request_module 會在處理主請求前發出子請求（subrequest）1。規則如下1：

  • 子請求回 2xx → 放行。
  • 回 401 → 拒絕，且把子請求回應中的 WWW-Authenticate 傳給客戶端。
  • 回 403 → 拒絕。
  • 其他狀態碼 → 視為錯誤。

auth_request_set $var $upstream_http_<name>; 可把子請求回應的標頭存成主請求的 nginx 變數；由於子請求不該攜帶原始請求主體，慣例會搭配 proxy_pass_request_body off; 與 proxy_set_header Content-Length "";1。

以下是 Authelia 官方文件中的標準寫法5：

# 伺服器層級：宣告授權端點
set $upstream_authelia http://authelia:9091/api/authz/auth-request;

# 內部授權端點（外部無法直接存取）
location /internal/authelia/authz {
    internal;
    proxy_pass $upstream_authelia;
    proxy_set_header X-Original-Method $request_method;
    proxy_set_header X-Original-URL    $scheme://$http_host$request_uri;
    proxy_set_header X-Forwarded-For   $remote_addr;
    proxy_set_header Content-Length    "";
    proxy_set_header Connection        "";
    proxy_pass_request_body            off;
}

# 受保護的應用
location / {
    auth_request /internal/authelia/authz;
    auth_request_set $user   $upstream_http_remote_user;
    auth_request_set $groups $upstream_http_remote_groups;
    auth_request_set $mail   $upstream_http_remote_email;
    auth_request_set $name   $upstream_http_remote_name;

    proxy_set_header Remote-User   $user;
    proxy_set_header Remote-Groups $groups;
    proxy_set_header Remote-Email  $mail;
    proxy_set_header Remote-Name   $name;

    # 未認證時導向登入頁
    auth_request_set $redirection_url $upstream_http_location;
    error_page 401 =302 $redirection_url;

    proxy_pass http://app_backend;
}
Traefik ForwardAuth#

Traefik 的 ForwardAuth 中介軟體同樣以 2XX 代表放行；非 2XX 時，把授權伺服器的回應直接回給客戶端2。它會自動附上 X-Forwarded-Method、X-Forwarded-Proto、X-Forwarded-Host、X-Forwarded-Uri、X-Forwarded-For2。

主要設定欄位包含：address、authResponseHeaders（複製到後續轉發請求，同名會被覆蓋）、authResponseHeadersRegex、authRequestHeaders、forwardBody、maxBodySize、maxResponseBodySize、headerField、preserveRequestMethod、preserveLocationHeader、addAuthCookiesToResponse、authSigninURL2。舊的 trustForwardHeader 已棄用，應改用進入點（entrypoint）層級的 forwardedHeaders.trustedIPs2。

Caddy forward_auth#

Caddy 的 forward_auth 是 reverse_proxy 加上 handle_response 的語法糖3：

forward_auth [<matcher>] [<upstreams...>] {
    uri <to>
    copy_headers <fields...>
}

它固定使用 GET、改寫 URI，並附上 X-Forwarded-Method 與 X-Forwarded-Uri3。2xx 放行；其他狀態碼拒絕，並把授權伺服器的回應複製回客戶端。copy_headers 支援 Before>After 改名語法3。

Envoy ext_authz#

Envoy 的 external authorization 過濾器支援 HTTP 與 gRPC 兩種介面4：

  • gRPC：實作 Authorization.Check(CheckRequest) → CheckResponse4。

allowed_upstream_headers 與 allowed_upstream_headers_to_append 決定哪些授權回應標頭會被複製到上游請求；authorization_response.allowed_client_headers 決定哪些回傳給客戶端；可用 x-envoy-auth-headers-to-remove 移除不想要的標頭4。安全相關設定：failure_mode_allow 預設 false、status_on_error 預設 403、shadow_mode4。另有一組統計指標：ok / denied / error / disabled / failure_mode_allowed / invalid4。

ingress-nginx（Kubernetes）#

ingress-nginx 以 annotation 實作外部認證：auth-url、auth-signin、auth-response-headers、auth-method、auth-request-redirect、auth-snippet、auth-always-set-cookie、auth-cache-key、auth-cache-duration（預設 200 202 401 5m）、auth-keepalive*、auth-proxy-set-headers、enable-global-auth6。同樣是 2xx 放行，其他狀態碼拒絕並可導向登入6。

3.1 Authelia 的標頭#

3.4 標頭模式的根本風險#

這些標頭只能存在於代理與後端之間。Authelia 官方明確警告：Trusted Header SSO 所使用的標頭屬於內部使用，絕不可被送回瀏覽器，也絕不可接受來自客戶端的同名標頭10。Django 官方文件同樣要求：採用 Remote User 認證的部署，不可部署在客戶端能自行提供該標頭的位置11。

4. 將「已有自建登入」的應用接上代理：絞殺者模式分波次遷移#

絞殺者模式的核心是：先在新舊系統之間插入一層間接（代理 / 閘道），再以薄切片（thin slice）逐步把功能與流量從舊系統搬到新系統，最後讓舊系統退場12。以下六個波次是把該模式套用到本情境的具體化。

flowchart LR
    W1[波次1<br/>代理上線前<br/>舊登入仍為唯一入口] --> W2[波次2<br/>代理置前<br/>逐路由豁免]
    W2 --> W3[波次3<br/>應用信任注入標頭<br/>雙軌並存]
    W3 --> W4[波次4<br/>翻轉真相來源<br/>IdP 聯邦既有使用者表]
    W4 --> W5[波次5<br/>廢除舊登入頁<br/>單一登出]
    W5 --> W6[波次6<br/>退役舊 session 表]

波次 1：盤點與準備（代理尚未接管流量）#

  • 盤點應用實際使用的登入相關路由：登入頁、登出端點、密碼重設、API 端點、健康檢查、靜態資源、Webhook。
  • 盤點應用如何取得身分：cookie 名稱、session 儲存位置、PDF、附表。
  • 確認代理與應用之間的網路是否只有代理能到達應用。這是後續所有標頭信任的前提。Gitea 官方文件直接寫明「Gitea 必須只能經由代理存取」13。
  • 決定 Cookie 網域策略（見第 7 節）。

波次 2：代理置前，逐路由豁免#

把代理接到應用前面，但先不要讓應用改變任何行為。此時應用仍在自己的 cookie 上判斷身分，代理只是多了一層認證。為了不擋掉應用自己的登入流程，必須把登入相關路徑設為豁免：

  • oauth2-proxy：--skip-auth-route=GET=/login、--skip-auth-route=POST=/login、--skip-auth-route=GET=/logout8。
  • Authelia：以 rules 的 resources / methods 搭配 bypass 策略達成等效效果14。

此階段的目標是可逆：一旦出現問題，把代理移開即可回到原狀。

波次 3：應用改為信任注入標頭，雙軌並存#

這是風險最高、也最關鍵的一步。應用要在「沒有注入標頭時仍用自己的登入」與「有注入標頭時改信任代理」之間取得平衡。

跨語言通用模式：在認證中介層（middleware）中按以下順序判斷：

  1. 請求是否帶有可信的注入標頭（且來源 IP 在代理白名單內）？
  2. 是 → 以該標頭指定的身分建立／更新本機 session。
  3. 否 → 退回原有的本機登入判斷。

具體框架實作：

  • Django：使用 RemoteUserMiddleware 或 PersistentRemoteUserMiddleware 搭配 RemoteUserBackend / AllowAllUsersRemoteUserBackend11。注意事項11：

    • 必須放在 AuthenticationMiddleware 之後。
    • AUTHENTICATION_BACKENDS 必須保留 ModelBackend 作為後備，否則所有人都無法登入。
    • RemoteUserMiddleware 會在每個請求重檢標頭；標頭消失時登出並使 session 失效。PersistentRemoteUserMiddleware 則保留 session。
    • 預設 header = "REMOTE_USER" 是 WSGI 環境變數鍵，客戶端無法偽造；但在 ASGI 下代理必須負責剝除它。
    • 自訂標頭（例如 HTTP_AUTHUSER）必須由代理剝除，因為 X-Auth-User 與 X-Auth_User 都會正規化為 HTTP_X_AUTH_USER。

  • Grafana：[auth.proxy] 區段提供 enabled、header_name（預設 X-WEBAUTH-USER）、header_property（username 或 email）、auto_sign_up、sync_ttl（預設 15 分鐘）、whitelist（IP / CIDR，防止偽造）、headers（映射名稱 / 角色 / 電子郵件 / 群組等額外標頭）、enable_login_token（預設 false）、headers_encoded15。Grafana 會把使用者快取進自己的資料庫，之後每 sync_ttl 重新同步一次15。

  • Gitea：ENABLE_REVERSE_PROXY_AUTHENTICATION（預設 false）、ENABLE_REVERSE_PROXY_AUTHENTICATION_API（預設 false）、REVERSE_PROXY_AUTHENTICATION_USER（預設 X-WEBAUTH-USER）、REVERSE_PROXY_AUTHENTICATION_EMAIL（預設 X-WEBAUTH-EMAIL）、REVERSE_PROXY_AUTHENTICATION_FULL_NAME、ENABLE_REVERSE_PROXY_AUTO_REGISTRATION（預設 false）、REVERSE_PROXY_TRUSTED_PROXIES（預設 127.0.0.0/8,::1/128）、REVERSE_PROXY_LIMIT（預設 1）、REVERSE_PROXY_LOGOUT_REDIRECT1316。

波次 4：翻轉真相來源（讓 IdP 聯邦既有使用者表）#

這是本報告最重要的建議。不要搬遷密碼雜湊，直接讓 IdP 反向查詢既有資料庫。

Keycloak 的 User Storage SPI 正好為此設計17：

  • 核心介面：UserStorageProvider（含 preRemove 生命週期）、UserStorageProviderFactory。
  • 能力介面：UserLookupProvider（登入必需）、UserQueryProvider、UserRegistrationProvider、UserBulkUpdateProvider。
  • 憑證驗證：CredentialInputValidator（supportsCredentialType、isConfiguredFor、isValid）；讀取時不可更新則使用 CredentialInputUpdater 並拋出 ReadOnlyException。
  • 註冊方式：於 META-INF/services/org.keycloak.storage.UserStorageProviderFactory 宣告。
  • 執行模型：provider 實例每個交易（transaction）建立一次，使用後呼叫 close()17。
  • 官方範例：user-storage-simple、user-storage-jpa17。

聯邦（federated）與匯入（import）的差異17：

Keycloak 官方文件明確支持漸進遷移：「若您正把 Keycloak 遷為官方使用者儲存並要淘汰舊的外部儲存，您可以慢慢把應用遷移到 Keycloak；當所有應用都遷移完畢，再解除匯入使用者的連結，並讓舊的 legacy 外部儲存退場。」17

同一原則也適用於 LDAP / AD 聯邦18：

  • Edit Mode：READ_ONLY / WRITABLE / UNSYNCED；Import Users 開關。
  • 「Keycloak 從不匯入密碼。密碼驗證一律在 LDAP 伺服器上進行。」18
  • 同步設定：fullSyncPeriod、changedSyncPeriod、batchSizeForSync（預設 1000）。
  • 連線：Connection URL（以空白分隔可做故障轉移）、Connection Timeout（預設 5000 ms）、Priority。
  • 注意：provider 之間沒有故障轉移，一個 provider 失敗會直接取消該次呼叫18。

若真的必須遷移密碼雜湊（不建議，但可行）：Keycloak 的 PasswordHashProvider 提供 policyCheck、encodedCredential、verify 三方法17。內建支援演算法17：

Keycloak 沒有內建 bcrypt，若舊系統用 bcrypt，必須自行實作 PasswordHashProvider，或在 User Storage SPI 中以 CredentialInputValidator 直接在舊資料庫上驗證（後者是本報告建議的路線）。預設演算法可用 --spi-password-hashing--provider-default=<alg> 指定17。

OWASP 對舊雜湊升級的建議19（若走遷移路線時適用）：

  • Argon2id 優先（例如 m=19456、t=2、p=1 等已接受的參數組合）；scrypt 為後備；bcrypt 僅供 legacy（cost ≥ 10，且有 72 位元組長度限制）。
  • PBKDF2-HMAC-SHA256 建議 600,000 次；SHA512 建議 220,000 次；SHA1 建議 1,400,000 次（僅 legacy）。
  • 升級手法：強制到期重設、分層雜湊（如 bcrypt(md5(password))）、於下次成功登入時重新雜湊、於下次認證時提高 work factor、過渡期允許混合演算法、以 PHC 字串格式保存演算法與參數。

波次 5：廢除舊登入頁，實作單一登出#

  • 移除或停用舊登入頁路由，讓所有未認證請求都由代理導向 IdP。
  • 啟用單一登出，見第 6 節。
  • 驗證「從 IdP 登出後，舊應用是否立即失效」。

波次 6：退役舊 session 表與舊程式碼#

  • 確認無任何流量走舊 session 路徑後，才移除舊的 session 儲存與登入程式碼。
  • 保留舊密碼欄位一段觀察期，以備回退。

5. 網路與信任邊界：標頭信任的成立條件#

注入標頭只有在「客戶端無法繞過代理直接觸及後端」時才有意義。以下是可操作的檢查項。

5.1 應用只能經由代理存取#

  • 網路層：以防火牆 / 安全群組 / Kubernetes NetworkPolicy 限制後端只接受來自代理的流量。
  • Gitea 官方明言「Gitea 必須只能經由代理存取」13；Azure AD Application Proxy 官方亦要求「採用標頭式認證的應用，其存取應限制為僅來自連接器的流量」20。

5.2 設定應用的信任代理清單#

以代理的 TCP 來源位址設定應用（或 IdP）的可信 IP14。實務細節14：

  • Docker 環境：為代理容器指定靜態 IP，不要信任整個 Docker 網段。
  • Kubernetes 環境：改用服務網格（service mesh）處理。
  • 驗證測試：對一條「該 IP 可 bypass」的規則，偽造送出 X-Forwarded-For: 169.254.1.2。若設定正確應得到 302（被要求登入）；若得到 200 則代表設定有漏洞14。

5.3 東－西向（service-to-service）的身分驗證#

邊緣的 forward auth 只處理南北向流量。服務之間的身分屬於東－西向問題，Istio 提供對應機制21：

  • PeerAuthentication：設定 mtls.mode 為 STRICT / PERMISSIVE / DISABLE，可精細到 portLevelMtls21。
  • SPIFFE 身分由 Kubernetes Service Account 推導；istiod 的 CA 簽署 CSR；Istio agent 透過 SDS 分送憑證並自動輪替21。
  • RequestAuthentication：以 jwtRules（issuer + jwksUri）驗證 JWT。無效 token 會被拒絕，未帶 token 的請求預設被允許21。
  • AuthorizationPolicy：selector、action（ALLOW / DENY / CUSTOM）、rules.from/to/when；評估順序為 CUSTOM → DENY → ALLOW21。requestPrincipals: ["*"] 表示必須有有效 JWT；可依 request.auth.claims[iss] 等宣告條件做匹配21。

5.4 跨服務的使用者身分傳遞#

當服務 A 需要以「使用者本人的身分」呼叫服務 B 時，RFC 8693 Token Exchange 是標準作法22：

  • grant_type=urn:ietf:params:oauth:grant-type:token-exchange22。
  • 參數：subject_token、subject_token_type、actor_token、actor_token_type、resource、audience、scope、requested_token_type22。
  • Token 型別 URN：access_token、refresh_token、id_token、saml1、saml2、jwt22。
  • 假冒（impersonation）與代理（delegation）的差異由 act 宣告表達代理鏈22。
  • 典型微服務用法：前端資源伺服器把使用者 token 換成一個範圍更窄的 token，再交給後端服務22。

若服務 B 只拿到不透明（opaque）token，則使用 RFC 7662 Token Introspection23：POST 表單編碼，必填 token，可選 token_type_hint；回應必含 active，並可含 scope、client_id、username、token_type、exp、iat、sub、aud、iss、nbf、jti23。內省端點必須使用 TLS 並要求授權23。

6. 雙重 Session 與單一登出#

6.1 問題的樣貌#

代理有自己的 session（例如 Authelia 的 cookie），應用也有自己的 session。兩者的生命週期不同步，會產生三種症狀：

  1. 從 SSO 登出後，直接訪問應用仍然可用（因為應用 cookie 還在）。
  2. 應用登出後，SSO 仍處於登入狀態，再次訪問應用會「被自動登入」，使用者困惑。
  3. 權限變更（角色調整、停用帳號）不會即時反映到應用。

6.2 解決方案一：後通道登出（Back-Channel Logout）#

OIDC Back-Channel Logout 1.0（Final，2023-12-15）讓 IdP 在 session 結束時，以伺服器對伺服器的方式通知每個 RP24：

  • 註冊參數：backchannel_logout_uri、backchannel_logout_session_required24。
  • 通知內容是一個 Logout Token JWT，含 iss、aud、iat、exp、jti，以及內容含 http://schemas.openid.net/event/backchannel-logout 的 events；還要包含 sub 與 / 或 sid24。
  • 必須不含 nonce；typ 建議為 logout+jwt24。
  • 驗證步驟定義於規格 §2.6；驗證失敗時應回 40024。

這是本情境最可靠的解法，因為它不依賴瀏覽器行為。

6.3 解決方案二：RP 發起的登出（RP-Initiated Logout）#

OIDC RP-Initiated Logout 1.0（Final，2022-09-12）25：

  • end_session_endpoint：IdP 提供的登出端點。
  • id_token_hint（建議提供）。
  • post_logout_redirect_uri：必須與預先註冊的 post_logout_redirect_uris 完全相符。
  • state、client_id。

此機制由前端觸發，適合「使用者主動按登出」的情境。

6.4 解決方案三：前通道登出（Front-Channel Logout）#

OIDC Front-Channel Logout 1.0（Final，2022-09）由 IdP 以隱藏 iframe 載入各 RP 的登出 URI26。可靠性較低，且會被瀏覽器的第三方 Cookie 封鎖機制破壞。

6.5 解決方案四：Session Management#

OIDC Session Management 1.0 讓 RP 的 iframe 與 OP 的 iframe 以 postMessage 輪詢，使用 client_id 與 session_state，並以 prompt=none 重新驗證27。輪詢有成本，實務上常作為前通道登出的補充。

6.6 應用仍保有自己 session 時的收斂策略#

若短期內無法完全移除應用自有的 session，建議：

  • 應用 session 的有效期不得長於 IdP session 的有效期。
  • 應用 session 應記錄簽發時所用的 IdP session id（sid），以便後通道登出時精準撤銷。
  • 應用應在每個請求（或短期快取內）確認 IdP session 仍有效。
  • Django 的 RemoteUserMiddleware 的「每次請求重檢標頭、標頭消失即登出」行為11，正是這個策略的現成實作。

6.7 前端最佳實務（BFF）#

draft-ietf-oauth-browser-based-apps-27（2026-07-06）是本主題的 Best Current Practice28：

  • 隱含流程（implicit）MUST NOT 使用（§7.2）28。
  • BFF（Backend for Frontend）模式 §6.1：使用機密客戶端（confidential client），token 只保存在伺服器端，瀏覽器只持有 cookie session28。
  • Cookie 要求：Secure 與 HttpOnly MUST；SameSite=Strict SHOULD；SHOULD NOT 設定 Domain；SHOULD 使用 __Host-Http- 前綴；客戶端 session 應加密28。
  • CSRF 防護為 MUST（§6.1.3.3）28。
  • Session 生命期應與 refresh token 生命期對齊（§6.1.2.2）28。

7. Cookie、SameSite 與網域：SSO 能否成立的前提#

7.1 Cookie 屬性的正確理解#

  • SameSite 有 Strict、Lax、None；Lax 自 Chrome 80 起是瀏覽器預設值，且存在一個寬鬆變體（"Lax-allowing-unsafe"），允許在設定後 2 分鐘內進行跨站 POST2930。
  • SameSite=None 必須搭配 Secure29。
  • Domain 開頭的點會被忽略；省略 Domain 會得到主機專屬 cookie，設定 Domain 則會與所有子網域共用29。
  • 值不可為公共後綴（public suffix）29。
  • __Secure- 前綴需要 Secure 且走 HTTPS；__Host- 前綴需要 Secure、Path=/ 且不可設 Domain29。

7.2 網域與 SameSite 的實務取捨#

Authelia 的 session cookie 預設 same_site 為 lax（過去為 none），並明確警告 strict「在許多使用情境下無法運作」31。

7.3 會話管理安全要求#

OWASP Session Management Cheat Sheet 的相關要求32：

  • Session ID 需至少 64 bits 的 CSPRNG 熵（驗證用 token 需至少 128 bits）。
  • Secure 與 HttpOnly 為必要。
  • 應明確設定 SameSite（偏好 Strict），且絕不在未搭配 Secure 時使用 None。
  • 不要設定 Domain（跨子網域暴露 session）；也不要把不同安全等級的應用放在同一網域。
  • 建議使用 __Host- 前綴；只有在確實需要跨子網域共用時才使用 __Secure-。
  • 閒置逾時：高價值 2–5 分鐘、低風險 15–30 分鐘；絕對逾時 4–8 小時。
  • 任何權限變更（登入、改密碼、角色變更）都必須更新 session ID，以防 session fixation。
  • 登出必須在伺服器端失效，並附加 Clear-Site-Data 與 Cache-Control: no-store。
  • 記錄 session ID 的加鹽雜湊，絕不記錄原始值。

注意：該 Cheat Sheet 未提供明確的 SSO 指引，但其關於 Domain 的警告與 SSO 直接相關——這正是 SSO 便利性與安全性之間的張力所在。

7.4 Authelia session 設定要點#

Authelia 的 session 設定包含31：session.secret、session.name（預設 authelia_session）、session.same_site、session.inactivity（5m）、session.expiration（1h）、session.remember_me（1M）；每個 cookie 可設定 domain、authelia_url、default_redirection_url、name、same_site、inactivity、expiration、remember_me；session.redis 可讓 Authelia 變成無狀態 / 高可用31。domain 必須是 authelia_url 主機名稱的後綴或相等，且不可為公共後綴或 localhost31。

Authelia 存取控制規則的重點14：default_policy 預設為 deny；rules[] 可依 domain / domain_regex、policy（deny|bypass|one_factor|two_factor）、subject（巢狀清單表示 AND/OR）、networks、methods、resources、query 匹配；首個匹配者勝出14。

7.5 其他身分傳遞機制的安全前提#

  • RFC 7636 PKCE：code_verifier 為 43–128 個未保留字元、≥256 bits 熵；code_challenge_method 支援 plain（SHOULD NOT）與 S256（MTI，必須實作）33。範例：verifier dBjftJeZ4CVP-mB92K27uhbUJU1p1r_wW1gFWFOEjXk 對應 challenge E9Melhoa2OwvFrEMTJguCHaoeK1t8URWbuGJSstw-cM33。
  • OAuth 2.0 安全 BCP（draft-ietf-oauth-security-topics-29，2024-06-03）34：
    • 公開客戶端 MUST 使用 refresh token 輪替或寄送者約束（sender-constrained）的 refresh token（§2.2.2、§4.14.2）。
    • 存取 token 建議使用 mTLS（RFC 8705）或 DPoP（RFC 9449）做寄送者約束（§2.2.1、§4.10.1）。
    • 洩漏途徑：§4.1 重導 URI 驗證、§4.2 Referer、§4.3 瀏覽器歷史、§4.9 偽造 / 被攻陷的資源伺服器。
    • PKCE 對公開客戶端為 MUST、對機密客戶端為 RECOMMENDED（§2.1.1）；AS MUST 支援 PKCE，且 MUST 防禦 PKCE 降級攻擊（§4.8）。
    • 該文件沒有 session 管理 / SSO 登出的章節；僅 §4.14.2 提到 AS 可在登出或改密碼時撤銷 refresh token。請勿推論其涵蓋 SSO 登出。
  • 憑證填充防禦：MFA 是最有效的手段（Microsoft 指出約可防範 99.9% 的帳號盜用），其餘包含 CAPTCHA、IP 緩解、裝置 / 連線指紋（JA3）、不可預測的使用者名稱、多步驟登入、要求 JS、劣化處理、通知使用者；另可檢查洩漏密碼（Pwned Passwords，ASVS 2.1.7）35。

8.4 依據情境的選擇建議#

  • 舊應用願意改程式碼：Keycloak（User Storage SPI 聯邦舊資料庫）+ 任一 Forward Auth 代理。這是最乾淨的路線。
  • 舊應用不願或不能改程式碼：Cloudflare Access 或 Azure AD Application Proxy（標頭式 SSO），把身分以標頭 / JWT 方式餵給應用。
  • 已經使用 Kubernetes：ingress-nginx annotation 或 Istio（RequestAuthentication + AuthorizationPolicy），並以 PeerAuthentication 處理東－西向 mTLS。
  • 只需輕量邊緣認證：Authelia 或 oauth2-proxy，設定與維運成本最低。
  • 需要漸進切換：oauth2-proxy 的 --skip-auth-route 是最直接的工具。

9. 風險與常見陷阱#

flowchart TD
    RISK[風險] --> R1[標頭偽造<br/>應用可被直連]
    RISK --> R2[雙重 session<br/>登出不同步]
    RISK --> R3[Cookie 網域放大<br/>子網域可讀 session]
    RISK --> R4[SameSite 設定錯誤<br/>OIDC 重導中斷]
    RISK --> R5[密碼雜湊搬遷<br/>bcrypt 無內建支援]
    RISK --> R6[工具維護停滯<br/>如 Ory Oathkeeper]
  1. 標頭偽造：最嚴重且最常見。若應用可被直接觸及，攻擊者只要送出 Remote-User: admin 就能冒充任何人。對策：網路隔離 + 信任 IP 清單 + 以 X-Forwarded-For 偽造測試驗證141320。
  2. 雙重 session：見第 6 節。對策：後通道登出 + 應用 session 不得長於 IdP session。
  3. Cookie 網域放大：為跨子網域 SSO 而提升 Domain，等於把 session 暴露給所有子網域32。對策：嚴格管理子網域，或改用 __Host- 前綴（但代價是無法跨子網域共用）。
  4. SameSite 設定錯誤：Strict 會打斷 OIDC 重導流程；None 未搭配 Secure 會被瀏覽器拒絕3129。
  5. 密碼雜湊搬遷：Keycloak 無內建 bcrypt17。對策：優先採聯邦查詢而非雜湊搬遷；真的必須搬遷時，依 OWASP 的漸進升級手法處理19。
  6. 工具維護活躍度：Ory Oathkeeper 的最新版本日期明顯落後於同類專案，選型時應納入評估。
  7. 相依於瀏覽器行為的登出機制：前通道登出與 Session Management 依賴 iframe / 第三方 Cookie，會被瀏覽器政策破壞2627。對策：以伺服器對伺服器的後通道登出為主24。

10. 結論與建議路徑#

10.1 核心結論#

  1. Auth Proxy 解決的是邊緣認證，不是應用內部的身分模型。 舊應用仍會有自己的 session，兩者必須刻意調和。
  2. 最乾淨的橋接方式是讓 IdP 聯邦既有使用者資料庫，而不是搬遷密碼雜湊。Keycloak 的 User Storage SPI（搭配 CredentialInputValidator）與 LDAP 聯邦都支援「舊系統仍是真相來源」，且官方明確支持漸進遷移1718。
  3. 分階段上線（絞殺者模式）是必要條件，不是加分項。過渡期必須能讓兩套登入並存，並可隨時回退。
  4. 標頭信任只有在網路層保證應用不可被直連時才成立101113。
  5. 單一登出必須以伺服器對伺服器的後通道登出實作，不可依賴瀏覽器端機制24。

10.2 建議的落地順序#

10.3 給不同情境讀者的最短路徑#

  • 想最快看到成效：Authelia（或 oauth2-proxy）+ nginx auth_request，用 bypass 規則或 --skip-auth-route 保住舊登入。
  • 想一次到位：Keycloak（User Storage SPI 聯邦舊資料庫）+ Traefik ForwardAuth 或 Envoy ext_authz。
  • Kubernetes 環境：ingress-nginx 外部認證 annotation + Istio 東－西向 mTLS。
  • 舊應用完全不能改：Cloudflare Access 或 Azure AD Application Proxy 的標頭式 SSO。
