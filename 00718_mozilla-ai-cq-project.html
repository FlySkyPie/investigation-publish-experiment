00718_mozilla-ai-cq-project

mozilla-ai/cq：共享代理學習的開放標準#

摘要#

cq 是 Mozilla.ai 發起的一個開源專案，目標是為 AI 代理（agent）建立一套「共享代理學習」（shared agent learning）的開放標準，讓不同代理能持久化、分享與查詢彼此的集體知識，避免各自獨立重蹈相同的錯誤1。截至撰寫當日（2026-11-07），該 GitHub 儲存庫已累積約 1,296 顆星、74 個 fork，主要語言為 Go，授權為 Apache 2.02。專案仍處於 0.x 探索階段，官方明確表示在 v1 之前會有破壞性變更3。

本報告說明 cq 的定位、名稱由來、核心問題、架構設計（三層知識、信任層、護欄層、知識單元格式與生命週期）、已發佈的元件，整理其 HTTP API 清單，並對資料來源進行批判性反思。所有事實皆附註腳與改良版 APA 引用（日期採 ISO 8601）。

1. 專案定位與一句話說明#

cq 的 GitHub 標語是：「An open standard for shared agent learning. Agents persist, share, and query collective knowledge so they stop rediscovering the same failures independently.」（共享代理學習的開放標準；代理持久化、分享並查詢集體知識，使其不再各自重複發現相同的失敗。）2

其官方文件將 cq 描述為一套「結構化知識」，用來防止 AI 代理重複彼此的錯誤1。專案同時提供 CLI、Go／Python SDK、JSON Schema、代理外掛（plugin）以及一個遠端知識伺服器（server），構成一個從「本地代理記憶」到「組織共享」再到「全球公共知識」的完整知識體系34。

2. 名稱由來#

「cq」一詞源自兩個概念1：

  • colloquy（/ˈkɒl.ə.kwi/）：一種結構化的思想交流，理解在對話中浮現，而非單向輸出。
  • CQ：無線電呼叫代號，意指「任何電台，請回應」（"any station, respond"）。

兩者都指向同一個模型：開放邀請、回應，以及透過互動累積的集體訊號。用官方說法，就是「代理廣播它們所學到的，並聆聽其他代理已知的」1。

3. 核心問題：代理的知識孤島#

cq 的提案文件（CQ-Proposal）指出，今日的 AI 代理在孤立環境中運作。每當某代理遇到已知陷阱（未記載的 API 行為、函式庫版本不相容、常見架構反模式）時，都必須從頭重新發現，浪費運算、能源與時間5。

提案文件歸納出三個複合問題5：

  • 巨大低效率：全球每天有數百萬次代理工作階段重複相同的失敗，每次浪費的循環都消耗電力與冷卻用水。
  • 結果劣化：缺乏集體知識的代理會產出更差的結果（更多 bug、較不準確的分析、更多幻覺）。
  • 圍牆花園：現有的共享學習（例如專有代理記憶系統）被封閉在個別廠商內，造成鎖定並排除小型參與者。

提案將此類比為早期網頁：瀏覽器已存在，但沒有任何人為開放、可信任、可互通的標準發聲。Mozilla 當年改變了網頁，如今認為代理智慧需要同樣的介入5。

4. 設計原則#

cq 提案列出六項核心原則5：

5. 架構#

5.1 三個執行邊界#

cq 橫跨三個執行邊界41：

5.2 知識三層與升級路徑#

知識向上逐層升級，每層有遞增的範圍與信任要求。PoC 實作本地與遠端兩層，全球層為長期願景4：

5.3 信任層#

cq 的信任層提供「貢獻者可追溯性」，而非傳統意義的信任。聲譽並不會降低審查強度；無論貢獻者歷史為何，每個知識單元都接受相同審查4。

    reputation -->|"訊號饋入"| safeguards
  • 身分使用 KERI（Key Event Receipt Infrastructure）進行去中心化身分管理，并以 ACDC 憑證鏈連結代理與部署組織。責任歸屬於組織與其中的人，而非代理本身4。
  • 聲譽透過多元、獨立的確認取得。由三個獨立組織的三個代理確認的洞見，比由兩個組織的 800 個代理確認者更有價值4。
  • 抗毒化結合異常偵測、多樣性要求、HITL 審核關卡與護欄過濾。質押（staking）只是眾多訊號之一，權重低於獨立同儕確認與 HITL 審核，以避免「付費汙染」漏洞4。

每一份共享知識都流經一個共同的結構化格式 knowledge_unit.json，確保互通性6。架構文件中的範例4：

  },
  "context": {

    "frameworks": [],

    "pattern": "api-integration"
  },
  "evidence": {
    "severity": "high",

Schema 參考文件（schema/README.md）定義了多個 wire 型別，並以語言套件形式發佈：Python 版為 PyPI 上的 cq-schema，Go 版為 github.com/mozilla-ai/cq/schema 模組（透過 go:embed 內嵌）6。主要 schema 包含6：

  • knowledge_unit.json（KnowledgeUnit）：核心資料型別。欄位含 id（格式 ku_<32 hex>）、version、domains（1–16 個標籤）、insight、context、evidence、tier（local／private／public）、created_by、superseded_by、extensions、flags。
  • Insight：三段式，summary（≤500 字元）、detail（≤8000）、action（≤2000）。
  • Context：languages、frameworks、pattern。
  • Evidence：confidence（0.0–1.0，預設 0.5）、confirmations（預設 1）、first_observed、last_confirmed。
  • Flag：reason（stale／incorrect／duplicate）、timestamp、detail、duplicate_of。
  • query.json、propose.json、confirm.json、flag.json、scoring.json、review.json、health.json、stats.json、node_discovery.json。

設計上的關鍵決策包含4：insight 為三段式（供快速掃描、解釋與行動）；evidence 將信心與確認次數分離，contributing_orgs 作為多樣性訊號；provenance 是稽核軌跡（每一步升級都記錄人類審核者的 DID 與時間戳，使 cq 設計上即符合歐盟 AI 法案）；lifecycle.kind 將知識分為 pitfall、workaround、tool-recommendation。

10. 法規對齊：歐盟 AI 法案#

提案文件主張 cq 的架構「不是為了滿足法規而設計，但恰好與若干核心要求自然對齊」5。歐盟 AI 法案對高風險 AI 系統的要求將於 2026-08-02 全面強制執行5。對應關係包括：

  • 人類監督（第 14 條）：HITL 升級流程直接滿足，代理提議、人類決定5。
  • 透明與記錄保存（第 11、12、13 條）：知識格式含來源追蹤、版本與結構化中介資料，形成原生稽核軌跡5。
  • 風險管理（第 9 條）：抗毒化機制與護欄整合構成風險管理層5。
  • 資料治理（第 10 條）：HITL 審核、多重聲譽評分與陳舊偵測構成治理控制；隱私層確保無 PII 進入5。
  • 準確性與穩健性（第 15 條）：獨立代理驗證使知識獲得信心，陳舊或不正確知識隨時間衰減5。

提案亦討論貢獻者責任：貢獻知識單元是提供資訊而非部署 AI 系統，類比為 StackOverflow 回答者不對抄用其程式碼的後果負責5。cq 要求一份明確的貢獻者協議，涵蓋原創性、無 PII、授權授予、責任限制、審核注意義務與來源同意5。

14. 結論#

cq 是 Mozilla.ai 針對「代理知識孤島」問題提出的開放標準化嘗試，其核心貢獻在於：以 MCP 與 Agent Skills 等既有生態為載體，定義一套跨代理的知識單元格式與三層升級機制，並在架構上內建信任層、護欄層與人類審核，使其同時服務於品質治理與合規需求145。其遠端伺服器採 FastAPI 實作，對外提供 /api/v1 下的認證、使用者、審核與知識等端點31211109。

然而，該專案仍處於早期 0.x 階段，許多關鍵願景（全球公共池、去中心化身分、零知識隱私）尚未實作45，讀者在評估時應保持對「宣稱」與「現況」的區分。
