現代 UI/UX 導向的自架 RSS 閱讀器調查#

本報告調查可取代三套既有專案的自由開源軟體（FOSS）方案，並以「現代 UI/UX」為主要篩選標準。凡介面仍停留在傳統三欄式（資料夾樹＋文章列表＋閱讀窗格）的舊式 RSS 閱讀器，一律不列入推薦。

摘要#

核心結論：目前不存在同時滿足「網頁為基礎、現代微網誌式介面、原生混合 RSS 與社群來源、且部署簡單」的單一自架專案。 這是 2026 年開源生態的一個明確缺口：具備真正現代介面的專案（如 Folo）幾乎都是雲端服務而非自架；能自架的專案則多為傳統介面。

因此實務答案是一組搭配：

必須指名的陷阱：Folo（39.3k 星）雖然是當今最現代、最受歡迎的開源閱讀器，但無法自架，它需要 api.folo.is 的雲端帳號才能運作1。同樣地，Feedbin（3.8k 星）介面現代，但作者明文不建議自架2。

1. 問題定義與判準#

1.1 三套被取代的專案#

FeedDeck 是一套受 TweetDeck 啟發的多欄（deck）式閱讀器，同時彙整 RSS 與社群來源，以 Flutter 撰寫、後端為 Supabase，採 MIT 授權、約 318 星3。其架構非以網頁為基礎。最新版本為 v1.4.13。

NewsBlur 是一套自架新聞閱讀器，Django 後端搭配 Backbone.js 前端，MIT 授權、約 7,700 星4。其 docker-compose 需 11 個以上容器（4 種資料儲存：PostgreSQL、MongoDB、Redis、Elasticsearch），部署過於複雜4。

FeedFlow 是一套以 Kotlin Multiplatform 撰寫的極簡閱讀器，Apache 2.0 授權、約 1,300 星，最新版本 v1.21.0（2026-11-10）5。它完全沒有網頁版，本身也不含伺服器，而是連向本地檔案或 FreshRSS／Miniflux 等外部後端5。

1.2 「現代 UI/UX」的判準#

本報告以下列可驗證的技術特徵判斷介面是否現代，而非主觀感受：

1.3 為何排除舊式閱讀器#

以下專案雖然功能完備且維護活躍，但因介面仍為傳統三欄式而不列入推薦：

  • FreshRSS（16.6k 星，AGPL-3.0）：最主流但為經典三欄佈局6
  • Miniflux（9.9k 星，Apache-2.0）：極簡清單，非卡片／時間軸7
  • Tiny Tiny RSS（社群分支 884 星）：原專案已於 2025-11-01 退休，介面陳舊8
  • selfoss（2.5k 星）、Stringer（4.1k 星）、CommaFeed（3.6k 星）、Nextcloud News（1.0k 星）、yarr（4.1k 星）：皆為傳統列表式介面

這些專案在功能上仍是優秀的後端，但無法滿足「現代 UI/UX」這項要求。本報告第 4 節和第 5 節聚焦於真正符合標準的候選。

3. 多欄 Deck 佈局（最接近 FeedDeck）#

3.1 Glance#

Glance 是一套自架儀表板，將所有訂閱來源彙整於單一可自訂介面9。採 AGPL-3.0 授權、約 38,200 星，最新版本 v0.8.8（2026-11-07）9。以 Go 撰寫，可編譯為單一執行檔或使用 Docker 映像，相依極少9。

為何符合標準：其設定檔採用 columns 為基礎的佈局，每個頁面可有多個欄位，尺寸可設為 small 或 full9。這正是 FeedDeck 的多欄體驗在自架生態中最接近的對應。內建與 Feed 相關的 widget 包含 rss、reddit、hacker-news、lobsters、videos（YouTube）、twitch-channels、releases（GitHub）9。

微網誌特徵：具備卡片流版面與縮圖，視覺上接近社群平台的動態牆。

限制：Glance 是儀表板而非完整閱讀器——它以 widget 呈現摘要，沒有已讀／未讀狀態管理，也沒有訂閱管理與搜尋10。若需要完整的閱讀狀態追蹤，仍須搭配一個後端。

3.2 多欄佈局的現實限制#

需要指出的是：在自架生態中，同時具備多欄佈局、完整已讀狀態、以及原生社群來源的專案並不存在。這點在多方獨立調查中得到一致結論1011。實務做法是「Glance 負責多欄呈現，RSSHub 負責來源擴充」，但兩者之間沒有已讀狀態同步。

4. 現代卡片／時間軸型自架網頁閱讀器#

這一類是本報告的重點：它們是完整的自架閱讀器（具備訂閱管理、已讀狀態、搜尋），但介面已完全現代化。

4.1 Oksskolten — 現代自架閱讀器的首選#

Oksskolten 自稱「AI 原生的 RSS 閱讀器」，核心差異化在於對每篇文章自動進行全文擷取，並轉換為乾淨的 Markdown12。採 AGPL-3.0 授權、約 507 星，最新版本 v0.5.0（2026-06-08）12。

評價：這是清單中唯一同時具備「shadcn/ui 現代介面、單容器部署、完整閱讀器功能、AI 功能」的專案。缺點是星數僅 507、社群規模小。

4.2 Fusion#

Fusion 是一套輕量、自架優先的閱讀器，明確宣示「設計上不含 AI 功能」以維持專注13。採 MIT 授權、約 2,400 星，最新版本 v1.3.0（2026-10-07）13。

評價：與 Oksskolten 同為單容器現代閱讀器。Fusion 較輕、較單純（無 AI），社群稍大。兩者定位重疊，可視是否要 AI 功能抉擇。

4.3 Glean — 現代介面但尚未達生產可用#

Glean（拾靈）是一套自架 RSS 閱讀器與個人知識管理工具15。採 AGPL-3.0 授權、約 874 星；最新版本為 v0.3.0-alpha.6（2026-11-11），維護極為活躍（8 天內發佈 6 個 alpha）15。

評價：介面符合現代標準，但官方表明尚不建議用於生產環境，且 6 容器部署與「簡化部署」的目標相衝15。

4.4 其他現代卡片式閱讀器#

  • RSSMonster（MIT，579 星，v2.3.0／2026-09-09）：Vue 3 ＋ Express ＋ SQLite／MySQL，支援 Fever 與 Google Reader API、本機 AI 推論、智慧資料夾、桌面 Electron 版16。可用 SQLite 單容器運行。介面為三欄卡片式，現代化程度中等。
  • FeedMe（MIT，748 星，無正式發佈版）：並非具備後端的自架閱讀器，而是建置期由 Node 腳本抓取 RSS 並呼叫 LLM 產生摘要、再輸出為靜態網站的方案17。Docker 版在容器內以 cron 定期重建17。介面確為 shadcn/ui 卡片流，但「可訂閱任意 RSS」是透過編輯設定檔 feedme.config.yaml 完成，而非網頁操作17。適合當作個人儀表板，不適合當作通用閱讀器。

5. 微網誌原生時間軸型#

若「現代 UI/UX」的具體意指微網誌式時間軸（貼文卡片、頭像、互動），則需從社群平台軟體而非 RSS 閱讀器中尋找。

5.1 Friendica — 最符合「微網誌＋RSS」的方案#

Friendica 是一套完整的 Fediverse 社群網路軟體，原生支援訂閱外部 RSS/Atom 並將其顯示於使用者的時間軸中，與 ActivityPub 貼文並列18。採 AGPL-3.0 授權，約 1,700 星，最新穩定版本 2026.05-1（2026-05-21）18。

官方文件的直接證據（doc/en/user/connectors.md）：

"Put the URL into the Connect box on your Contacts page... All that the pages need to have is a discoverable feed using either the RSS or Atom syndication format."18

另一份文件（doc/en/user/making-friends.md）寫道：

"You can 'follow' almost anybody or any website that produces a syndication feed (RSS/Atom, etc.)."18

運作方式：將 feed 網址貼入聯絡人頁面的「Connect」欄位，該 feed 的貼文便會出現在時間軸，與 ActivityPub、Diaspora 等聯邦貼文並列18。文件亦註明無法對 feed 來源的內容回覆（單向訂閱）18。

評價：這是唯一能「原生」在微網誌時間軸中呈現 RSS 的自架方案，無須任何橋接。代價是 4 容器部署，且它本質是社群網路，閱讀狀態管理、訂閱分類等閱讀器功能較弱。

5.2 Mastodon ＋ 橋接#

Mastodon 是微網誌時間軸的參考實作，AGPL-3.0 授權、約 50,600 星，最新版本 v4.7.5（2026-11-03）20。但它沒有內建 RSS 訂閱能力，必須透過外部「RSS 轉 ActivityPub」機器人将 feed 貼文轉發進聯邦網路，才能在時間軸中看到19。這是可行的變通，但設定繁瑣且非原生。

5.3 Fread — 微網誌客戶端，但無法自架#

Fread 是一套去中心化微網誌客戶端，在同一個 app 中整合 Mastodon、Bluesky 與 RSS，並可建立跨協定的統一時間軸21。採 Apache-2.0 授權、約 403 星，最新版本 v1.10.5（2026-10-19）21。以 Kotlin Multiplatform 撰寫，主要平台為 Android（iOS 與桌面版開發中）21。

評價：在功能定義上最精準命中「微網誌式介面 ＋ RSS」的需求，且時間軸為微網誌樣式21。但它是行動客戶端，不提供伺服器端，無法以網頁或 Docker 自架21。可作為 FeedFlow 的替代客戶端，但不能取代 NewsBlur。

5.4 Folo — 必須指名的不可自架陷阱#

Folo（前稱 Follow）是最受歡迎的開源 AI RSS 閱讀器，AGPL-3.0 授權、約 39,300 星，桌面版 v1.17.0（2026-11-02）1。它整合 RSS 與社群來源、具備現代時間軸介面與豐富 AI 功能1。

然而，經逐目錄查核其儲存庫後確認：Folo 無法自架。 儲存庫中不存在 docker-compose.yml、Dockerfile 或任何自架說明文件；docs/ 目錄僅有依賴升級紀錄，api/ 目錄只有單一 webhook 檔案，沒有後端伺服器程式碼1。其實際架構為 Cloudflare Workers ＋ Vercel，所有客戶端都必須向 api.folo.is 驗證並同步，需要 Folo 帳號才能運作1。

部分二手資訊誤稱 Folo 可透過 Docker 自架11；本報告以儲存庫內容查核結果為準，採信「不可自架」。

6. AI 驅動的現代閱讀器#

6.1 Feeds Fun#

Feeds Fun 是一套自架新聞閱讀器，以 LLM 自動為每則新聞指派標籤，再由使用者建立規則依標籤評分、篩選與排序22。採 BSD 3-Clause 授權、約 399 星，最新版本 v1.29.4（2026-10-22）22。

評價：介面為現代 SPA，AI 標籤／評分是獨特賣點。但 6 容器部署與 NewsBlur 的複雜度問題相似22。

6.2 NewsNow — 現代卡片介面但非 RSS 閱讀器#

NewsNow 是一套即時熱門新聞聚合器，以 React 19 ＋ UnoCSS ＋ Nitro 撰寫，採 MIT 授權、約 22,400 星，最新版本 v0.0.43（2026-10-13）23。Docker 部署為單一容器，官方 docker-compose.yml 僅定義一個 newsnow 服務23。

為何不能當作閱讀器：它不是以使用者訂閱為中心的 RSS 閱讀器。其來源為 50 餘個預先寫死的爬蟲（微博、知乎、Hacker News、GitHub Trending、Product Hunt 等），使用者無法新增任意的 RSS 網址2311。RSS 僅在少數來源（如 Kaopu、AIHOT）內部作為資料來源使用11。

此外，專案 README 已公告 NewsNext（下一代）即將推出，且不再接受貢獻23，v0.0.x 系列正在收尾。

評價：若需求是「現代卡片式的新聞／熱門動態看板」而非訂閱管理，它是最現代的選項之一。但不符 RSS 閱讀器的定義。

6.3 TrendRadar — 排除#

TrendRadar 星數約 63,600，具備 RSS 爬取與 AI 分析，但本質為推播通知服務（微信、飛書、Telegram、Slack 等），沒有可瀏覽的閱讀器介面24。不符需求，列出以供辨識。

7. 輔助工具：社群來源與任意網站#

7.1 RSSHub — 社群來源的關鍵補充#

RSSHub 自稱「全球最大的 RSS 網路」，可為本身不提供 RSS 的網站與平台產生 feed，涵蓋 Twitter／X、YouTube、Reddit、Telegram、Mastodon、Instagram、TikTok 等25。採 AGPL-3.0 授權、約 47,000 星，採每日建置版本標記25。

部署：單一容器即可啟動（docker run -d -p 1200:1200 diygod/rsshub）；官方推薦的 docker-compose 另含 Redis 與 Browserless25。實際做法是產生對應路由網址（如 /reddit/:subreddit、/youtube/user/:username），再將該網址加入任何閱讀器或 Glance25。

這是滿足「社群來源」需求的實務路徑：由於沒有任何現代自架閱讀器原生支援 Bluesky／Mastodon，一律需經由這類橋接服務1126。

7.2 RSS-Bridge#

RSS-Bridge 同樣是 feed 產生器而非閱讀器，以 Unlicense（公有領域）釋出、約 9,300 星，提供 447 種以上的 Bridge（Mastodon、Reddit、YouTube、TikTok、Twitch、Telegram 等）27。單容器部署27。與 RSSHub 功能重疊，可擇一使用；Oksskolten 亦內建對 RSS Bridge 的整合12。

8. 客戶端（非網頁）選項#

若可接受非網頁介面，以下客戶端具備現代 UI，並可連接自架後端。

Lettura 值得特別注意：它以 Tauri ＋ React 19 ＋ shadcn/ui 撰寫，README 明確標榜介面設計28。但它是純桌面應用，無伺服器元件、無 Dockerfile，資料存於本機 IndexedDB，因此無法自架28。可作為 FeedFlow 的桌面替代品。

FeedFlow 本身仍活躍維護（v1.21.0／2026-11-10），且已支援連接 FreshRSS／Miniflux 等自架後端5。若痛點僅在於「沒有網頁版」，搭配一個自架後端即可，無須更換客戶端。

10.1 若最重視「現代卡片式閱讀體驗」#

選擇 Oksskolten（要 AI）或 Fusion（要單純）。兩者皆為單容器、具備 shadcn/ui 現代介面、完整的訂閱與已讀狀態管理。這是「現代 UI」與「部署簡單」的最佳交集1213。

10.2 若最重視「微網誌式時間軸」#

選擇 Friendica。它是唯一能在微網誌時間軸中原生呈現 RSS 的自架方案，無須橋接18。代價是 4 容器部署與較弱的閱讀器功能。

10.3 若最重視「多欄 Deck 佈局」（即 FeedDeck 的核心體驗）#

選擇 Glance。其 columns 設定與多種 feed widget 是最接近的自架對應9。但須理解 Glance 是儀表板而非閱讀器，沒有已讀狀態910。

10.4 若最重視「社群來源覆蓋」#

無論選哪一套，都需搭配 RSSHub。目前沒有任何現代自架閱讀器原生支援 Bluesky 或 Mastodon，這是生態層級的缺口1126。

10.5 關於 Bluesky 的特別說明#

Bluesky 自 2024 年起提供官方 RSS（bsky.app/profile/{handle}/rss）27，因此可透過原生 RSS 訂閱取得，無須橋接。Mastodon 同樣提供每個帳號的 RSS27。真正需要 RSSHub／RSS-Bridge 的是 Twitter／X、Instagram、TikTok 等不提供 RSS 的平台25。

11. 來源品質與限制#

  • 時效性：所有數據擷取於 2026-11-14。星數與版本號變動頻繁；RSSHub 採每日建置、Glean 於 8 天內連發 6 個 alpha 版，讀者應以官方頁面為準2515。
  • 已解決的來源衝突：關於 Folo 是否可自架，有二手來源稱「可透過 Docker 多容器自架」11，另一來源稱「不可自架」1。本報告採後者，理由是前者未提出儲存庫中的證據，而後者提供了逐目錄查核結果（無 Dockerfile、無 docker-compose、無後端程式碼、api/ 僅一個 webhook 檔）1。
  • 無法以 API 覆核的日期：本報告撰寫期間 GitHub API 對未驗證請求回應 403，故部分版本日期無法程式化覆核。其中 FeedDeck 最新版本 v1.4.1 的發佈年份在兩個來源中不一致（2024 與 2026）3，未能釐清，讀者應以官方 Releases 頁面為準。
  • 「現代」判定為技術性判定：本報告以框架世代、樣式系統、版面型態等可查核特徵判斷介面是否現代（見 1.2 節），而非主觀美感評價。同一專案在不同人眼中可能感受不同。
  • 未實地部署：本報告未實際部署任何專案。容器數量係依據各專案官方 docker-compose.yml 的服務定義統計，實際生產環境可能還需反向代理（Caddy、Traefik）與憑證管理。
  • 星數不等於品質：Glance 有 38.2k 星但無已讀狀態；Oksskolten 僅 507 星卻是功能最完整的現代自架閱讀器。星數僅反映社群關注度。
  • 未涵蓋的鄰近類別：Karakeep（約 30,500 星，AGPL-3.0，3 容器，可自動訂閱 RSS 並以現代卡片介面呈現）與 Linkwarden（約 20,400 星，AGPL-3.0，3 容器，可訂閱 RSS）雖具備現代介面與 RSS 匯入能力，但本質為書籤／稍後閱讀庫而非訂閱閱讀器，已讀狀態模型不同，故未列入主表3435。
