摘要#

是。 LibreDesk 內建一組穩定的 REST API（路徑前綴 /api/v1），任何外部程式都可以用「每位客服專員一組」的 API key + secret 呼叫它，藉此讀寫對話、聯絡人、標籤、狀態、報表與 AI 功能12。

除此之外，LibreDesk 還提供四種方向相反或用途不同的整合介面：

LibreDesk 沒有外掛（plugin）系統、沒有官方 SDK，但官方有釋出 OpenAPI 3.0 規格檔，可自動產生客戶端程式庫34。

整合面上有兩個容易誤判的限制需先留意：Webhook 失敗不重試（事件會直接遺失）5，以及所有整合都只能走網路介面，無法在行程內擴充4。

三、REST API（外部程式呼叫 LibreDesk）#

3.1 認證方式#

API key 是「每位客服專員（agent）」個別產生的，產生位置為 Admin → Teammates → Agents → 開啟該 agent → Generate API key。系統會顯示一組 API key 與 API secret，secret 只顯示一次，需立即保存；具備 users:manage 權限者才能產生金鑰1。

金鑰可隨時在同一頁面重新產生或撤銷。以某把 API key 發出的請求，其角色與權限等同於擁有該金鑰的客服專員，因此權限最小化原則必須靠「建立專用帳號 + 專用角色」來實現18。

官方支援兩種標頭格式1：

# 方式一：Basic authentication
curl -X GET "https://your-libredesk-instance.com/api/v1/conversations" \
  -H "Authorization: Basic <base64_encoded_key:secret>"

# 方式二：Token authentication
curl -X GET "https://your-libredesk-instance.com/api/v1/conversations" \
  -H "Authorization: token your_api_key:your_api_secret"

四、Webhook（LibreDesk 主動通知外部程式）#

若需求是「LibreDesk 發生事件時，反過來通知我方系統」，則應使用 Webhook，而非輪詢 API。

設定位置：Admin → Integrations → Webhooks → New webhook，需填寫名稱、目標 URL、訂閱事件、簽章密鑰（選填）、是否啟用5。

4.1 事件清單#

值得注意的是，團隊指派不會觸發 conversation.assigned（僅「指派給個人」才會）；message.updated 僅在對外訊息狀態變為 sent 或 failed 時發出5。

4.2 傳送標頭#

以上標頭依官方文件所列5。

4.3 交付保證與重試（重要限制）#

官方文件對此的說明相當直白，且是整合設計時最容易誤判的地方5：

Deliveries run in a background worker pool. Failed deliveries are not retried. Events are dropped when the delivery queue is full.

也就是說：

官方因此明確建議：收到 webhook 後應先驗簽、立即回 200，再把實際處理工作丟到背景非同步執行。任何在 HTTP 回應路徑上阻塞的慢速處理，都會導致事件遺失5。

這代表若要做到 at-least-once 的可靠度，必須自行在接收端實作持久化佇列與補償機制（例如定期以 API 輪詢比對），不能依賴 webhook 本身5。

Webhook 目標 URL 也受 LibreDesk 選配的 SSRF 防護機制涵蓋；該防護預設為關閉510。

4.4 安全性#

設定密鑰後，LibreDesk 會以 HMAC-SHA256 簽署內容，並在 X-Libredesk-Signature 標頭以 sha256=<signature> 形式傳送，接收端應進行常數時間比對5：

import hmac
import hashlib

def verify_signature(payload, signature, secret):
    expected_signature = hmac.new(
        secret.encode('utf-8'),
        payload,
        hashlib.sha256
    ).hexdigest()
    return hmac.compare_digest(f"sha256={expected_signature}", signature)

驗簽時必須使用原始請求內容（raw body），不可先經過 JSON 解析再重新序列化，否則簽章會不符5。

五、Context Links（從對話側邊欄跳轉外部系統）#

Context Links 會在對話側邊欄產生連結，客服點擊後開啟外部網址，並自動帶入聯絡人與對話資訊。設定位置為 Admin → Integrations → Context links11。

可用的 URL 樣板變數包括 {{email}}、{{phone}}、{{external_user_id}}、{{contact_id}}、{{first_name}}、{{last_name}}、{{conversation_uuid}}，以及 {{token}}11。

其中 {{token}} 是關鍵設計：LibreDesk 會產生一組 AES-256-GCM 加密且具時效性的權杖，內含上述所有欄位再加上 agent_id、agent_email、iat、exp。權杖格式為「12 bytes nonce + ciphertext」再進行 base64 編碼，shared secret 即為 AES-256 金鑰。接收端系統解密後即可一次取得完整 payload，避免敏感資料直接暴露在 URL 或瀏覽器歷史紀錄中11。

sequenceDiagram
    participant A as 客服專員
    participant LD as LibreDesk
    participant X as 外部系統（CRM）
    A->>LD: 點擊側邊欄 Context Link
    LD->>LD: 以 AES-256-GCM 產生含 exp 的權杖
    LD->>X: 開啟 URL 並附上 token
    X->>X: 用共享密鑰解密並驗證 exp
    X-->>A: 顯示對應客戶資料

六、Widget API（自建聊天前端）#

若目標是「把 LibreDesk 官方聊天元件嵌入自家網站」，只要一行 <script> 即可12：

<script>
  window.LibredeskSettings = {
    baseURL: 'https://support.example.com',
    inboxID: 'YOUR_INBOX_UUID'
  };
</script>
<script async src="https://support.example.com/widget.js"></script>

若需要完全自製前端，官方另提供 Widget API：一組公開（無需 agent API key）的 HTTP 端點加上 WebSocket 協定，涵蓋啟動器設定、聊天設定、驗證交換、建立對話、取得對話、送出訊息、更新已讀、下載逐字稿、handoff 表單、行銷活動（campaigns）、媒體上傳等13。

訪客身分驗證採用 HS256（HMAC-SHA256）簽署的 JWT，由我方伺服器以收件匣的 Secret key 簽發，secret 永不離開伺服器端；LibreDesk 驗簽後，會依 JWT 中的 external_user_id 尋找或建立對應聯絡人12。

七、AI Tools（AI 助理呼叫外部 API）#

這是容易被忽略但對整合很有用的一條路徑：LibreDesk 的 AI 助理可以在回覆客戶的過程中，主動呼叫你提供的 HTTP 端點（例如查訂單、查餘額、取消訂閱）。設定位置為 Admin → AI → Tools，再逐一授權給各個助理；工具也可開放給客服用的 copilot 與 Generate reply14。

工具定義欄位包括名稱（模型的 function name，上限 64 字元、僅限英數與 -、_）、描述（模型據此判斷何時呼叫）、URL 與方法（僅 GET 或 POST）、標頭（內容加密儲存）、參數（JSON Schema）、是否要求已驗證聯絡人、是否可用於 copilot / Generate reply、以及是否要求客服逐次核准14。

參數以 JSON Schema 描述，GET 時置於 query string，POST 時作為 JSON body14：

{
  "type": "object",
  "properties": {
    "order_id": { "type": "string", "description": "The order ID to look up" }
  },
  "required": ["order_id"]
}

7.2 安全注意事項#

官方文件提出三條明確規則14：

  1. 先驗自己的密鑰：在工具上設定如 X-Api-Key 的標頭，並拒絕未帶該標頭的請求。端點暴露在網際網路上，工具設定是唯一能證明請求來自 LibreDesk 的依據。
  2. 客戶身分一律取自標頭，絕不取自參數：請求 body 中的內容是模型依客戶輸入所撰寫，必須視為不受信任的輸入。若模型傳入 account_id=99999，應忽略該數字，改用標頭中聯絡人所屬的帳號。
  3. 敏感資料要求 X-Libredesk-Contact-Verified 為 true：訪客可以在聊天中任意聲稱任何 email。此標頭只有在「30 分鐘內通過一次性驗證碼」、「以簽章 JWT 識別的身分」或「客服由 copilot 發起」時才為 true。

關鍵陷阱：「Require verified contact」開關只控制 AI 是否先要求輸入驗證碼，並不會阻止請求送達你的端點。請求仍可能帶著 X-Libredesk-Contact-Verified: false 抵達。端點必須每次自行檢查該標頭，僅在其為 true 時回傳個人資料14。

官方 repo 內附有可執行的範例程式位於 scripts/tools-server14。

7.3 回應處理與資源上限#

回應應為小型、扁平的 JSON，過長的 payload 會被截斷。2xx 視為「成功取得資料」（助理據此回答），非 2xx 視為失敗（助理通常會告知無法協助並轉交真人）。「查無資料」應以 2xx 搭配空清單或簡短訊息表示，非 2xx 保留給真正的錯誤（如 API key 錯誤、上游服務中斷）14。

資源上限設定於 config.toml 的 [ai_agent] 區段14：

時間上限：單次助理執行在即時聊天為 90 秒、在 email 為 3 分鐘；每次供應商呼叫上限 60 秒。觸及任何上限即轉交真人14。

需注意官方標明 AI 功能目前為 beta 狀態，且助理回覆會實際發送給客戶，建議先在低流量收件匣測試14。

八、使用者體驗整合：SSO#

LibreDesk 支援以 OpenID Connect 讓客服專員登入（Google、Microsoft 或任意自訂 OIDC 供應商，例如 Keycloak）。設定路徑為 Admin → Security → SSO15。

限制在於：SSO 不會自動建立帳號。仍需先在 LibreDesk 內建立 agent，登入時系統以供應商回傳的 email 比對既有 agent15。這點對「以外部身分系統為單一真相來源」的場景會造成額外的帳號同步工程。

九、權限模型（整合時最需注意的一環）#

權限以 object:action 格式命名（例如 conversations:read_all）。每個 agent 可被指派多個角色，實際權限為各角色權限的聯集8。

預設角色有二8：

與整合最相關的權限包括8：

  • conversations:read、conversations:write、conversations:read_all、conversations:read_unassigned、conversations:read_team_all
  • messages:read、messages:write、messages:write_private、messages:write_as_contact
  • contacts:read_all、contacts:write、contacts:export
  • users:manage（產生／撤銷 API key 的必要權限，也是指派角色的必要權限）
  • webhooks:manage、context_links:manage、reports:manage

重要警告：官方文件明確指出 users:manage 實質上等同完整存取權，因為擁有者可以把任何角色（包含 Admin）指派給任何人，包括自己。整合用的 API key 應避免綁定具備 users:manage 的帳號8。

開對話檢視時，agent 需要 conversations:read 再加上一個符合該對話指派狀態的清單權限（例如 conversations:read_assigned 或 conversations:read_team_inbox）8。

十一、結論與選型建議#

11.1 直接回答問題#

「LibreDesk 有沒有 API 讓第三方程式整合？」

有，而且是官方文件化的正式功能，不是隱藏的內部端點。外部程式只要具備一組 agent API key 與 secret，即可透過 /api/v1 進行完整的讀寫操作。README 也把「API 與 Webhook」列為 Administration and integrations 下的正式功能4。

11.2 整合路徑選擇#

flowchart TD
    Q1{"誰發起？"} 
    Q1 -- "外部程式要讀寫資料" --> A["REST API /api/v1<br/>Basic 或 token 認證"]
    Q1 -- "LibreDesk 有事要通知我" --> B["Webhook<br/>HMAC-SHA256 簽章"]
    Q1 -- "客服要在側邊欄一鍵跳轉" --> C["Context Links<br/>AES-256-GCM 權杖"]
    Q1 -- "AI 助理回覆時要查我資料" --> E["AI Tools<br/>身分標頭 + 共享密鑰"]
    Q1 -- "要自製聊天前端" --> D["Widget API<br/>JWT HS256 + WebSocket"]

11.3 限制與風險#

  1. 無外掛系統：不可能在 LibreDesk 內以程式擴充功能，所有整合都必須走網路介面4。
  2. 無官方 SDK：需自行以 HTTP 呼叫，或由 OpenAPI 規格自動產生客戶端3。
  3. 文件尚未完整：官方自承部分端點未撰寫文件1。
  4. 權限即身分：API key 完全繼承所屬 agent 的權限，切記不要綁定含 users:manage 的帳號8。
  5. AGPL-3.0 授權：若以修改後的 LibreDesk 提供網路服務，需注意 AGPL 的原始碼釋出義務6。
  6. SSO 不自動建帳號：外部身分系統無法成為唯一真相來源，需額外同步 agent 資料15。
  7. Webhook 不重試：失敗或逾時即永久遺失事件，可靠度須由接收端自行補強5。
  8. AI 功能為 beta：AI 助理與工具呼叫仍在 beta，且會實際對客戶發話14。

11.4 進行整合前的檢查清單#

11.5 一句話總結#

LibreDesk 對第三方整合的態度是「開放網路介面、封閉執行檔」：Rest API、Webhook、Context Links、AI Tools、Widget API 等介面足以支撐絕大多數整合需求，但不提供任何形式的行程內擴充能力。
