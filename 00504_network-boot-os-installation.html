網路開機與網路安裝作業系統完整指南#

本報告說明如何透過網路（而非本機硬碟、光碟或 USB）啟動電腦並安裝作業系統。內容涵蓋底層協定（PXE、DHCP、TFTP）、現代替代方案（iPXE、UEFI HTTP Boot）、自動化安裝的應答檔機制、無磁碟開機的根檔案系統取得方式、常見工具比較、實作範例，以及安全性考量。所有事實均附註腳與 APA 改良格式（ISO 8601 日期）之參考文獻。

1. 什麼是網路開機#

網路開機（Network Booting / Netboot） 是指電腦不從本機儲存裝置開機，而是透過網路協定向伺服器取得開機映像檔，進而啟動作業系統或安裝程式1。其典型應用包含：資料中心大量部署伺服器、無磁碟工作站（Thin Client）、磁碟映像複製（Cloning）、以及救援環境的啟動。

網路開機的客戶端只需要一張支援 PXE 的網路卡（NIC）與標準協定 DHCP、TFTP2。

無磁碟節點（Diskless Node）指的是沒有磁碟機、改以網路開機載入作業系統的電腦，其優點包含成本較低、運轉安靜、集中化管理3。取得作業系統的方式大致分為三類：NFS 根目錄、RAM disk 記憶體開機、以及區塊層級虛擬磁碟（iSCSI、AoE、NBD 等）3。

2. 網路開機的層次架構#

理解網路開機時，必須區分三個彼此獨立但常被混淆的層次：

PXE 是負責「把安裝程式的核心與 initrd 送上裸機」的傳輸機制；安裝程式再透過核心命令列參數（kernel cmdline）去抓取應答檔4。

3. PXE 開機流程詳解#

PXE（Preboot Execution Environment，讀作 "pixie"）是由 Intel 在「Wired for Management」框架下提出的規格，PXE 2.0 於 1998 年 12 月發布，2.1 於 1999 年 9 月發布；目前它已成為 UEFI 標準的一部分2。其設計目標是在網卡韌體中放入一個小型的 PXE ROM，提供通用網路裝置介面（UNDI）、極簡的 UDP/IP 堆疊、開機前 DHCP 客戶端與 TFTP 客戶端2。

3.2 步驟二：找到開機伺服器與開機程式名稱#

PXE 客戶端使用 RFC 4578 定義的三個 DHCP 選項來識別自己，且這些選項必須出現在所有 PXE 封包中6：

  • Option 93 — Client System Architecture Type：16 位元架構識別碼。常見值為 0（Intel x86PC，傳統 BIOS）、6（EFI IA32）、7（EFI BC）、9（EFI x86-64）6。
  • Option 94 — Client Network Interface Identifier：type 1 = UNDI，附主次版本號6。
  • Option 97 — Client Machine Identifier：16 位元組的 GUID，type 06。

此外，PXE 客戶端必須請求 DHCP 選項 128–135，這些選項內容供下載後的 NBP 使用，而非開機 ROM 本身6。

3.3 步驟三：DHCP 選項 66 與 67#

定義於 RFC 2132 第 9.4 與 9.5 節7：

  • Option 66 — TFTP server name：當 DHCP 表頭的 sname 欄位被用於其他 DHCP 選項時，用以識別 TFTP 伺服器7。
  • Option 67 — Bootfile name：當 DHCP 表頭的 file 欄位被用於其他 DHCP 選項時，用以識別開機檔名7。

這兩個選項之所以存在，是因為原始 BOOTP 表頭的 sname（64 位元組）與 file（128 位元組）欄位在 DHCP 選項佔用空間後會不足7。許多 DHCP 伺服器（例如 ISC dhcpd）也直接使用 next-server（等同 siaddr）與 filename 欄位7。若 PXE 客戶端只從未啟用 PXE 的 DHCP 伺服器取得回應，將無法開機2。

3.4 步驟四：proxyDHCP（DHCP 重導）#

由於企業的 DHCP 伺服器通常被嚴格管控，PXE 標準定義了 proxyDHCP，將需求拆成兩個可獨立管理的伺服器2：

  1. 傳統 DHCP 伺服器：提供所有客戶端的 IP 位址與遮罩。
  2. proxyDHCP 伺服器：只對通過 PXE 識別的客戶端提供 TFTP 伺服器 IP 與 NBP 名稱。

客戶端送出一次 PXE DHCPDISCOVER，會收到兩個互補的 DHCPOFFER。由於兩個服務無法共用同一個主機上的 port 67/UDP，proxyDHCP 執行於 port 4011/UDP2。

3.5 步驟五：以 TFTP 傳輸 NBP#

客戶端使用 TFTP 將 NBP（Network Bootstrap Program） 載入 RAM，必要時進行驗證（例如 UEFI Secure Boot），然後執行2。TFTP（RFC 1350）在 UDP 上運作8：

  • 傳輸由送往伺服器知名 port 69 的 RRQ（讀取請求）或 WRQ（寫入請求）開始8。
  • 資料以固定 512 位元組區塊傳輸；每個 DATA 封包必須被 ACK 確認後才能送下一個（lock-step）8。
  • DATA 封包小於 512 位元組代表傳輸結束8。
  • 五種封包類型：RRQ(1)、WRQ(2)、DATA(3)、ACK(4)、ERROR(5)8。
  • TFTP 沒有認證機制，因此伺服器必須限制可存取的檔案8。
  • 傳輸效能後來由 TFTP Blocksize Option（RFC 2348，1998）與 TFTP Windowsize Option（RFC 7440，2015）改善8。

3.6 步驟六：NBP 執行並鏈式載入#

NBP 是開機鏈的第一環。它通常會再以 TFTP 請求額外檔案，啟動一個極簡的作業系統執行環境（Windows PE，或 Linux 核心 + initrd）2。一旦這個小型作業系統開始運作，它會載入自己的網路驅動與 TCP/IP 堆疊，之後剩餘的傳輸改用更穩健的協定（HTTP、CIFS 或 NFS），而非 TFTP2。常見的 NBP 包含：

  • PXELINUX（BIOS 下的 pxelinux.0），為 Syslinux 的衍生品9。
  • iPXE / gPXE（undionly.kpxe、ipxe.efi），功能完整的開源開機韌體10。
  • 廠商自製 NBP（例如 WDS 的 boot.wim 映像）。

3.7 UEFI 與傳統 BIOS 的差異#

UEFI 規格第 24 章（Network Protocols — SNP, PXE, and BIS）定義了開機服務環境中的網路存取協定：Simple Network Protocol（SNP）、PXE Base Code Protocol 與 Boot Integrity Services（BIS）11。SNP 提供網路卡的封包層介面，供高階驅動產生 DHCP、TFTP、MTFTP 等開機服務11。EFI_PXE_BASE_CODE_PROTOCOL 疊在 EFI_MANAGED_NETWORK_PROTOCOL 之上，其介面包含 Dhcp()（完成 DHCPv4 DORA 或 DHCPv6 SARR 序列）、Discover()、Mtftp() 及 UDP 讀寫函式11。

實務後果：BIOS 客戶端與 UEFI 客戶端需要不同的開機檔，因此 DHCP 伺服器必須依 Option 93 分支處理。ISC dhcpd 範例如下9：

option architecture-type code 93 = unsigned integer 16;
if option architecture-type = 00:00 {
    filename "path/to/BIOS/pxelinux.0";
}
elsif option architecture-type = 00:09 {
    filename "path/to/EFIx64/syslinux.efi";
}
elsif option architecture-type = 00:06 {
    filename "path/to/EFIia32/syslinux.efi";
}

需注意架構碼 06（EFI IA32）與 07（EFI BC） 常被廠商誤用於 CSM/x64 開機9。此外，UEFI Secure Boot 可在執行 NBP 前驗證其簽章2；UEFI 2.5 新增了 HTTP Boot 與 iPXE HTTP chainloading，讓客戶端可透過 HTTP 而非 TFTP 下載開機檔，因而省去 TFTP 伺服器2。

5. 現代替代方案#

5.1 iPXE#

iPXE 是領先的開源網路開機韌體，提供完整的 PXE 實作並附加多項功能；它可取代網卡上原有的 PXE ROM，或以鏈式載入（chainload）方式進入 iPXE 而無須重刷韌體13。GitHub 上的 ipxe/ipxe 儲存庫約有 2.1k stars、818 forks14。

其特色包含13：

  • 透過 HTTP 或 HTTPS 從網頁伺服器開機（不限於 TFTP）
  • 從 iSCSI SAN 開機
  • 透過 FCoE 從 Fibre Channel SAN 開機
  • 從 AoE SAN 開機
  • 從無線網路開機
  • 從廣域網路（WAN/Internet）開機
  • 從 Infiniband 網路開機
  • 以腳本控制開機流程
  • 建立互動式表單與選單

授權方面，iPXE 主體採用 GNU GPL 第 2 版（或任一較新版本），部分歷史因素下的程式碼採用 GPL 相容授權如二條款 BSD 授權15。最新穩定版為 v2.0.0（2026 年 3 月 6 日發布），新增 UEFI Secure Boot shim 支援、LoongArch64 與 RISC-V 架構支援、autoexec.ipxe 自動下載、EAPoL/port 認證、LLDP、現代 TLS（DHE/ECDHE、X25519、P-256/P-384、ECDSA）並移除 TLS v1.016。

5.2 UEFI HTTP Boot#

UEFI HTTP Boot 於 UEFI 規格 2.5 版引入，結合 DHCP、DNS 與 HTTP 來進行網路開機與部署，以 HTTP(S) 取代 TFTP 作為檔案傳輸方式17。相較於傳統 PXE，HTTP Boot 能處理遠大於 TFTP 的檔案，且可跨越更大的距離；PXE 依賴 UDP 廣播，而 HTTP Boot 可從不位於區域網路的伺服器下載數 MB 的檔案，例如 Linux 核心與根檔案系統17。

Intel 指出 PXE 的弱點：「PXE has no mechanism for encryption or authentication, is susceptible to man-in-the-middle attacks, does not scale outside of local networks, and has reliability issues associated with TFTP time-outs and UDP packet loss」，並直言「The TFTP & UDP transactions associated with PXE may be the last unencrypted traffic on your network and are trivial to intercept」17。

運作方式：客戶端以 DHCP Option 60（Vendor Class Identifier）傳送 HTTPClient 字串自我識別，伺服器則以 Option 67 回傳一個 http:// URL 的開機檔位址，客戶端再以 HTTP(S) 下載18。iPXE 文件指出：「You must configure your DHCP server to check for a UEFI HTTP Boot client, and to provide the string HTTPClient as the vendor class identifier, and an HTTP URI as the boot filename」19。SUSE 文件亦強調「the DHCPv4 server must use the HTTPClient parameter for the vendor class ID, as the client uses it to identify an HTTP Boot offer」20。

ISC dhcpd 範例（同時服務 PXE 與 HTTP 客戶端）20：

class "pxeclients" {
  match if substring (option vendor-class-identifier, 0, 9) = "PXEClient";
  option vendor-class-identifier "PXEClient";
  next-server 192.168.111.1;
  filename "/bootx64.efi";
}
class "httpclients" {
  match if substring (option vendor-class-identifier, 0, 10) = "HTTPClient";
  option vendor-class-identifier "HTTPClient";
  filename "http://www.httpboot.local/sle/EFI/BOOT/bootx64.efi";
}

與 iPXE HTTP Boot 的關係：iPXE 的「UEFI HTTP chainloading」應用說明指出：「Version 2.5 of the UEFI specification introduces the UEFI HTTP Boot feature. You can use the basic UEFI HTTP Boot client to chainload iPXE from an HTTP server, eliminating the need for a separate TFTP server in your boot infrastructure」19。原生 UEFI HTTP Boot 客戶端刻意設計得很簡單，只下載並執行一個開機檔；iPXE 則作為第二階段解鎖進階功能19。iPXE 會自動繼承韌體憑證：「when running on a UEFI platform, iPXE will automatically obtain any certificates stored in the UEFI TlsCaCertificate variable」21。

5.3 netboot.xyz#

netboot.xyz 是一個以 iPXE 為基礎的開源網路開機作業系統安裝器，本體是一個不到 1 MB 的 iPXE 開機程式，開機後提供選單，從上游取得網路安裝器、Live 發行版與救援工具，因此無須管理安裝媒體22。它支援 x86（32/64 位元）與 arm64，並同時支援 Legacy（PCBIOS）與 UEFI 模式22。

其主要選單分類包含：Linux 網路安裝、桌上型與 Live 發行版、安全與鑑識、工具與救援、Hypervisor 與儲存、Windows（WIM）、netboot.xyz 端點、iPXE Shell、重新開機23。可用的作業系統約 80 種以上，包含 AlmaLinux、Alpine、Arch、CentOS、Debian、Fedora、FreeBSD、NixOS、Ubuntu 等22。

鏈式載入方式24：

  • 透過 PXE / TFTP：於 DHCP 指定 filename "netboot.xyz.kpxe"；若網卡有問題可改用 netboot.xyz-undionly.kpxe（undionly 版本借用網卡開機韌體）。
  • 透過既有 iPXE：在 iPXE shell（按 Ctrl-B）執行 dhcp 然後 chain --autofree https://boot.netboot.xyz。
  • 透過 ISO / USB：netboot.xyz.iso 可掛載為虛擬媒體（Citrix XenServer、Proxmox VE、VMware、VirtualBox）或用於頻外管理（Dell DRAC / HP iLO）；netboot.xyz.img 可寫入 USB。
  • 透過 GRUB/syslinux：chain --autofree https://boot.netboot.xyz/menu.ipxe。

netboot.xyz 本質上是一組整理過的 iPXE 腳本、選單與重新打包的作業系統映像，而非 iPXE 本身的分支22。其主儲存庫為 github.com/netbootxyz/netboot.xyz，約有 12.5k stars、867 forks，授權為 Apache-2.025。在 Secure Boot 方面，它透過 Microsoft 信任的 shim 鏈式載入已簽署的 iPXE 二進位檔；完整端到端安裝支援目前限於 Debian、Devuan 與 Kali，其他發行版可能需要關閉 Secure Boot 才能完成最後安裝步驟22。

5.4 iVentoy#

iVentoy 是與 Ventoy 同一作者開發的增強型 PXE/HTTPBoot 伺服器，只需將 ISO 檔放入資料夾即可讓客戶端透過網路開機，無須解壓縮或逐一設定26。其特色包含：直接開機原始 ISO 檔（透過 HTTP 或 NBD 串流）、保留每個 ISO 的原生開機選單、同時支援 x86 Legacy BIOS / IA32 UEFI / x86_64 UEFI（含 Secure Boot）/ ARM64 UEFI / LoongArch64 UEFI、涵蓋 110 種以上作業系統、可執行於 Windows 與 Linux26。

其網路 ISO 開機流程為：客戶端取得 PXE/TFTP 指示後，iVentoy 傳送一個 iPXE 核心給客戶端，客戶端顯示 Ventoy 圖形介面列出可用 ISO，選定的 ISO 再被串流至 RAM 或透過網路區塊掛載（NBD/iSCSI/NFS/SMB）27。

iVentoy 提供四種 DHCP 模式以與既有 DHCP 伺服器共存：Proxy / ProxyNet（內建 DHCP 只回應 next-server/bootfile，不發放 IP）、External（同網段，iVentoy 監聽 DHCP 封包學習客戶端 BIOS 模式）、ExternalNet（不同網段/VLAN，需由第三方 DHCP 依客戶端架構動態設定 bootfile）28。

需留意 Ventoy 與 iVentoy 是兩個不同產品：Ventoy 為 100% 開源、用於透過 USB/硬碟安裝作業系統；iVentoy 則部分開源、部分閉源，用於透過網路（PXE）安裝作業系統29。標準 Ventoy 另內建本地 PXE 功能：以 Ventoy USB 開機後按 F5: Tools 選擇 PXE，該主機即成為臨時的 DHCP + TFTP 伺服器，讓同網段設定為網路開機的目標機連上並載入 Ventoy 選單，開機存於主機 Ventoy USB 上的原始 ISO 檔30。

6. 自動化 / 無人值守網路安裝#

安裝自動化是與 PXE 傳輸不同的一個層次：它負責事先回答安裝程式的問題，使安裝無須人工介入。以下是各主要作業系統的機制。

6.1 Debian preseed#

Preseeding 是設定 debian-installer（d-i）所問問題的答案；它不是必需的，空的 preseed 等同於手動安裝，你預先設定的每個問題會改變基準行為；安裝程式讀取 debconf 格式檔案，並將值餵入 debconf 資料庫31。

6.2 Ubuntu autoinstall（Subiquity）#

Ubuntu Server 20.04+ / Desktop 23.04+ 使用 autoinstall 格式（為 d-i preseeding 的現代替代），以 YAML 撰寫、由 Subiquity 安裝程式處理；與 preseed 的關鍵行為差異是：只要有任何 autoinstall 設定存在，未回答的問題會採預設值（若無預設值則失敗），而不會停下來詢問；可將區段標記為 interactive-sections 以保留互動32。

傳遞方式有兩種：一是透過 cloud-init（建議方式），在 #cloud-config 檔案中以頂層 autoinstall: 鍵放入，透過 NoCloud datasource 傳遞；二是直接放在安裝媒體根目錄的 autoinstall.yaml32。Subiquity 的優先序為：核心命令列 → 安裝系統根目錄 → cloud-config → 安裝媒體根目錄33。

所需檔案為 user-data（含 #cloud-config 後接 autoinstall: version: 1 ...）與 meta-data（通常為空，或含 instance-id），透過 HTTP（ds=nocloud-net;s=http://server:port/）或標籤為 CIDATA 的 ISO/vfat 磁碟提供32。

PXE 串接：以 autoinstall ds=nocloud-net;s=http://_gateway:3003/ 開機32。cloud-init 負責傳遞設定，但不處理 autoinstall 指令——由 Subiquity 處理；cloud-config 頂層指令修改臨時安裝環境，而 autoinstall: user-data: 下的指令則修改目標系統的首次開機34。

6.4 SUSE AutoYaST#

AutoYaST 是 SUSE 的無人值守大量部署系統，使用 AutoYaST profile（又稱 control file）——通常是名為 autoinst.xml 的 XML 檔，內含安裝與設定資料；YaST 解析 profile 後無需使用者互動即可設定系統36。其流程分三階段：準備、安裝、安裝後設定（第二階段）；與一般單階段 SLES 安裝不同，AutoYaST 於首次開機後執行第二階段，需具備 autoyast2 與 autoyast2-installation 套件，可用 <second_stage config:type="boolean">false</second_stage> 停用36。

PXE 串接：YaST 會在開機時於開機媒體或 initrd 根目錄尋找 autoinst.xml，或於標籤 OEMDRV 的裝置上尋找；否則於核心命令列傳入 autoyast=URL，支援 file://、device://、nfs://、http://、https://、tftp://、ftp://、cifs:// 等38。需注意 PXE 迴圈問題：安裝後機器會再次 PXE 開機而重新安裝；解法是使用會切換 TFTP 設定的 HTTP/CGI，或在 profile 中以 <pxe> 資源於重開機前為該 MAC 上傳 localboot 0 設定38。

6.5 cloud-init（首次開機設定）#

cloud-init 是 Linux 雲端實例/VM/裸機首次開機設定的實質標準，依 五個序列開機階段運作：Detect（ds-identify 偵測平台）、Local（cloud-init-local.service，在網路前執行、尋找本地 datasource 並寫入網路設定）、Network（cloud-init-network.service，網路就緒後完整處理 user-data）、Config（cloud-config.service，執行 cloud_config_modules 含 runcmd）、Final（cloud-final.service，如 rc.local 的晚期階段）39。

NoCloud datasource 所需的四種設定檔為40：

  • user-data — 使用者設定（cloud-config YAML 或 shell 腳本；cloud-config 需 #cloud-config 標頭）
  • meta-data — YAML，至少含 instance-id
  • vendor-data — 選用的廠商預設值
  • network-config — 選用的網路設定

NoCloud 的傳遞來源包含本機檔案系統、標籤為 CIDATA 的磁碟、自訂網頁伺服器（ds=nocloud;s=https://...，HTTP 時使用 -net 後綴）或 FTP/FTPS 伺服器40。seedfrom/s 值必須以 / 結尾40。cloud-init 不是安裝程式，它是 Ubuntu autoinstall 所搭乘的機制；改變 meta-data 中的 instance-id 會讓 cloud-init 將該次開機視為全新的「首次開機」40。

6.6 應答檔機制比較#

關鍵區別：preseed 遇到未回答的問題會停止，autoinstall 則採預設值（或失敗）；Autoinstall 為 YAML 且建構於 cloud-init 之上，preseed 為 debconf 鍵值3132。

7. 無磁碟開機：根檔案系統怎麼來#

無磁碟節點的作業系統映像取得方式分三類3：

  1. NFS 根目錄 — 核心載入記憶體後，其餘作業系統透過網路檔案系統連線存取。
  2. RAM disk / RAM 開機 — 作業系統映像被取入 RAM disk 並從記憶體執行。
  3. 虛擬磁碟 / 區塊層級開機 — 磁碟操作被虛擬化並轉為網路協定（iSCSI、AoE、NBD 等），遠端的是原始區塊裝置。

7.1 NFS 根目錄#

依 Linux 核心官方文件，NFS root 是經典的 Linux 無磁碟技術41：

  • 核心以 root=/dev/nfs 告知使用 NFS 而非實體裝置，並以 nfsroot=[<server-ip>:]<root-dir>[,<nfs-options>] 指定；若未給定 nfsroot，預設為 /tftpboot/%s（%s 為客戶端 IP）41。
  • ip=<client-ip>:<server-ip>:<gw-ip>:<netmask>:<hostname>:<device>:<autoconf> 參數設定網路，最常見形式為 ip=dhcp41。
  • NFS 客戶端支援與核心層級自動設定（DHCP/BOOTP/RARP）必須編譯為內建（而非模組）才能使用 nfsroot41。
  • 使用 NFS root 的系統，/etc/resolv.conf 常連結至 /proc/net/pnp，因為 DNS 資訊由此匯出41。

7.2 iSCSI 開機#

iSCSI 將區塊導向的 SCSI 指令封裝為 iSCSI PDU，透過 TCP/IP 傳輸，並定義 initiator 與 target 的 Session（I-T nexus）；與 NFS 不同，iSCSI 呈現的是遠端區塊裝置，作業系統將其視為本機磁碟42。依 ArchWiki，開機時掛載 iSCSI target 有三種方式43：

  1. 標準 initramfs — 設定為初始化網路連線、掛載 iSCSI target 並自其開機。
  2. 韌體式（BIOS/UEFI）與網路卡 — 某些韌體與網卡可在開機進入作業系統前自行初始化網路連線並掛載 iSCSI target，「This is common in server- and enterprise-grade hardware」43。
  3. 自訂 PXE 韌體如 iPXE — 掛載 iSCSI target 並開機。

傳遞韌體 iSCSI 設定給作業系統的機制是 iBFT（iSCSI Boot Firmware Table），作業系統/initramfs 讀取此 ACPI 表以自動設定網路與 iSCSI session43。微軟的 iSCSI Target Server 可從單一集中映像開機數百台電腦，使用 differencing VHD 時一個主映像可開機最多 256 台電腦；微軟測試曾於 34 分鐘內部屬 256 台電腦，且「A specialized network adapter is not required for this scenario, and a software boot loader can be used (such as iPXE open source boot firmware)」44。

7.3 AoE（ATA over Ethernet）#

ATA over Ethernet（AoE） 由 Brantley Coile Company 開發，用於在乙太網路上簡單高效地存取區塊儲存45：

  • AoE 運作於乙太網路 Layer 2，不使用 IP，因此無法透過網際網路或其他 IP 網路路由（性質較接近 FCoE 而非 iSCSI）45。
  • 它將 ATA 指令封裝於乙太網路框架（IEEE 指派 EtherType 0x88A2），向作業系統呈現為 SCSI 磁碟45。
  • 協定層較少使其快速輕量；AoE 規格僅 12 頁，而 iSCSI 為 257 頁（RFC 3720）45。
  • 不可路由是其唯一的安全機制；沒有 AoE 專屬的密碼/加密機制，以 MAC 為基礎的存取清單（"masks"）可被偽造，最安全的做法是使用 VLAN 隔離45。
  • Linux 自 kernel 2.6.11+ 原生支援；Windows/Mac/BSD 透過第三方驅動（如 WinAoE、WinVBlock）45。

7.4 NBD（Network Block Device）#

NBD 是 Linux 上的網路協定，可將一部機器的區塊裝置（通常為硬碟或分割區）轉發給另一部機器，使本機得以存取另一部電腦上的磁碟46。它最初為 Linux 2.1.55 開發、於 1997 年釋出，2011 年重新修訂並正式文件化，現為協作式開放標準46。依核心文件：「Linux can use a remote server as one of its block devices... This can be used for stations with low disk space (or even diskless) to borrow disk space from another computer. Unlike NFS, it is possible to put any filesystem on it」；nbd 核心模組只需裝在客戶端，nbd-server 完全在使用者空間執行47。

7.5 無磁碟開機框架：LTSP 與 DRBL#

LTSP（Linux Terminal Server Project） 是免費/開源的 Linux 終端伺服器，由 Jim McQuillan 於 1999 年創立，採 GPLv3；其客戶端開機流程為：伺服器上建立 chroot 環境 → 客戶端以 PXE 取得核心與 initrd（透過 TFTP）→ initrd 要求 DHCP IP 與根檔案系統伺服器位址 → 客戶端透過 NFS 或 NBD 掛載根檔案系統48。LTSP 4 使用 XDMCP 與 NFS 根目錄；LTSP 5（"MueKow"）使用 NBD 或 NFS 與經 SSH 通道的 LDM48。

DRBL（Diskless Remote Boot in Linux） 是 NFS/NIS 伺服器，提供客戶端無磁碟或無系統環境，由台灣國家高速網路與計算中心（NCHC）自 2003 年起開發49。客戶端設定以 PXE 或 Etherboot 從網卡開機，向 DRBL 伺服器要求 IP 與 TFTP 映像，經 TFTP 開機初始 RAM disk 後掛載 NFS 分享作為根（/）分割區49。DRBL 自 1.6.3+ 有四種模式：Full DRBL、Full Clonezilla、DRBL SSI（Single System Image）與 Clonezilla Box50。官方強調「DRBL does NOT touch the client hard drives, therefore, other operating systems (e.g. MS Windows) installed on the client [remain intact]」50。

7.6 無狀態 / RAM 開機#

依 Linux 核心文件，initramfs 是連結進核心映像的 gzip cpio 壓縮檔，開機時被解壓至 rootfs；若其中含 /init，該程式以 PID 1 執行，負責尋找並掛載真正的根裝置（可能位於網路上，需要 DHCP 等）51。這個「early userspace」階段正是 NFS/iSCSI/AoE/NBD 根目錄掛載的起點51。

無狀態（stateless）RAM 開機通常指客戶端透過網路下載完整作業系統映像、載入 RAM 並完全從記憶體執行；由於映像被複製到 RAM，操作期間的任何變更（由使用者、蠕蟲或病毒造成）「can be either wiped out when the power is removed... or prohibited entirely (if the image is a network filesystem)」，因此非常適合圖書館、學校等公共使用環境3。常見的無狀態混合做法是唯讀共用根目錄搭配本地 overlay：共用唯讀根檔案系統作為每個節點的範本，本地寫入的檔案存於節點記憶體並於重開機後消失52。

7.7 根檔案系統取得方式比較#

這些方法共同的模式是：DHCP 告訴客戶端何處可找到開機程式；TFTP 傳送核心與 initramfs；initramfs 的 early userspace init 接著掛載真正的根目錄——無論是網路檔案系統（NFS）、網路區塊裝置（iSCSI/AoE/NBD）或記憶體中的 RAM disk（無狀態）2413。

9. 實作範例：以 dnsmasq + iPXE + HTTP 建立網路開機伺服器#

現代實務上常見的架構是「三檔案系統」：dnsmasq 負責 proxy-DHCP 與 TFTP（同一份輕量設定），iPXE 由笨拙的韌體 PXE ROM 鏈式載入後接手真正的 HTTP 傳輸，網頁伺服器則提供大型檔案（核心、initrd、ISO、腳本）63。

選擇此模式的原因：TFTP 是 1981 年的 lock-step 一次一封包協定，對於約 1 MB 的 iPXE 二進位檔尚可，但對 60 MB 的 initrd 而言是折磨；一旦 iPXE 開始運作，所有大型檔案都改用 HTTP 提供63。

9.1 前置準備#

伺服器需有靜態 IP（例如 192.168.1.2），且每個客戶端都能在第二層觸及它（PXE 以廣播為基礎；須同 VLAN 或使用 DHCP relay）63。安裝套件：

# Debian/Ubuntu
sudo apt update && sudo apt install dnsmasq ipxe nginx

# RHEL/Fedora
sudo dnf install -y dnsmasq ipxe-bootimgs nginx

需注意：dnsmasq 預設設定會啟用 DNS 伺服器，若只想要 PXE，應以 port=0 明確停用 DNS63。

9.2 決定 proxy-DHCP 或完整 DHCP#

  • Proxy-DHCP — dnsmasq 與既有 DHCP 伺服器（路由器/pfSense/UniFi）並存，只回應 PXE 特定部分，既有伺服器仍負責發放 IP。若你已有不想汰換的 DHCP 伺服器（幾乎所有人），應採用此模式63。
  • 完整 DHCP — dnsmasq 也負責發放 IP，需停用路由器上的 DHCP。僅在你已用 Linux 伺服器提供 DHCP，或建置全新網段時採用63。

9.3 dnsmasq 設定（同時服務 UEFI 與 BIOS）#

客戶端在 DHCP Option 93（client-arch） 宣告其架構，dnsmasq 據此標記並發送正確開機檔63。建立 /etc/dnsmasq.d/pxe.conf：

# ---- 關閉 DNS：我們只要 proxy-DHCP + TFTP ----
port=0

# 偵錯期間記錄 DHCP/TFTP 交易（之後可註解掉）
log-dhcp

# ---- Proxy-DHCP ----
# 在本子網公告 PXE 服務但不發放位址，",proxy" 是關鍵字
dhcp-range=192.168.1.0,proxy

# ---- TFTP ----
enable-tftp
tftp-root=/srv/tftp

# ---- 依架構（DHCP Option 93）選擇開機檔 ----
dhcp-match=set:bios,option:client-arch,0      # 傳統 BIOS
dhcp-match=set:efi64,option:client-arch,7     # x86-64 UEFI
dhcp-match=set:efi64,option:client-arch,9     # x86-64 UEFI（替代碼）
dhcp-match=set:efi32,option:client-arch,6     # x86（IA32）UEFI（少見）

# BIOS 客戶端：鏈式載入 BIOS iPXE 二進位檔
dhcp-boot=tag:bios,undionly.kpxe

# UEFI x86-64 客戶端：鏈式載入 EFI iPXE 二進位檔
dhcp-boot=tag:efi64,ipxe.efi

# 已執行 iPXE 的客戶端會以 option 175 自我標記。
# 將它們指向 HTTP 選單，而非另一個 iPXE 二進位檔——這能打破開機迴圈。
dhcp-match=set:ipxe,175
dhcp-boot=tag:ipxe,http://192.168.1.2/boot.ipxe

最後兩行是常被遺漏的部分；若省略，症狀是無限迴圈：韌體載入 iPXE → iPXE 重做 DHCP → dnsmasq 又叫它載入 iPXE → 永遠循環。iPXE 以 DHCP Option 175 自我識別；比對後對已是 iPXE 的客戶端改發 HTTP 選單即可63。

若偏好不使用顯式 iPXE 鏈式載入的單行做法，dnsmasq 亦支援 pxe-service 指令63：

pxe-service=x86PC,"PXELINUX (BIOS)",bios/lpxelinux
pxe-service=X86-64_EFI,"PXELINUX (EFI)",efi64/syslinux.efi

9.4 放置 iPXE 二進位檔並啟動#

sudo mkdir -p /srv/tftp
sudo cp /usr/lib/ipxe/undionly.kpxe /srv/tftp/   # BIOS
sudo cp /usr/lib/ipxe/ipxe.efi      /srv/tftp/   # UEFI x86-64
sudo systemctl restart dnsmasq
sudo ss -ulnp | grep -E ':(67|69)\b'

若主機板的 UEFI 拒絕 ipxe.efi，可改編譯 snponly.efi（使用韌體自身網路驅動的 SNP 介面），它在完整驅動版本失敗時往往可用63：

sudo apt install build-essential liblzma-dev git
git clone https://github.com/ipxe/ipxe.git
cd ipxe/src
make bin-x86_64-efi/snponly.efi
sudo cp bin-x86_64-efi/snponly.efi /srv/tftp/ipxe.efi

9.5 iPXE 選單腳本#

撰寫 /var/www/html/boot.ipxe（dnsmasq 指向 iPXE 客戶端的 URL）63：

#!ipxe

:start
menu PXE netboot
item --gap --             Install
item install_manual       Install Debian (manual, normal installer)
item install_auto         Install Debian (unattended preseed)
item --gap --             Other
item rescue               Installer rescue mode
item shell                iPXE shell
item exit                 Boot from local disk
choose --default install_manual --timeout 10000 target && goto ${target}

:install_manual
kernel http://192.168.1.2/debian/linux
initrd http://192.168.1.2/debian/initrd.gz
boot

:install_auto
kernel http://192.168.1.2/debian/linux
initrd http://192.168.1.2/debian/initrd.gz
imgargs linux auto=true priority=critical interface=auto \
  url=http://192.168.1.2/preseed.cfg \
  hostname=debian domain=lan
boot

此處有刻意的設計選擇：預設選項是手動安裝、而非無人值守安裝；無人值守安裝會無確認地清除磁碟，你絕不希望一次誤觸的網路開機默默重新格式化機器；破壞性選項只差一次按鍵，但絕不成為預設63。

若要依 MAC 自動安裝，以安全的下墜邏輯分支63：

#!ipxe
iseq ${net0/mac} 52:54:00:ab:cd:01 && goto auto_nvme ||
iseq ${net0/mac} 52:54:00:ab:cd:02 && goto auto_sda  ||
goto start        # 未知機器進入安全的手動選單

9.7 UEFI Secure Boot 現實#

  • iPXE 未由 Microsoft 簽署。啟用 Secure Boot 時，韌體會拒絕執行未簽署的 ipxe.efi，出現安全違規而開機失敗，沒有任何 iPXE 旗標能解決63。
  • 三條實際路徑63：
    1. 安裝時停用 Secure Boot，安裝後再啟用（家用/實驗室最常見）。
    2. 鏈式載入已簽署的開機程式（Microsoft 簽署的 shimx64.efi + 發行版簽署的 grub），全程保持 Secure Boot，但失去 iPXE 的腳本/HTTP 能力。
    3. 自行登錄 MOK 金鑰並簽署 iPXE 二進位檔，最純粹但擴展性差。
  • 另一項 UEFI 陷阱：某些韌體只有在明確啟用網卡的 "UEFI network stack" / "IPv4 PXE" 選項時才會以 UEFI 模式 PXE 開機，且部分主機板會將 BIOS 式與 UEFI 式網路開機列為不同的開機選單項目63。

10. 安全性考量#

10.1 風險#

未加密的 TFTP / PXE 無認證：Intel 指出「PXE has no mechanism for encryption or authentication, is susceptible to man-in-the-middle attacks... The TFTP & UDP transactions associated with PXE may be the last unencrypted traffic on your network and are trivial to intercept」，此開機流程違背當今網路的「零信任」概念17。

流氓 DHCP / proxyDHCP：由於 DHCP 無認證，網段上任何主機都可冒充 DHCP 伺服器並注入惡意設定。CISA 的 ATT&CK 條目 DHCP Spoofing（T1557.003） 描述：「Adversaries may spoof as a rogue DHCP server on the victim network, from which legitimate hosts may receive malicious network configurations」，攻擊者可藉此取得中間人（adversary-in-the-middle）位置64。

中間人攻擊（MITM）：TFTP 傳輸未經認證與加密，同網段攻擊者可攔截或修改開機流量65。

開機映像竄改 / 憑證洩漏：Bureau Veritas 的滲透測試報告顯示，由於 PXE 使用無認證的 TFTP，攻擊者可掛載 WinPE 映像、下載 .wim 並以 wimlib-imagex 掛載，進而擷取 Unattend.xml、Bootstrap.ini（含部署分享位置與憑證）與 VARIABLES.DAT（含 base64 編碼的 USERID、USERDOMAIN、USERPASSWORD），並以這些憑證列舉網域分享66。

10.2 緩解措施#

UEFI Secure Boot 限制開機流程只能執行受信任金鑰簽署的程式碼，多數現代 UEFI 系統預設啟用22。需注意 iPXE 專案對此頗有微詞，稱 Secure Boot 是「primarily a form of pay-to-play security theatre. Unless you are prepared to manage your own keys... there are no meaningful restrictions on the code that can be signed, or on who can perform the signing」69。

HTTPS Boot 於 UEFI 規格 2.5 版引入，結合 DHCP、DNS 與 HTTP 並加入 TLS；Linaro 說明其安全效益為「In contrast to legacy protocols like PXE, Booting over HTTPS upholds modern security standards such as HTTPS and certificate validation」70。

802.1X 確保只有經認證/授權的裝置能連上網路。由於 PXE 必須在任何作業系統認證客戶端之前執行，Cisco 特別為此情境記錄了 IEEE 802.1X Open Authentication：「allows a host to have network access without having to go through IEEE 802.1X authentication. Open authentication is useful in an applications such as the Preboot Execution Environment (PXE), where a device must access the network to download a bootable image containing an authentication client」67。Cisco 亦記錄搭配 Pre-Auth ACL 的 Low Impact Mode，在認證完成前只允許 DHCP、DNS 與 TFTP 流量67。

DHCP snooping 是 Layer 2 交換器功能，區分受信任埠（合法 DHCP 伺服器所在）與非受信任埠（終端裝置）；交換器維護記錄 MAC、IP、租約時間與 VLAN 的綁定表，用以驗證 DHCP 訊息，可防止 DHCP spoofing、DHCP starvation 與中間人攻擊68。它與 Dynamic ARP Inspection（DAI）及 IP Source Guard 搭配運作，後兩者消費 DHCP snooping 綁定表68。

簽署開機映像：即使有 HTTPS 傳輸安全，開機內容本身仍應簽署，讓客戶端可驗證完整性與真實性。實務上透過 UEFI Secure Boot 信任鏈達成；Microsoft 的部署堆疊即要求開機映像必須由客戶端 NVRAM 中受信任的 CA 簽署，已撤銷 2011 年憑證的強化系統會拒絕以舊 CA 簽署的 SCCM 開機映像，直到重新以 2023 年憑證簽署71。

iPXE 與 Secure Boot shim：標準 iPXE 二進位檔未由 Microsoft UEFI Secure Boot CA 信任的金鑰簽署，因此會被啟用 Secure Boot 的韌體拒絕。iPXE 專案透過信任鏈解決69：

  1. Shim — 由 Microsoft 第三方 UEFI CA 簽署的小型開機程式（ipxe/shim），客製為信任 iPXE Secure Boot CA。
  2. 已簽署的 iPXE — shim 驗證並啟動以 iPXE Secure Boot CA 憑證簽署的 ipxe.efi。
  3. autoexec.ipxe — iPXE 開始運作後載入開機腳本。

iPXE 文件說明 DHCP 設定應將 filename 指向 shim（如 ipxe-shim.efi）而非 iPXE 二進位檔本身：「The Secure Boot shim (e.g. ipxe-shim.efi or snponly-shim.efi) will automatically load the iPXE binary with the corresponding name」69。對 Linux，iPXE 的 shim 指令會交棒給發行版自己的簽署 shim（如 shimx64.efi / BOOTX64.EFI），且「will silently do nothing if UEFI Secure Boot is disabled」72。限制：由於任何修改都會使簽章失效，已簽署的 iPXE 版本無法客製——imgverify 不可用、佈景主題遺失，且「You cannot compile your own iPXE binary with additional features and have it trusted by the Secure Boot shim」；端到端 Secure Boot 網路開機目前限於有發布簽署網路開機 shim 的發行版（Debian 系列：Debian、Devuan、Kali）69。
