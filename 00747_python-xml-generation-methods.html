用 Python 產生 XML 檔案的方法比較：指令式節點、樣板引擎與 JSX 風格語法#

本報告調查「在 Python 中產生（寫出）XML 檔案」的主要技術路線。內容涵蓋標準函式庫、lxml、產生器（builder）DSL、樣板引擎，以及字典與資料模型轉 XML 等家族，並就正確性、安全性、效能與維護狀態提出可查證的事實與選用建議。

所有事實均附註腳與 APA 格式參考文獻，參考文獻日期採 ISO 8601（YYYY-MM-DD）。查核日期為 2026-11-14。

1. 摘要：分層的結論#

若把「產生 XML」拆成三件事：正確性（escape、編碼、namespace、CDATA）、規模（是否需要串流）、可讀性（程式碼是否好寫好讀），可得以下結論：

  1. 機器對機器、需要 schema 保證的情境，應使用 DOM 或節點 API，首選 xml.etree.ElementTree 或 lxml.etree。序列化器會自動處理 escape，且建構出來的樹可再送進 schema 驗證器12。
  2. 需要極大檔案（GB 級）或無法保證記憶體上限時，應使用串流（incremental）產生：lxml.etree.xmlfile 或 xml.sax.saxutils.XMLGenerator34。
  3. 純字串拼接（f-string、%、str.join）是唯一「保證錯誤」的做法。它不會 escape，直接對應 CWE-91 XML Injection 的定義5。
  4. 樣板引擎（Jinja、Mako、Genshi、Chameleon）適合「文件導向」產物（HTML、SVG、報表、RSS）。用在機器交換格式時，escape 正確性取決於樣板作者是否在每個上下文正確使用過濾器，且缺乏 schema 驗證67。
  5. JSX 風格與純函式 builder 家族（lxml.builder.E、yattag、dominate、htbuilder）提供最佳的可讀性與「就是 Python」的組合性，代價是額外相依，且多數專案社群規模較小891011。
  6. dict 轉 XML 的工具（dicttoxml、xmltodict.unparse）無法保證保真。官方文件自承「僅涵蓋常見的 90% 情境」，屬性順序、混合內容順序、多重頂層註解都不保留12。dicttoxml 自 2022-12-23 起未再更新13。

2. 標準函式庫路線#

2.1 xml.etree.ElementTree：多數情境的預設答案#

官方文件對這個模組的第一句描述是「實作簡單且有效率的 API，用於解析與建立 XML 資料」1。自 Python 3.3 起，該模組「只要可用就會使用快速實作」，而 xml.etree.cElementTree 別名自 3.3 起被棄用1。

建立節點的核心是 Element 與 SubElement：

import xml.etree.ElementTree as ET

root = ET.Element("catalog")
book = ET.SubElement(root, "book", {"id": "1"})
book.text = "Python"
ET.SubElement(book, "price").text = "9.99"

tree = ET.ElementTree(root)
tree.write("out.xml", encoding="utf-8", xml_declaration=True,
           short_empty_elements=True)

SubElement(parent, tag, /, attrib={}, **extra) 的簽章在 Python 3.15 有兩項變更：attrib 可為 frozendict，且 parent 與 tag 改為僅位置參數（positional-only）1。

序列化參數方面，ElementTree.write() 的簽章為 write(file, encoding='us-ascii', xml_declaration=None, default_namespace=None, method='xml', *, short_empty_elements=True)，其中1：

  • xml_declaration：False 表示永不輸出宣告、True 表示一定輸出、None（預設）表示「只有在編碼不是 US-ASCII 或 UTF-8 或 Unicode 時才輸出」。
  • encoding：預設 us-ascii。tostring() 另支援 encoding="unicode" 以取得 str 而非 bytes1。
  • method：可為 "xml"、"html"、"text"。
  • short_empty_elements：Python 3.4 新增。True（預設）輸出 <a/>，False 輸出 <a></a>1。

tostring() 的簽章為 tostring(element, encoding='us-ascii', method='xml', *, xml_declaration=None, default_namespace=None, short_empty_elements=True)。其中 xml_declaration 與 default_namespace 為 Python 3.8 新增，short_empty_elements 為 3.4 新增1。

美化輸出有兩種機制，語意不同：

  • xml.etree.ElementTree 沒有 pretty_print 參數。標準函式庫提供的是 indent()。
  • xml.etree.ElementTree.indent(tree, space=' ', level=0) 於 Python 3.9 新增，文件說明為「對子樹附加空白以在視覺上縮排，可用於產生美化輸出」，space 預設為兩個空白1。注意它修改樹本身（把空白寫進 text 與 tail），因此必須在序列化之前呼叫。

namespace 行為：以 Clark 表示法 {uri}local 建立的標籤在序列化時，會查詢全域註冊表 register_namespace(prefix, uri)（Python 3.2 新增）。文件說明「註冊表是全域的，任何既有對應（無論是該 prefix 或該 URI）都會被移除」，且「此 namespace 中的標籤與屬性會盡可能以給定 prefix 序列化」1。若沒有註冊，序列化器會自行合成 ns0、ns1 這類前綴。

escape 行為與其極限（最常被誤解的部分）：

  • 序列化時，ElementTree 對文字內容會 escape &、<、>；對屬性值則另外 escape " 與 '1。
  • 但標準函式庫不驗證、也不 escape 非法的控制字元。Python 3.15 才新增 xml.is_valid_text(data) 這類檢查函式，其文件說明合法 XML 1.0 字元「幾乎都可使用，除了 C0 控制字元（不含 TAB、CR、LF）、代理對（surrogate）字元與特殊 Unicode 字元 U+FFFE、U+FFFF」14。換言之，寫入端並不會替你擋掉這些字元，你必須自己驗證或清理。
  • 打錯字元的代價是產出無法解析的文件，而不是例外。這正是「序列化器有 escape 但仍需輸入驗證」的原因5。

CDATA：xml.etree.ElementTree 的序列化器沒有產生 <![CDATA[ ... ]]> 的機制，文件中亦未提供。若一定要 CDATA，需改用其他方案（見 3.3 與 4.1）。同一頁文件另指出解析端「目前會跳過 XML 註解、處理指令與文件類型宣告」，但用 API 手動插入的註解與處理指令會被輸出1。

TreeBuilder 的定位：文件說明它是「泛用元素結構建構器，把一連串 start、data、end、comment、pi 呼叫轉換為良構（well-formed）的元素結構。可用它搭配自訂解析器建立元素結構」1。它是解析端的 target，不是產生工具，也不解決串流寫出的問題。

其他版本重點：

  • canonicalize(xml_data=None, *, out=None, from_file=None, **options) 為 C14N 2.0 轉換函式，Python 3.8 新增。選項含 with_comments、strip_text、rewrite_prefixes、qname_aware_tags、qname_aware_attrs、exclude_attrs、exclude_tags1。
  • iterparse() 與 XMLPullParser 皆為解析端工具。文件明講 iterparse() 的樹「只是逐步建構，並非逐步釋放」1。
  • Python 3.13 為 iterparse() 迭代器新增 close()。3.15 起若迭代器開啟檔案卻未明確關閉，會發出 ResourceWarning1。
  • Python 3.14 起，對 Element 取真假值（truth value）被棄用15。

2.2 xml.dom.minidom：可用但官方已引導使用者改道#

minidom 是 DOM 的最小實作。文件第一段就寫明：「並非已熟悉 DOM 的使用者，應考慮改用 xml.etree.ElementTree 模組來處理 XML」16。它的實用價值在於兩點：

  • Node.writexml(writer, indent='', addindent='', newl='', encoding=None, standalone=None)：indent 是當前節點縮排、addindent 是子節點的遞增縮排、newl 是換行字串。Python 3.8 起保留使用者指定的屬性順序，3.9 新增 standalone16。
  • Node.toprettyxml(indent='\t', newl='\n', encoding=None, standalone=None)：回傳美化後的文件，indent 預設為 tab16。

已知缺陷（文件自承）：DOMException 未被支援，改用一般 Python 例外如 TypeError、AttributeError。DOMTimeStamp 與 EntityReference 未實作。removeAttribute() 與 removeAttributeNS() 在找不到屬性時會拋 NotFoundErr，與 DOM 規格「無作用」的規定不同16。此外 xml.dom 本身並未被標記為棄用（被棄用的是 xml.etree.cElementTree）141。

2.3 xml.sax.saxutils：真正的串流寫出工具#

標準函式庫中唯一「以事件驅動方式寫出 XML」的官方機制，是 XMLGenerator。其建構子為 XMLGenerator(out=None, encoding='iso-8859-1', short_empty_elements=False)。文件敘述：「此類別實作 ContentHandler 介面，把 SAX 事件寫回一份 XML 文件。換句話說，以 XMLGenerator 作為 content handler 會重現被解析的原始文件。out 應為 file-like 物件，預設 sys.stdout。encoding 預設 iso-8859-1。short_empty_elements 控制無內容元素的格式：False（預設）輸出成對的起訖標籤，True 輸出單一自閉合標籤。」short_empty_elements 於 3.2 新增4。

注意此處的預設值與 ElementTree 相反（XMLGenerator 預設 False，ElementTree 預設 True）41。

兩個配套的 escaping 函式4：

  • escape(data, entities={})：escape &、<、>。可傳入 entities 字典做額外替換，且「&、<、> 即使提供了 entities 也一律會被 escape」。文件特別警告：「此函式只應用於 escape 那些無法直接用在 XML 中的字元，不要當成一般字串轉換函式使用。」
  • quoteattr(data, entities={})：類似 escape()，但額外把資料準備成屬性值。它會依內容挑選引號字元以盡量避免編碼引號。若資料中同時有單引號與雙引號，會把雙引號編碼並以雙引號包住。

xml.sax 套件本身只文件化解析端（reader、handler、input source），沒有「用 SAX 事件寫出 XML」的獨立 API。寫出必須靠 saxutils.XMLGenerator174。

3.1 序列化與美化輸出#

lxml.etree.tostring() 支援 encoding、method（'xml'、'html'、'text'、'c14n'、'c14n2'）、xml_declaration、pretty_print、with_tail、standalone、doctype、exclusive、inclusive_ns_prefixes、with_comments、strip_text 等參數。ElementTree.write() 另支援 compression（GZip level 1 至 9）2。

pretty_print 的行為在官方 FAQ 有明確界定：美化輸出「意味著對內容加入空白」，而實作會「只在不會影響資料的情況下加入空白，也就是只在不含資料的節點之間」。若資料是從檔案解析而來且含無意義空白，須先用 remove_blank_text=True 解析，讓解析器丟掉空白文字節點，之後序列化時才能安全縮排22。

lxml 另有 etree.indent(root)（4.5 新增），它會改變記憶體中的樹（呼叫後 root.text 變成 '\n '）。此點與 pretty_print 只在輸出階段加空白不同23。

CDATA 方面，lxml 的解析器預設會剝除 CDATA 並以純文字取代（strip_cdata=True）。若要保留，需 etree.XMLParser(strip_cdata=False)。若要主動產生 CDATA，使用 etree.CDATA 工廠包裝文字3：

from lxml import etree

el = etree.Element("content")
el.text = etree.CDATA("a & b")
print(etree.tostring(el, encoding="unicode"))
# <content><![CDATA[a & b]]></content>

文件同時提醒一個陷阱：「注意 .text 屬性並不會給出任何提示，說明該文字內容被 CDATA 包裹」3。

3.2 C14N（Canonical XML）與數位簽章#

lxml.etree 支援 C14N 1.0 與 C14N 2.0：「以 ElementTree.write() 或 tostring() 序列化 XML 樹時，可傳入 method="c14n"（1.0）或 method="c14n2"（2.0）。此外有 etree.canonicalize()，可在不於記憶體中建立樹的情況下，把已序列化的 XML 轉成標準形式。」3 例如：

c14n_xml = etree.canonicalize("<root><test z='1' y='2'/></root>")
print(c14n_xml)   # <root><test y="2" z="1"></test></root>

標準函式庫的 xml.etree.ElementTree.canonicalize() 文件則說明了為何這件事對簽章重要：「標準化是讓 XML 輸出一致化，使位元組級比較與數位簽章成為可能。它削減了 XML 序列化器的自由度。主要限制關於 namespace 宣告的位置、屬性的排序，以及可忽略的空白。」1 這也是「以字串或樣板拼接 XML 之後再去簽章」會踩雷的根本原因：屬性順序或空白的任何差異都會改變標準化位元組，導致簽章驗證失敗31。

3.3 增量與串流產生：lxml.etree.xmlfile#

自 lxml 3.1 起提供 xmlfile API，以 with 陳述式增量產生 XML。官方說明其目的：

「其主要目的是自由且安全地把外圍元素與已建好的記憶體中樹混合，例如寫出由大量重複子樹組成的文件（如資料庫傾印）。但在記憶體用量重要、或 XML 天然是按序列步驟產生的許多情況下，它都很有用。」

以及關鍵的記憶體論述：「一種常見模式是有數個巢狀的 element() 區塊，然後在迴圈中建立記憶體中的 XML 子樹，並逐一寫入 XML 檔。如此一來，它們在建立後即可從記憶體移除。這可大幅降低應用程式的記憶體足跡，同時讓整體 XML 產生保持簡單、安全且正確。」3

參數與版本：close=True（3.4 起）讓 lxml 在離開 context manager 時呼叫物件的 .close()。buffered=False（3.4 起）完全停用緩衝。xf.flush()（3.4 起）可明確沖出緩衝內容。3.4.1 起另有對應的 htmlfile。4.0 起支援 async coroutine3。

from lxml import etree

with etree.xmlfile("big.xml", encoding="utf-8") as xf:
    xf.write_declaration(standalone=True)
    with xf.element("dump"):
        for row in rows:                  # rows 可為產生器
            el = etree.Element("row", id=str(row.id))
            el.text = row.value
            xf.write(el)
            el = None                     # 立即讓它可被回收

3.4 驗證：把「產出的東西對不對」變成可執行檢查#

lxml.etree 提供 DTD、RelaxNG、XMLSchema、Schematron 四個驗證器類別，皆提供 validate(etree)（回傳 True 或 False）、assertValid(etree)（失敗時拋 DocumentInvalid）、assert_()（失敗時拋 AssertionError），以及 error_log 屬性以讀取錯誤細節2。這是「產生 XML」這一側最容易被忽略、但效益最高的一步：在寫檔或送出前，用同一份 XSD 驗證自己產出的樹。

3.5 解析器安全預設值#

lxml.etree.XMLParser 的預設值包含 no_network=True（阻止網路存取相關檔案）、resolve_entities='internal'、strip_cdata=True2。FAQ 指出：「自 5.x 版起，lxml 預設停用外部實體展開（XXE）。若你確實想允許以該功能把外部檔案載入 XML 文件，必須明確設定 resolve_entities=True。」22 另有一則官方說明指出 resolve_entities 的預設值原本是 True，在 lxml 6.1 改為 'internal'2。

需要留意的是，lxml 6.1.3 的版本說明提到一個已修正的問題：外部參數實體（external parameter entity）在 resolve_entities="internal" 下仍被允許解析19。這代表「版本升級」本身就是安全維護的一部分。

4.1 lxml.builder.E（E-factory）#

不需要額外安裝（已含於 lxml）。文件定義其價值：「與一般 Element 工廠不同，E 工廠允許你傳入的不只是標籤與一些可選屬性。你還可以傳入文字與其他元素。文字會被加為 text 或 tail，元素會被插到正確位置。」8

from lxml import etree as ET
from lxml.builder import E

ET.tostring(E("tag", "text", key="value"))
# b'<tag key="value">text</tag>'
ET.tostring(E("tag", E("subtag", "text"), "tail"))
# b'<tag><subtag>text</subtag>tail</tag>'

namespace 可透過 ElementMaker(namespace=..., nsmap=...) 設定。from lxml.builder import E 取得的即是 ElementMaker 的單例8。文件中的 HTML 產生範例也示範了如何用小型 helper（例如 CLASS(v) 回傳 {'class': v}，因為 class 是 Python 保留字）與 E.p(...) 混搭8。

4.6 真正的 JSX 風格與 t-string：PEP 750#

Python 3.14 引入了 template strings（t-strings）。PEP 750 狀態為 Final，對應 Python 版本為 3.1429。語法是在字串前加 t：

from string.templatelib import Template

name = "World"
template: Template = t"Hello {name}"
assert template.strings[0] == "Hello "
assert template.interpolations[0].value == "World"

Template 具有 strings 與 interpolations 兩個屬性。Interpolation 具有 value、expression、conversion、format_spec29。PEP 明言此機制的動機之一是安全：

「f-strings 沒有辦法在插值被合併進最終字串之前攔截並轉換它們。因此，f-strings 的不謹慎使用可能導致安全漏洞。」（PEP 以 SQL injection 與 XSS 為例）

PEP 亦給出 HTML 範例，其中 html() 處理器會 escape 插值，使 t"<p>{evil}</p>" 變成 <p>&lt;script&gt;...&lt;/script&gt;</p>29。同時 PEP 明確說明它不是要靠來取代 Jinja：「像 Jinja 這類專案在使用者自訂、設計師或內容創作者撰寫的樣板情境下仍有需要。PEP 750 設想的 DSL 是：非靜態的部分就是 Python，同樣的作用域規則、型別、運算式語法。」29

實務評價：t-strings 提供了一條「讓 escape 由處理器集中負責」的正規管道，是 Python 官方對「別再手動拼接 XML 或 HTML」的語言層回應。但它本身不是 XML 產生器，仍需自行實作處理器。

4.7 語法風格對照#

以下用同一份結構（含屬性與巢狀子元素）示範四種風格，突顯可讀性差異。

風格 A：指令式節點（ElementTree）

root = ET.Element("order", {"id": "A1"})
item = ET.SubElement(root, "item", {"sku": "X"})
ET.SubElement(item, "qty").text = "2"

風格 B：E-factory（lxml.builder）

root = E.order({"id": "A1"}, E.item({"sku": "X"}, E.qty("2")))

風格 C：context manager（yattag）

doc, tag, text = Doc().tagtext()
with tag("order", id="A1"):
    with tag("item", sku="X"):
        with tag("qty"):
            text("2")

風格 D：純函式與索引（htbuilder）

root = order(id="A1")[ item(sku="X")[ qty("2") ] ]

四者的共同優點是屬性與文字都由函式參數進入，而非字串插值，因此 escape 由函式庫負責18911。差別在於：A 與 B 產生標準 XML 樹物件（可驗證、可 XPath、可序列化為多種方法），C 與 D 產生字串（輕量但沒有結構可驗證）2911。

5.1 Jinja#

  • 官方文件版本標示為 3.1.x。GitHub pallets/jinja 有 11,816 stars，授權 BSD-3-Clause，最近一次 push 為 2025-06-143031。
  • 文件名言：「Jinja 樣板就是一個文字檔。Jinja 可以產生任何以文字為基礎的格式（HTML、XML、CSV、LaTeX 等）。樣板不需要特定副檔名。」6

關鍵選項與過濾器（皆為官方文件用語）326：

  • autoescape：設為 True 即預設啟用 XML 與 HTML 自動 escape。自 2.4 起亦可為一個 callable（接收樣板名稱、回傳 bool）。官方建議搭配 select_autoescape() 使用，並在文件中註記「未來版本的 Jinja 可能基於安全理由預設啟用自動 escape，因此建議現在就明確設定而不是依賴預設值」32。
  • xmlattr 過濾器：「既不是 none 也不是 undefined 的值會自動被 escape，因此可安全地接受不受信任的使用者輸入。」但另有一條限制：「使用者輸入不應作為此過濾器的鍵。若任何鍵含有空白、/、> 或 =，會以 ValueError 失敗。」6
  • tojson 過濾器：「把物件序列化為 JSON 字串，並標記為可安全在 HTML 中輸出。此過濾器僅供 HTML 文件使用。」並附警告：「回傳字串在 HTML 文件與 <script> 標籤中是安全的。例外是以雙引號包住的 HTML 屬性，此時應改用單引號或 |forceescape 過濾器。」6
  • 空白控制：trim_blocks（預設 False，移除區塊後的第一個換行）、lstrip_blocks（預設 False，移除行首到區塊前的空白與 tab）、newline_sequence（'\r'、'\n'、'\r\n'，預設 '\n'）、keep_trailing_newline（預設 False，會剝掉結尾單一換行）326。
  • SandboxedEnvironment：以沙箱方式產生程式碼，「若樣板試圖存取不安全的程式碼，會拋出 SecurityError」。另提供 ImmutableSandboxedEnvironment 等變體7。
  • 最值得引用的一段警告（在沙箱安全性考量中）：「Jinja 只產生文字，它不瞭解例如 JavaScript 程式碼。取決於樣板輸出將如何被使用，你可能需要做其他後處理來限制輸出。」7 這句話正是「autoescape 不等於端到端安全」的官方表述。

5.6 樣板引擎用於 XML 的結構性弱點#

把上述引擎放回「產生 XML」的脈絡，會看到三個共同限制：

  1. 樣板引擎不知道自己在哪個上下文插值。同一個 {{ v }} 可能落在文字節點、屬性值、標籤名或 CDATA 中，而這四個位置需要不同的 escape 規則75。
  2. 樣板輸出是字串，不是樹。因此無法直接送進 XMLSchema、RelaxNG 或 Schematron 驗證器做「產生前驗證」，除非再解析一次2。
  3. 對簽章類用途不友善。屬性順序與空白的差異會改變 C14N 結果13。

不過，第 5.3 與 5.4 節的 Genshi 與 Chameleon 是一個例外方向：它們要求樣板本身是良構 XML，因此「標籤層級的結構錯誤」會被解析器在編譯期就擋下，這是純文字樣板（Jinja、Mako）沒有的保護3537。

6.4 JSON 轉 XML 為何不可逆#

若工作流是「先有 JSON，再轉 XML」，須知道這個轉換本質上是有損的。差異來源是 XML 具備 JSON 沒有的特性48：

  • 屬性：XML 元素可同時有屬性與子內容，JSON 沒有原生屬性概念。慣例（如 @attr 前綴）是任意的。
  • namespace：XML 支援帶 namespace 的元素，JSON 沒有原生支援。
  • 混合內容：XML 允許文字與子元素交錯，JSON 沒有對應表示。
  • 註解與處理指令：XML 有 <!-- --> 與 <?pi?>，JSON 沒有。
  • CDATA：XML 有 <![CDATA[ ... ]]>，JSON 沒有對應。
  • 文件類型宣告：DTD 與 DOCTYPE 沒有 JSON 類比。
  • 順序：XML 元素順序有意義，JSON 物件鍵依規格無序。
  • 單一元素與複數元素：同一位置是單一子元素或陣列，各慣例處理方式不同。

具體慣例方面：BadgerFish 把元素名變物件屬性、文字內容放 $、屬性放在以 @ 開頭的屬性、namespace 放 @xmlns，而它的侷限是「若元素的文字內容全為空白會被丟棄」，且無法處理混合內容（例如 <p>text <strong>bold</strong> more text</p>）。Parker 慣例則是「有損的，它單純忽略 XML 屬性。優點是產生更精簡乾淨的 JSON」48。

實務建議：若需要 JSON 與 XML 之間的可靠往返，應在資料模型中顯式保留屬性、namespace 與順序的資訊，而不是依賴通用的轉換慣例4812。

7. 正確性與安全性#

7.1 escape 規則與其易錯處#

XML 1.0 對寫入端的最基本要求如下49：

  • & 與 < 在字元資料中必須 escape。
  • > 除特定情形外可不必 escape，但字面字串 ]]> 不得出現在字元資料中。
  • 屬性值中若以單引號或雙引號作定界，對應的引號字元必須 escape。
  • 五個預定義實體為 &lt;、&gt;、&amp;、&apos;、&quot;。

合法字元方面，XML 1.0 只接受 U+0009（tab）、U+000A（LF）、U+000D（CR）三個 C0 控制字元。其餘 U+0000 至 U+001F 控制字元、代理對區段（U+D800 至 U+DFFF）、U+FFFE 與 U+FFFF 皆不合法4914。XML 1.0 亦建議使用 UTF-8 且不要 BOM49。

研究限制聲明：W3C 規格頁（https://www.w3.org/TR/xml/）在本報告的抓取過程中回應失敗，因此上述規則係轉引自維基百科的 XML 條目與 Python 標準函式庫文件。兩者在相關段落互相一致4914。

寫在 Python 裡的實務含意是：

  • ElementTree 與 lxml 會替你 escape 文字與屬性中的關鍵字元12。
  • 但沒有任何一者會替你驗證控制字元。Python 3.15 才提供 xml.is_valid_text() 這個檢查函式，且它不是序列化器的自動行為14。
  • 且沒有任何一者會替你驗證標籤名稱。這正是前面 xmltodict 的 CVE 爭議核心12。

7.2 唯一不可原諒的做法：字串拼接#

CWE-91「XML Injection」的定義是：「產品未能適當中和 XML 中使用的特殊元素，使攻擊者可在 XML 被終端系統處理之前修改其語法、內容或指令。」其延伸說明直接點出：「XML 中的特殊元素可包括保留字或字元，例如 <、>、" 與 &，這些可被用來新增資料或修改 XML 語法。」標準的緩解策略列在 Input Validation 之下：「假設所有輸入都是惡意的。採用『接受已知良好』的輸入驗證策略，即使用一份嚴格符合規格的許可清單。拒絕任何未嚴格符合規格的輸入，或把它轉換成符合規格的東西。」5

CWE-91 在 CWE 階層中是 CWE-74（Improper Neutralization of Special Elements in Output Used by a Downstream Component）的子項，並擁有多個子項，包括 CWE-643（Improper Neutralization of Data within XPath Expressions）與 CWE-652（Improper Neutralization of Data within XQuery Expressions）5。它也被對應到 CAPEC-250（XML Injection）與 CAPEC-83（XPath Injection）5。

相關但不同的一個弱點是 CWE-611 XML External Entity（XXE）。XXE 主要被描述為解析端的風險（處理的 XML 文件可含指向控制範圍外文件的實體 URI），但它在「同時讀寫 XML 的管線」中同樣重要：若該管線會再解析使用者可控的 XML，其解析器設定就必須一併處理。標準緩解是「許多 XML 解析器與驗證器可設定為停用外部實體展開」50。OWASP 的建議更強硬：「盡可能停用文件類型定義（DTD）。若解析器支援，就拒絕 DOCTYPE 宣告。若應用真的需要 DTD，則停用外部實體解析與外部 DTD 載入，並限制實體展開。」並補充「除非明確需要，否則停用 XInclude，因為它可不經 DTD 就載入資源」51。

Python 標準函式庫的 xml 文件頁面在 XML security 一節列出四種攻擊型態14：

  • billion laughs 或指數實體展開：「使用多層巢狀實體。每個實體多次引用另一個實體，最終實體定義含一小段字串。指數展開會產生數 GB 的文字，消耗大量記憶體與 CPU 時間。」
  • quadratic blowup 實體展開：「與 billion laughs 類似，也濫用實體展開。它不採用巢狀實體，而是把一個含數千字元的大實體重複多次。效率不如指數情形，但它避免觸發禁止深層巢狀實體的解析器計數器。」
  • decompression bomb：「適用於所有能解析壓縮 XML 串流的 XML 函式庫，例如 gzip 化的 HTTP 串流或 LZMA 壓縮檔。」該頁並明確指出 xmlrpc 對此攻擊是脆弱的。
  • large tokens：「Expat 需要重新解析未完成的 token。若沒有 Expat 2.6.0 引入的保護，這可能導致二次方執行時間，被用來對應用程式造成阻斷服務。」此問題編號為 CVE-2023-52425。

該頁同時給出關鍵的版本資訊：「Expat 版本低於 2.7.2 可能對 billion laughs、quadratic blowup 與 large tokens 弱點脆弱，或對動態記憶體使用不成比例。」且「Python 綁定了一份 Expat。Python 使用綁定版或系統版，取決於組態設定。若 Python 使用這些較舊版本的 Expat，就可能脆弱。請檢查 pyexpat.EXPAT_VERSION。」另外「Expat 本身預設不存取本機檔案、也不建立網路連線」14。

7.3 產生端的安全檢查清單#

綜合以上，產生 XML 時真正需要自己動手做的是：

  1. 永不拼接字串。使用會 escape 的序列化器51。
  2. 驗證標籤名稱與屬性名稱。標準函式庫沒有提供這個工具，escape() 也不能用於此用途12。Python 3.15 新增的 xml.is_valid_name(name) 可用來檢查字串是否為合法的元素或屬性名稱14。
  3. 驗證文字內容中的控制字元。使用 xml.is_valid_text()（3.15 新增）或自行過濾 C0 控制字元14。
  4. 明確設定編碼與 XML 宣告。注意 xml_declaration=None 的「條件式輸出」行為可能讓下游在不同環境看到不同結果1。
  5. 需要簽章或位元組級一致性時，先做 C14N。屬性順序與可忽略空白的差異都會改變標準化位元組13。
  6. 若同時會解析 XML，務必關閉 DTD 與外部實體，並確認 Expat 版本511422。
  7. 用 schema 驗證產出。這是最直接、成本最低的正確性保證247。

  • xml.sax.saxutils.XMLGenerator 的寫出效能與 lxml 或 ElementTree 的比較。
  • xml.dom.minidom 的寫出效能基準（既有的 minidom 數據都是解析端）。
  • 樣板引擎渲染 XML 與程式化 DOM 建構之間的直接對比。
  • 各方法的產出檔案大小比較。

也就是說，「產生 XML」的效能領域，只有 lxml 對標準函式庫的序列化比較有官方數字20。

9. 取向建議#

9.1 決策表#

9.2 三個常見陷阱#

  1. 用 f-string 組 XML。這是最常見也最嚴重的錯誤，因為在簡單輸入下它「看起來會動」，直到某個欄位含 <、& 或控制字元514。
  2. 以為 autoescape=True 就安全。Jinja 官方文件自己就指出 Jinja 只產生文字、不瞭解輸出上下文，且 tojson 在雙引號屬性中需要額外處理76。
  3. 以為標準函式庫會驗證標籤名稱。它不會。這是 xmltodict CVE 爭議的技術核心，也是為什麼 escape() 不能拿來處理標籤名稱12。

9.3 何時「樣板引擎」是對的答案#

樣板引擎在這個問題上並非劣解，只是適用範圍不同：

  • 當輸出的主要消費者是人（HTML 頁面、報告、SVG 圖）時，樣板引擎的空白控制、繼承與巨集能大幅降低維護成本3237。
  • 當樣板作者與程式作者是不同人時，樣板語言的隔離價值就出現。PEP 750 對此的表述是：「像 Jinja 這類專案在使用者自訂、設計師或內容創作者撰寫的樣板情境下仍有需要。」29
  • 但當輸出是機器對機器、需要 schema 保證時，樣板引擎缺乏結構感知（它不知道自己在屬性、標籤名還是純文字中插值），這正是 autoescape 不足的根本原因75。

9.4 反面清單：不建議的作法#

  • 以 str.format 或 f-string 產生 <tag attr="{v}">：CWE-91 的直接成因5。
  • 使用 dicttoxml 作為交換格式產生器：它會自動加 type 屬性並改寫標籤名，且已逾三年未更新1342。
  • 把 xml.sax.saxutils.escape() 用於標籤名稱或屬性名稱：官方文件與 xmltodict 維護者都明確指出這會產生無效 XML412。
  • 在未做 C14N 的情況下對拼接而成的 XML 簽章：屬性順序與可忽略空白會改變標準化位元組13。
  • 依賴通用 JSON 到 XML 慣例做往返：BadgerFish 會丟棄全空白的文字內容且無法處理混合內容，Parker 則直接忽略屬性48。

10. 研究限制#

為使讀者能評估本報告的證據強度，以下列出查核過程中明確未能完成的部分：

  1. W3C 規格頁抓取失敗。https://www.w3.org/TR/xml/ 未能取得回應，XML 1.0 的 escape 與合法字元規則改以維基百科與 Python 標準函式庫文件互證4914。
