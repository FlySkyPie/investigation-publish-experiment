00555_canvas-ux-zoom-pan-lod

以 Web 技術實作可縮放、可拖曳的「畫布 UX」：Three.js 正交相機與 CSS2D/CSS3D Renderer 方案評估#

摘要#

本報告針對「畫布式使用者體驗（canvas UX）」需求進行研究：使用者需要能以滑鼠滾輪／觸控縮放（zoom in/out）並以拖曳移動視埠（viewport），如同 Web GIS 地圖操作，但操作對象是示意圖（diagram）或圖論圖（graph），而非地理地圖。報告先釐清既有純 CSS transform 縮放／拖曳方案在「縮放比例（ratio）」上的缺陷，以及純 HTML/CSS 方案缺乏細節層級（LOD, level of detail）而導致的效能問題；再分別評估兩種候選架構：(A) 以 Three.js 的 OrthographicCamera 呈現 2D 視圖並搭配內建控制器、(B) 以 CSS2DRenderer／CSS3DRenderer 渲染主體內容。最後提出建議架構與取捨。

1. 需求與問題定義#

1.1 需求#

需求可拆解為三項能力：

  1. 縮放（zoom）：以游標為錨點（zoom-to-cursor / anchor）放大縮小，捲動一格所對應的縮放倍率必須符合使用者直覺，可跨瀏覽器與裝置一致。
  2. 平移（pan）：拖曳以移動視埠，且平移速度須與當下縮放層級一致（放大時拖曳距離變小、縮小時變大），不可出現「越放大拖越快」或「越縮小拖越慢」的錯覺。
  3. 細節層級（LOD）：當内容（節點、邊、標籤）數量龐大時，低縮放層級顯示簡化表示，高縮放層級才顯示完整細節，以維持幀率。

1.2 Web GIS 的類比#

Web GIS 之所以能在大範圍地圖上流暢縮放，關鍵是「瓦片金字塔（tile pyramid）＋向量瓦片（vector tiles）＋連續縮放」三者的組合：

  • 瓦片金字塔：縮放層級 0 時整個世界在一片瓦片內，每一層把每片瓦片再切成 4 片（四叉樹）。縮放層級 z 的地圖像素寬度為 256 × 2^z（或 512 像素瓦片則為 512 × 2^z）1。
  • 向量瓦片：與傳統點陣瓦片不同，向量瓦片儲存的是原始幾何與屬性，由瀏覽器端以 GPU 重新繪製，因此「縮放不失真」且可動態改樣式；同時幾何資料比影像更好壓縮2.
  • 連續（小數）縮放：MapLibre GL JS 以 WebGL 每幀重算投影矩陣，原生支援小數縮放（如 z = 4.73）；Leaflet 則有 zoomSnap（預設 1）控制是否吸附到整數層級，設為 0 即為完全連續縮放34。
  • 過度縮放（overzoom）：當目前縮放超過最高可用瓦片層級時，沿用較低層級瓦片再放大顯示。MapLibre 以 OverscaledTileID 同時記錄「canonical zoom（瓦片資料實際層級）」與「overscaled zoom（顯示層級）」5；Leaflet 則以 maxNativeZoom 選項讓瓦片被自動放大4。

錨點數學（zoom-to-cursor）在 GIS 中的標準做法為：取得游標螢幕像素 → 反投影（unproject）取得世界座標 → 計算新縮放 → 將同一世界座標投影回螢幕 → 計算位移量並反向平移，使游標下的點保持不動。MapLibre 將其封裝為 calculateAnchoredCameraOptions()6。

1.3 既有純 CSS transform 方案的缺陷#

市面上最常見的縮放／拖曳方案（例如 anvaka/panzoom7、timmywil/panzoom8、BetterTyped/react-zoom-pan-pinch9、d3/d3-zoom10）本質上都是對一個容器套用 CSS transform: translate(...) scale(k)。其固有的限制如下：

(a) 縮放比例（ratio）問題

  • 滾輪步進在不同作業系統不一致：timmywil/panzoom 的 issue #560 指出，同一 step 屬性在 Windows 的 Chrome／Firefox 產生接近 120 的 deltaY，而 Edge、Opera 與 macOS 瀏覽器則接近 3，導致縮放步幅在不同瀏覽器差異極大，至今未解11。
  • 錨點漂移：timmywil/panzoom issue #538 回報反覆以固定焦點呼叫 zoomToPoint() 後視圖會隨時間漂移；即使在 Firefox 加入延遲仍會發生12。issue #331 指出在 animate: true 時快速捲動會因過場尚未結束就計算下一次縮放而「暴衝」13。issue #611 則指出當容器以 flex 置中（如彈窗圖片）時焦點縮放計算錯誤，至今仍為 open14。
  • 巢狀縮放的倍率失真：issue #647 指出若 panzoom 被放在一個本身帶有 transform: scale() 的父層內，捏合中點、捏合距離、contain 邊界與平移速度全部失準，維護者以「多數使用者不需要」為由拒絕修復15。
  • react-zoom-pan-pinch 亦有多個同類問題：issue #19 縮放時內容出現 x 偏移16、#49 當內容大於 wrapper 時縮放中心錯誤17、#264 zoomToElement 位置錯誤18、#286 resetTransform 未回到初始置中位置（v4 才修）、#392 centerOnInit 對超大圖失效（v4 才修）1920。
  • d3-zoom 系列的經典陷阱：zoomIdentity.translate().scale() 與 scale().translate() 因矩陣不可交換而結果不同21；scaleBy 搭配 SVG viewBox 時中心錯誤22；高 DPI（retina）canvas 上縮放中心偏移23；視窗 resiz後內部 transform 狀態未更新而偏移24；以及缺失可自訂參考點的 zoom.center()（issue #211 仍 open）25。

(b) 縮放必然造成的視覺劣化（ratio 問題的根源）

CSS transform: scale() 是「先依原始尺寸點陣化（rasterize），再於合成階段拉伸點陣」的後置運算。像素管線為 JavaScript → Style → Layout → Paint → Composite，而 transform 只影響 Composite，因此：

  • 文字在原始像素網格上做過的 hinting 與反鋸齒，在放大後不再正確；放大時出現插值模糊，縮小時筆畫細節被平均掉2627.
  • 邊框／筆畫會出現 次像素（sub-pixel） 取樣問題：1px 邊框在不同位置可能有時呈 1px、有時呈 2px，且邊緣半透明而造成對比下降27。
  • 瀏覽器不會在 CSS transform 之下重新向量化：向量內容（SVG）只在原始尺寸點陣化一次，之後整張材質被 GPU 拉伸28。vector-effect="non-scaling-stroke" 雖可讓筆畫寬度不隨 transform 改變，但規範僅保證在 SVG 自身 transform 屬性下可靠；若縮放來自套用在 <svg> 根元素上的 CSS transform，因整張 SVG 已被點陣化為材質再被合成器縮放，行為可能失效29. 且該屬性不影響文字本身的大小（僅影響文字的描邊）29.
  • devicePixelRatio 交互作用：高 DPI 螢幕上，若背板材質解析度與最終顯示解析度不匹配，會白白浪費高 DPI 的清晰度優勢30.
  • 大型 DOM 樹的效能：對一個龐大子樹套用 transform 會使其被提升為單一合成層，其背板材質以 devicePixelRatio 倍率配置（記憶體 ×4 或 ×9）；一旦內容變動，整個圖層需重新點陣化，可能造成掉幀；多個子元素各自形成圖層時更會「圖層爆炸（layer explosion）」，而圖層管理部分操作具有與圖層樹大小成正比的 CPU 成本3128。

(c) 缺乏 LOD

純 HTML/CSS 方案沒有「依縮放層級切換幾何細節」的原生概念，只能靠人工判斷可見性（culling）勉強維持效能，沒有幾何簡化機制。相較之下：

  • Excalidraw（約 134k stars32）以雙層 Canvas 2D（static canvas 繪形 + interactive canvas 繪選取框）繪製，僅以 isElementInViewport() 做視埠剔除，沒有超過剔除以外的 LOD32.
  • tldraw（約 51k stars33）以 React 產生 HTML/SVG 作為主體形狀（不是 canvas），輔以 Canvas 2D 繪製選取指示器；它實作了業界較完整的 LOD：空間索引＋display: none 剔除、getEfficientZoomLevel() 在超過 500 個形狀時對鏡頭移動中的縮放做「去抖（debounced zoom）」、圖片依 steppedScreenScale（貼近 2 的冪）請求低解析版本、低縮放下以純色取代陰影／虛線／網點填充、以及 textShadowLod（預設 0.35）等3435.

2. 方案 A：Three.js OrthographicCamera ＋ 內建控制器#

2.1 正交相機的焦距與縮放機制#

OrthographicCamera(left, right, top, bottom, near, far) 以 6 個平面定義一個長方體視錐；與透視相機不同，物件在成像中的大小不隨距離改變，故極適合 2D 場景36. 其縮放實作於 updateProjectionMatrix()：

const dx = (this.right - this.left) / (2 * this.zoom);
const dy = (this.top - this.bottom) / (2 * this.zoom);

zoom 愈大，可見世界區域愈小，物件看起來愈大。縮放是純粹的投影矩陣縮放，相機世界座標本身不變37. 這與 CSS transform: scale() 有本質差異：WebGL 是重新光柵化向量幾何，而非拉伸既有點陣，因此不繼承 1.3(b) 的模糊問題。

2D 設定範例（世界座標 (0,0) 置中，zoom=1 時視錐恰等於像素尺寸）：

const camera = new THREE.OrthographicCamera(-w/2, w/2, h/2, -h/2, 0, 1000);
camera.position.set(0, 0, 100);

注意：正交相機的 near 可為 0（透視相機不可）37.

2.2 內建控制器比較#

Three.js 於 examples/jsm/controls/ 提供多種控制器383940：

MapControls 是 2D 圖表最合適的選擇，因為其互動模型即為「左鍵拖曳平移、滾輪縮放」，與 Google Maps 一致；screenSpacePanning = false 會以世界平面射線求交來鎖定平移於世界 XZ 平面39. 其正交縮放為乘法／指數式：

_getZoomScale(delta) { return Math.pow(0.95, this.zoomSpeed * Math.abs(delta*0.01)); }

意即每一格滾動將 camera.zoom 乘上固定倍率，高縮放時絕對世界變化較小（細膩），低縮放時較大（粗放），避免了線性（加法）縮放在放大時過快、縮小時過慢的違和感38.

平移與縮放皆正確地除以 zoom。此為 2016 年修復 issue #8340 的成果：修正前正交相機的平移距離會受縮放層級影響（放大後拖太快、縮小後拖太慢），修正後改為 deltaX * (right-left) / zoom / clientWidth41.

zoomToCursor 的正交實作為：以 unproject() 取得縮放前的世界座標與縮放後的世界座標，再以位移差修正相機位置，使游標下的點保持不動38：

const mouseBefore = new Vector3(this._mouse.x, this._mouse.y, 0);
mouseBefore.unproject(this.object);
this.object.zoom = ...;
this.object.updateProjectionMatrix();
const mouseAfter = new Vector3(this._mouse.x, this._mouse.y, 0);
mouseAfter.unproject(this.object);
this.object.position.sub(mouseAfter).add(mouseBefore);

2.3 LOD 與效能#

  • LOD 類別：addLevel(object, distance, hysteresis) 依距離切換層級，update(camera) 內部計算 distance = camera 與物件距離 / camera.zoom，已除以 camera.zoom，故正交相機縮放亦能正確觸發 LOD 切換42. hysteresis 為避免邊界抖動的遲滯帶42.
  • InstancedMesh：以單一 draw call 繪製大量同幾何物件，但 Three.js 對其以整體包圍球做視錐剔除，不會對個別實例剔除；需手動調整 mesh.count 或改用第三方 InstancedMesh243.
  • 視錐剔除：Object3D.frustumCulled 預設為 true，渲染器以包圍球與視錐求交決定是否送 draw call44.
  • 官方效能建議：合併幾何（mergeGeometries()）以減少 draw call、動畫用 morph targets、靜態物件設 matrixAutoUpdate = false、盡量避免透明物件、重用 Vector3/Matrix4、正確 dispose() GPU 資源4546.

2.4 線條與文字在「任意縮放」下的清晰度#

純 CSS 方案難以維持筆畫寬度；Three.js 有多種對策：

  • Line2 / LineSegments2 + LineMaterial：以 instanced 三角帶（fat line）繪製寬線，頂點著色器以 offset /= resolution.y 將像素寬度換算回 NDC，因此預設（worldUnits: false）線寬維持固定的螢幕像素寬，不隨相機縮放改變；設 worldUnits: true 才會隨縮放改變。相對地 THREE.Line + LineBasicMaterial 的 linewidth 在 WebGL/WebGPU 被忽略，恆為 1 像素4748. LineSegments2.onBeforeRender 每幀自動更新 resolution uniform49.
  • 文字清晰度：SDF（signed distance field）計算法在片段著色器以 smoothstep(0.5 - fwidth(sd), 0.5 + fwidth(sd), sd) 於當下解析度重建邊緣，故縮放不模糊。troika-three-text（所屬 monorepo 約 2.0k stars50）可直接解析 ttf/otf/woff 並在 Web Worker 產生 SDF atlas，支援 kerning、連字、RTL、自動 Unicode 回退；限制為 SDF atlas 尺寸上限（sdfGlyphSize 需為 2 的冪）、非同步產生需監聽 synccomplete、不支援 woff2、worker 以字串 eval 建立故可能被 CSP 阻擋（可設 useWorker: false）50. MSDF（多通道 SDF，msdfgen 約 5k stars）尖角更銳利，但需離線預先產生 atlas51. TextGeometry 為真實擠出幾何、可任意縮放，但 tessellation 固定、長字串昂貴、須先轉換字型 JSON52. Canvas 材質文字則因固定點陣解析度，在放大時必然模糊，即使以 devicePixelRatio 放大亦僅延後問題53.

3. 方案 B：CSS2DRenderer / CSS3DRenderer 渲染主體#

3.1 CSS2DRenderer#

CSS2DRenderer 是 CSS3DRenderer 的簡化版，僅支援平移與 2D 旋轉；它把 CSS2DObject 轉為 DOM 元素，將物件 3D 世界座標經 viewProjectionMatrix 投影為螢幕座標，並設定：

element.style.transform = `translate(${-cx}%, ${-cy}%) translate(${tx}px, ${ty}px) rotate(${angle}rad)`;

其中沒有 scale()54. 因此：

  • CSS2D 標籤不隨相機縮放改變像素大小——這是設計使然，讓標籤在任意距離都保持可讀；社群曾提出需求（issue #9246）欲讓其縮放，被 mrdoob 以情境過於小眾關閉，最常見的 workaround 是自行在 transform 後追加 scale(camera.zoom, camera.zoom)55. 若希望標籤隨縮放縮放，須在動畫迴圈動態調整 font-size（baseFontSize * camera.zoom）55.
  • 官方文件亦註明其僅支援 100% 瀏覽器與顯示縮放（否則座標對應會失準）56.
  • 效能上為純 DOM 定位、無 canvas/WebGL，但每個 CSS2DObject 都是一個真實 DOM 節點，且每次 render() 皆重算 transform、並可能對整個場景做 z-index 排序，故適合數十至數百個標籤，不適合數千個56.
  • 適用情境：3D 物件上的標籤、提示、註解、量測標籤等需要恆定可讀大小的疊加 UI。

3.2 CSS3DRenderer#

CSS3DRenderer 以 CSS transform 的 matrix3d() 對 DOM 套用完整階層式 3D 變換，並以 CSS perspective() 模擬透視；其 DOM 結構為 domElement → viewElement → cameraElement → CSS3DObject，且有樣式快取（僅在字串變動時寫入 DOM）57. 重要事實：

  • 對正交相機的支援是後來才加入的。2017 年 issue #11534 中 mrdoob 曾言「我不認為 CSS3D 支援正交投影」；2018 年（R92）由 yomotsu 補上支援後關閉58. 官方現有範例 css3d_orthographic.html 即以 OrthographicCamera 同時搭配 WebGL 與 CSS3D 渲染同一場景59.
  • 兩種相機的 CSS 變換策略不同：透視相機用 translateZ() ＋ perspective()；正交相機改用 scale() ＋ translate()，不使用 perspective()57.
  • 正交路徑反而較銳利：issue #17641 中使用者發現透視相機路徑因 perspective() 觸發 GPU 光柵化而使 CSS 內容模糊；yomotsu 解釋「一旦套用 CSS-Transform3D，元素就會依初始尺寸光柵化，因 GPU 加速而不再是向量圖」60. 正交相機因改用 scale() 可較清晰。
  • 限制：官方文件明列「無法使用 Three.js 材質系統」「無法使用幾何」，舊版文件另列「僅支援 100% 瀏覽器與顯示縮放」61. 另有 setViewOffset 曾不受支援、後於 2023 年補上 viewElement 處理的問題62. DOM 開銷與 CSS2D 類似，適合數十至數百個「3D 卡片」型內容。

3.3 以 CSS Renderer 作為「主體」的問題#

若以 CSS2D／CSS3D 渲染圖表主體，會遇到：

  1. DOM 節點數 = 內容數，數千節點即造成 layout/reflow/paint 瓶頸56。
  2. CSS3D 沒有材質與幾何系統，複雜圖形須以 HTML/CSS 拼湊61.
  3. 僅支援 100% 瀏覽器縮放，使用者以瀏覽器縮放即錯位56.
  4. CSS2D 根本不縮放，若硬要縮放需自行 hack；CSS3D 雖縮放，但 matrix3d 之光柵化仍可能使內容模糊60.
  5. 仍不具備自動 LOD 與空間剔除，僅能做 DOM 層的人工剔除。

換言之，CSS Renderer 適合當「標籤／疊加層」，不適合作為「大量幾何主體」。

5. 建議架構#

綜合以上，建議採用混合式（hybrid）架構，而非單一方案：

  1. 幾何主體交由 WebGL＋OrthographicCamera 渲染：節點、邊以 InstancedMesh／合併幾何與 Line2 系列繪製，獲得正確的縮放比例與清晰度。
  2. 控制器採 MapControls：左鍵拖曳平移、滾輪縮放、啟用 zoomToCursor；設定 minZoom/maxZoom 並於頂點場景設定 screenSpacePanning = false39. 若日後需要自由旋轉再切回 OrbitControls.
  3. LOD 三層策略（對應 Web GIS 的瓦片金字塔概念）：
    • 幾何 LOD：以 LOD 類別（addLevel + hysteresis）依 distance / camera.zoom 切換簡化幾何42，或用螢幕空間誤差（screen-space error，SSE）門檻。SSE 的權威定義來自 Cesium 3D Tiles 規範：SSE = (geometricError × viewportHeight) / (2 × distance × tan(fovY/2))，當 SSE 超過門檻即細化到子節點72.
    • 內容 LOD：低縮放下隱藏或簡化次要元素（標籤合併、隱藏邊權重、以純色取代陰影與虛線），可參考 tldraw 的實務門檻（debouncedZoomThreshold 500、textShadowLod 0.35 等）34.
    • 剔除（culling）：保留 Three.js 預設視錐剔除44；對 InstancedMesh 手動依可見實例調整 mesh.count43.
  4. 標籤／UI 交由 CSS2DRenderer：將需要恆定可讀大小的標籤以 CSS2DObject 疊加於 WebGL canvas 之上（兩者可共用同一場景與相機，各自忽略對方型別的物件）56. 若需求為「世界座標等寬的標籤」，則改以 SDF 文字（troika-three-text）繪於 WebGL 內50，避免 DOM 開銷。
  5. CSS3DRenderer 僅在需要 3D 卡片式內容時才使用，且優先搭配正交相機路徑以避免透視路徑的模糊問題60.

決策準則：

  • 內容以簡單幾何（節點球、邊線）+ 大量為主 → Three.js WebGL 主體 ＋ CSS2D 標籤。
  • 內容以豐富 HTML（表格、影片、可選文字） 為主且數量在數百以內 → CSS3DRenderer（正交相機）。
  • 內容僅數十個且需與 DOM 生態密切整合、不介意模糊 → 純 CSS transform 方案（成本最低，但不可期待 LOD 與清晰度）。

6. 結論#

  1. 既有純 CSS transform 縮放／拖曳方案之所以「縮放比例處理不好」，根因在於 transform: scale() 是後置的點陣拉伸（必然模糊、次像素失真），加上滾輪 deltaY 跨瀏覽器不一致與錨點計算在 flex 置中、巢狀縮放、retina 等情境下的實作缺陷；這不是個別函式庫的疏漏，而是架構性的限制2728111415.
  2. 純 HTML/CSS 沒有 LOD 概念，難以支撐大型圖表；即使是 Excalidraw 也只做到視埠剔除，tldraw 才建立了較完整的 LOD 機制3234.
  3. Three.js OrthographicCamera ＋ MapControls 是需求的正解方向：正交投影適合 2D、縮放為投影矩陣縮放而非點陣拉伸、內建控制器已修正平移速度隨縮放的問題並提供 zoomToCursor37394138. 搭配 LOD、InstancedMesh、Line2、SDF 文字可同時滿足清晰度、比例正確性與效能42434750.
  4. CSS2DRenderer 應定位為「標籤／疊加層」而非主體：它不隨縮放改變像素大小（設計使然）且受限於 100% 瀏覽器縮放與 DOM 節點數56. CSS3DRenderer 可與正交相機搭配（R92 後支援），且在正交路徑下比透視路徑更清晰，但缺乏材質／幾何系統、效能受 DOM 節點數限制，適合作為 3D 卡片式內容而非大量幾何主體586061.
  5. 最佳實務為混合架構：WebGL 繪幾何主體與 LOD，CSS2D 疊標籤，必要時才以 CSS3D 承載豐富 DOM 內容；並以 Web GIS 的「錨點縮放 + 分層 LOD + 剔除」三原則指導實作67239.
