00532_openmetadata-domain-model-and-concepts

使用 OpenMetadata 必備的心智模型、領域模型、概念與領域知識#

摘要#

OpenMetadata 是一套開源的資料目錄（data catalog）、中繼資料管理（metadata management）與資料治理平台，官方定位為「資料與 AI 的開放情境層（The Open Context Layer for Data and AI）」1。本報告整理使用 OpenMetadata 前必須先建立的心智模型（mental model）、領域模型（domain model）、核心概念（concepts）與領域知識（domain knowledge）。

本報告以 OpenMetadata v2.0.x 官方文件與 OpenMetadata Standards 規格為主要來源23，並補充 GitHub 專案資訊1。全文為獨立文件，不需任何前置背景即可閱讀。

OpenMetadata 目前為 Apache-2.0 授權1，GitHub 上約 15.5k stars、2.5k forks1，最新版本為 2.0.5（2026-10-08 發布）4。

一、專案背景：它在生態系中的位置#

1.1 什麼是 OpenMetadata#

OpenMetadata 是一個統一的中繼資料平台，將技術中繼資料（technical metadata）、資料品質訊號、血緣（lineage）、欄位級血緣、擁有權、使用情形、政策、對話、記憶（memories）、詞彙表（glossaries）、分類（classifications）、指標（metrics）、領域（domains）、資料合約（data contracts）與資料產品（data products）串接成一個統一的「中繼資料知識圖譜（metadata knowledge graph）」1。

它提供 130+ 個連接器（connectors）、開放中繼資料標準、語意搜尋（semantic search）、API、SDK，以及一個 MCP server，讓每一個使用者與 AI 系統都能取得受治理的情境（governed context）1。

1.2 為什麼它對 AI 時代重要#

官方論述的核心是：AI 不需要另一個原始資料庫連接器，AI 需要的是「情境（context）＋記憶（memory）」1。一個直連倉儲、湖、儀表板或管線的連線，只暴露了原始結構，它不會告訴 AI 助理：

  • 這份資料是什麼意思
  • 是否已被認證（certified）
  • 誰擁有它
  • 哪些政策適用
  • 哪份合約管轄它
  • 若它改變會破壞什麼
  • 組織已經對它學到了什麼1

1.3 開源與商業化的關係#

OpenMetadata 由 Collate 公司主導，採開源（Apache-2.0）核心加上商業產品的模式14。其規格另外以 OpenMetadata Standards（openmetadatastandards.org）形式獨立發布，作為跨工具的中繼資料模型標準3。

二、最重要的心智模型（Mental Models）#

理解 OpenMetadata 之前，先建立以下五個心智模型，後續所有概念都會容易得多。

心智模型 1：Schema-First（規格優先）#

OpenMetadata 是「schema-first」平台。所有實體（entity）的定義都以 JSON Schema 撰寫，作為整個平台的唯一真實來源（single source of truth）5。

從同一份 JSON Schema，自動產生三種語言的程式碼：

  • Java 類別 → 給 API 後端（openmetadata-service）使用
  • Python 類別 → 給 Ingestion Framework 使用
  • TypeScript 型別 → 給 UI 使用5

官方說法是「三個視圖、同一個來源（three views from the same source）」，藉此保證 API、擷取層與 UI 對「實體」的認知完全一致，不會產生漂移5。

flowchart TD
    JS["JSON Schema<br/>(單一真實來源)"] --> J["Java Classes<br/>(API 後端)"]
    JS --> P["Python Classes<br/>(Ingestion Framework)"]
    JS --> T["TypeScript Types<br/>(UI)"]
    JS --> R["RDF / OWL 本體論"]
    JS --> S["SHACL 驗證形狀"]
    JS --> L["JSON-LD Context"]

心智模型 2：屬性與關聯分離（Attributes vs. Relationships）#

每一個中繼資料實體都有兩類欄位5：

  1. 屬性（Attributes）：實體的內在性質，例如 name、id、Table 的 columns、ML Model 的 algorithm。這些以 JSON 文件形式儲存在各自的實體表中（例如 table_entity）。
  2. 關聯（Relationships）：實體之間的關聯，以**圖的節點與邊（graph nodes/edges）**形式儲存在同一張 entity_relationship 表。邊上帶有關聯型別，例如 contains、uses、follows、owns。

這種分離的設計目的是「解耦關注點」，讓相關實體可以獨立處理，並在執行期驗證需要更新或檢索何種資訊5。

flowchart LR
    subgraph Store["儲存層"]
        A["實體表<br/>(JSON 文件)<br/>table_entity, dashboard_entity, ..."]
        B["關聯表<br/>(圖邊)<br/>entity_relationship"]
    end
    E["Entity"] --> A
    E --> B

心智模型 3：Service 是階層的根（Service as Root）#

「Service」代表與一個外部系統的連線，它是容器階層的最頂端，擁有其下所有資產5。FQN（fully qualified name）會以 Service 名稱作為前綴。

flowchart TD
    S["DatabaseService<br/>my_postgres"] --> D["Database<br/>analytics"]
    D --> SCH["DatabaseSchema<br/>public"]
    SCH --> TB["Table<br/>customers"]
    TB --> C1["Column<br/>id"]
    TB --> C2["Column<br/>email"]
    SCH --> SP["StoredProcedure"]

刪除 Service 會連帶清除其下所有 Database、Schema、Table、Column6。這是使用上最容易誤觸的破壞性操作之一。

心智模型 4：FQN 是實體的身分證#

每個實體都有 fullyQualifiedName（FQN），由其在階層中的位置推導而來。格式為點分階層56：

service.database.schema.table.column

不同領域的 FQN 也遵循相同邏輯：

FQN 由伺服器在 Prepare 階段依實體階層計算產生5。API 可用 GET /api/v1/<collection>/name/{fqn} 依 FQN 取得實體6。

心智模型 5：三種表示形式（JSON Schema / RDF-OWL / SHACL）#

OpenMetadata Standards 對同一套中繼資料模型提供三種互補表示3：

  1. JSON Schema（Draft-07）：911 份 schema，為主要格式，用於 REST API、驗證、程式碼產生37。
  2. RDF / OWL 本體論：Turtle 檔定義類別、屬性、階層、domain/range 限制；可 SPARQL 查詢，支援推理與知識圖譜3。另有 Provenance Ontology 延伸 W3C PROV-O，用於血緣3。
  3. SHACL 形狀：W3C SHACL 用於 RDF 資料的基數、型別、值域、關聯等限制驗證3。

兩者之間的橋樑是 JSON-LD contexts，將 JSON 屬性映射到 RDF 屬性，實現自動轉換3。

flowchart BT
    JS["JSON Schemas (911 份)<br/>Form 1：基礎定義"]
    ONT["OpenMetadata 本體論<br/>Form 2：RDF / OWL"]
    JL["JSON-LD 映射層"]
    SH["SHACL 驗證層<br/>Form 3"]
    APP["應用：知識圖譜 / 語意搜尋 / 推理"]

4.1 Service 與 Connector#

4.2 Ingestion Framework（擷取框架）#

Ingestion Framework 是 OpenMetadata 與外部系統之間的介面，以 Python 撰寫，包含所有 Connectors5。其核心設計是拓樸式執行（topology-based execution）8：

  • 每個 source 宣告一棵 topology tree，由 TopologyNode 組成，框架以**深度優先（depth-first）**巡訪8。
  • 每個 TopologyNode 有：producer（產生原始項目，如資料庫名稱）、stages（把項目轉成 entity request 的處理步驟）、children（子節點）、post_process（子節點完成後的清理，例如 mark_tables_as_deleted()）8。
  • TopologyContext 是執行緒安全的狀態物件，追蹤目前在階層中的位置，以便子節點建構 FQN8。

4.7 資料血緣（Data Lineage）#

血緣是有向圖：節點為實體（table、pipeline、dashboard、ML model、topic 等），邊為有方向的資料流11。

模型建立在 W3C PROV-O（Provenance Ontology） 標準上117：

  • Entity → 資料資產
  • Activity → 管線、查詢、作業（轉換）
  • Agent → 使用者、服務、團隊（執行活動者）

EntityLineage schema 的頂層屬性為 entity（圖的中心實體）、nodes（其他實體）、upstreamEdges、downstreamEdges11。每條 Edge 有 fromEntity、toEntity、lineageDetails、description11。

實體級 vs 欄位級血緣11：

  • 實體級（table-level）：整個資料集之間的高階依賴。
  • 欄位級（column-level）：細緻對應個別欄位如何流動與轉換。

  "toColumn": "staging.users.full_name",
  "function": "CONCAT"

轉換型別包含 Identity（原樣複製）、Derived（衍生，如 UPPER/CONCAT）、Aggregate（聚合，如 SUM/COUNT/AVG）、Join（連接條件使用）11。

血緣的來源（lineageDetails.source 列舉）11：Manual、ViewLineage、QueryLineage、PipelineLineage、DashboardLineage、DbtLineage、SparkLineage、OpenLineage、ExternalTableLineage、CrossDatabaseLineage、ChildAssets。

  2. Airflow Lineage Backend：每個 DAG 成為一個 Pipeline Entity；task 用 inlets / outlets 宣告血緣（inlets → 上游、outlets → 下游）。
  3. OpenLineage connector：從 Kafka broker 或 AWS Kinesis Data Streams 消費 OpenLineage 事件，支援至 OpenLineage 1.7.0。

4.8 資料品質與可觀測性（Data Quality & Observability）#

資料剖析器（Data Profiler） 擷取資料的統計樣貌（表與欄位的分布與描述統計），隨 profiler ingestion 執行，可輔助驗證假設，並支援自動 PII 標記與 Spark 引擎12。

Metric 是最小建構單元：對 Table 或 Column 執行的一次計算12。表級 metric 如 Row Count、Column Count；欄位級 metric 如 Values Count、Null Count、Distinct Count、Min/Max、Mean、Median、Sum、Standard Deviation、Histogram、四分位數等12。

資料品質七大維度12：

四個品質實體12：

  • TestDefinition：可重複使用的測試模板，定義「檢查什麼」，OpenMetadata 內建 50+ 種12。
  • TestCase：TestDefinition 的實例，套用到特定表／欄位並帶具體參數與結果12。狀態為 Success、Failed、Aborted、Queued12。
  • TestSuite：測試案例群組，分為 Executable（綁定單一表、透過 pipeline 自動執行）與 Logical（跨表的使用者自訂群組、無 pipeline）12。
  • TestResult：一次執行的結果，含時間戳、狀態、實際值、樣本資料127。

Profiling 與 Data Quality 的差異12：

測試結果流（端到端）12：定義 TestDefinition → 實例化 TestCase → 組織成 TestSuite → 執行（管線完成或排程觸發）→ 記錄結果 → 失敗則自動開啟 Incident → 送 Alert → 在 Incident Manager 處理 → 留存歷史作為疑難排解手冊。

4.9 資料合約（Data Contract）#

Data Contract 是資料生產者與消費者之間正式、可版本化的協定，定義資料資產的結構、品質、語意與 SLA，把隱含期待（例如「此欄位必有值」、「資料每日 6 點前更新」）轉為明示且可強制執行的條款13。每個資產最多只能有一份自己的合約13。

合約分為 七大區段，其中三個在執行時會被實際檢查13：

Schema 檢查：型別以**家族（family）**比對（Text 家族含 STRING/VARCHAR/TEXT；Integer 家族含 INT/BIGINT/TINYINT）。缺少或重複欄位會使執行失敗；型別不符會被回報但不會失敗13。

Semantics 檢查：規則是以 JSON Logic 運算式對資產中繼資料評估，UI 提供的欄位包含 Owners、Display Name、Description、Domain、Tags、Glossary Term、Tier、Updated on、Updated by、Version、Status；運算式返回 true 才通過13。

Quality 檢查：儲存含測試案例的合約時，OpenMetadata 會建立一個 test suite 與一個執行它的 pipeline；每次合約執行都觸發該 pipeline；最新結果為 Failed 或 Aborted 的測試算作失敗13。

執行狀態：Running、Success、Failed、Aborted13。可透過 UI「Run now」、API POST /v1/dataContracts/{id}/validate、或排程（Data Contract Validation 應用預設每日午夜執行）觸發13。

ODCS 關係：OpenMetadata 支援以 Open Data Contract Standard（ODCS）v3.1.0 匯入／匯出合約（向下相容 v2.2.x、向上可讀 v3.2.0）13。轉換並非一對一，ODCS 有些欄位無對應（會回報「未匯入」）；ODCS 的品質規則會轉成 OpenMetadata 測試案例；廠商特定檢查（Soda、Great Expectations、dbt、Monte Carlo）會被儲存但不執行13。

強制層級13：

資料產品繼承：僅屬於恰好一個資料產品的資產，會繼承該產品已核准的合約（含 semantics、security、SLA、terms of use，但不含 schema 與 quality）；資產若有自己的合約則優先使用自己的13。

4.10 治理與存取控制（RBAC + ABAC）#

OpenMetadata 的授權由三個原語構成，回答三個問題：誰是使用者、要存取什麼、想做什麼9。

Rule（規則） 是授權的原子單位，包含9：

Condition 提供 ABAC 維度，可檢查資產屬性：noOwner()、isOwner()、matchAllTags(...)、matchAnyTag(...)、matchTeam()、hasDomain()，可用 && / || 組合9。

Policy（政策） 是一組具名規則9：

  • 衝突解決：同一政策內規則衝突時，Deny 永遠勝出。
  • 指派模型：政策指派給團隊，不指派給個人；使用者加入團隊即繼承該團隊所有政策。
  • 繼承：政策沿團隊階層向下流動。
  • 設計原則：在階層頂端（Organization）設廣泛寬鬆規則，往下逐漸收嚴。

Role（角色） 是符合職務的政策套裝，可指派給個人使用者或整個團隊9。

檢視權限階層（逐層疊加）9：ViewBasic（名稱、型別、擁有者）→ ViewAll（完整 schema、血緣、標籤）→ ViewDataProfile（欄位剖析統計）→ ViewUsage（查詢頻率與存取者）→ ViewQueries（實際 SQL）→ ViewSampleData（實際列級資料）→ ViewTestCaseFailedRowsSample（失敗測試的列）9。

團隊階層9：Organization → BusinessUnit → Division → Department → Group。只有 Group 可以擁有資料資產9。

職責分離（Separation of Duties）9：例如管線部署由資料工程師（Create/EditAll）與管線核准者（Deploy）分工；PII 標記由資料管家（EditTags）與合規人員（稽核）分工。

認證面向（Authentication）：人類使用者可經 SSO（Azure AD、Google、Okta、Auth0、LDAP、SAML 等）；機器人／服務帳號則以基於 SSL 憑證的 JWT token 認證9。

4.11 指標（Metric）與 KPI#

Metric 記錄一個計算值的名稱、意義與公式／SQL。Metric 是純文件性質，OpenMetadata 只儲存定義，不計算數值9。屬性含 Name（camelCase，如 customerRetentionRate）、Display Name、Description、Expression（含語言標註 SQL/Python/Java）、Granularity（Daily/Weekly/Monthly）、Metric Type（Count/Average/Ratio/Percentage）、Unit of Measurement、Owner9。

KPI 則由 Data Insights 計算，追蹤平台健康狀態（例如「多少百分比的表有描述」）914。主要 KPI 類別為 Completed Description 與 Completed Ownership14。

4.12 資料探索（Data Discovery）#

OpenMetadata 提供單一目錄，以關鍵字搜尋、關聯（常被一起 join 的表、血緣）與複雜查詢探索資料15。

  • 階層檢視（Hierarchical View）：依關係與依賴以結構化分層呈現，可展開／收合。關鍵字搜尋：Ctrl+K / Cmd+K，由 Elasticsearch 支援，比對名稱、描述、元件名稱15。
  • 快速篩選：依 Owner、Tag、Tier、Data Product、Service、Service Type、Database、Schema、Columns，甚至軟刪除資產15。
  • 進階搜尋：視覺化查詢建構器（免語法），以 Field + Operator + Criteria 組成多條件 AND/OR15。
  • 探索關聯：常被 join 的表／欄位（由 profiler 量測）與上下游血緣15。

資產詳情頁的頁籤包含 Schema、Activity Feeds & Tasks、Sample Data、Queries（僅表）、Data Observability（僅表）、Lineage、Custom Properties、Executions（僅 pipeline）、Features（僅 ML model）、Details（dashboard/ML model）15。

API 遵循一致的 RESTful 模式6：

GET    /api/v1/<collectionName>             # 列表（含篩選、分頁）
GET    /api/v1/<collectionName>/{id}        # 依 ID 取得
GET    /api/v1/<collectionName>/name/{fqn}  # 依 FQN 取得
POST   /api/v1/<collectionName>             # 建立
PUT    /api/v1/<collectionName>             # 建立或更新
PATCH  /api/v1/<collectionName>/{id}        # 依 ID 部分更新
DELETE /api/v1/<collectionName>/{id}        # 刪除（預設軟刪除）

所有實體共通的 API 特性：分頁（cursor 與 offset）、版本（GET /{id}/versions）、軟刪除與還原、fields 參數（GET /{id}?fields=owner,tags,usageSummary）6。

內部採用 EntityResource + EntityRepository 模式：前者處理 HTTP 請求、驗證 schema、管理認證；後者是 DAO 層，負責 CRUD、FQN 建構、關聯管理與變更事件6。

5.4 POST / PUT 流程#

POST（建立）5：

  1. Prepare：驗證資料、計算 FQN、檢查關聯
  2. Store：剝除 href 屬性後將 JSON 文件存入實體表；將關聯圖邊存入 entity_relationship
  3. 回傳建立的實體

PUT（建立或更新）5：若不存在則同 POST；若存在則只允許可變欄位變更（id、name 不可變），更新後寫回並視需要修改關聯。

5.5 內部 SDK#

Python 的 OpenMetadata 類別（位於 ometa/ometa_api.py）由 25+ mixins 組成，模組化存取 API8：OMetaTableMixin、OMetaPipelineMixin、OMetaDashboardMixin、OMetaPatchMixin、OMetaTagGlossaryMixin、OMetaServiceMixin、OMetaLineageMixin 等8。
